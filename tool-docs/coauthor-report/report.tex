{\LARGE\bfseries VCF-RDFizer: coauthor discussion brief}\\[4pt]
{\small 1 October 2026 \textbullet\ Current manuscript and next decisions}

\hd{1. What is the paper's argument?}
\textbf{VCF-RDFizer turns genomic variant files into a shared graph with explicit
links and access rules. These benefits must justify the cost of conversion.}

VCF is a file format for genomic variants. RDF represents data as a graph of
statements called \emph{triples}; SPARQL is its query language. Conventional VCF
tools can answer the same biological questions. The proposed benefit is making
links between datasets and access rules explicit and independently checkable.

\textbf{Meeting goal:} agree on the central claim, the experiments needed before
submission, and what belongs in the main text.

\hd{2. What has been demonstrated?}
\emph{Which participants carry a ClinVar-classified variant in the 81 genes on
the ACMG secondary-findings list, and which results may each requester receive?}

ClinVar supplies variant classifications. We use real public genomes with
\textbf{simulated consents}: research, clinical care only, or withdrawal. A further
rule restricts results in 28 cancer-predisposition genes to clinical care.
A clinical laboratory, cardiovascular study and biobank therefore receive
different results.

\sub{What the experiment establishes}
\begin{itemize}[itemsep=3pt]
\item \textbf{Every requester receives the same answer in both implementations:}
the RDF route and an independent \texttt{bcftools} + Python pipeline. Each released
dataset is also checked against the rules and the source VCF.
\item Shared identifiers join variants despite different chromosome names; the
cohort also joins a separate frequency file to identify rare variants.
\item Results include \emph{all} ClinVar classifications. The pathogenic/likely
pathogenic subset has 0 carrier matches in the five-genome setup and 8 in the cohort.
\end{itemize}

\textbf{Interpretation:} this supports linked analysis and correct implementation
of the simulated access rules. It does not establish real-world consent validity.

\newpage
{\Large\bfseries Validation: what was tested}

\hd{3. How well is the conversion checked?}
\textbf{The test is whether conversion preserves the source data, and whether
our checks would notice an error.} It does not assess whether the original
biological variant calls are correct.

The base benchmark contains 143 recorded cases across ten public files and
controlled experiments that vary record or sample counts. The validation evidence
comes from three complementary checks:

\sub{A. Do the VCF and RDF give the same answers?}
We ask 13 questions twice: once by reading the original VCF, and once by querying
the converted graph. These \emph{paired comparisons} cover record and allele
counts, genotypes, file metadata, and summaries of record and annotation values.
They test more than whether conversion produced a readable file.

\begin{tabularx}{\textwidth}{@{}L >{\raggedright\arraybackslash}p{0.39\textwidth}@{}}
\toprule
\textbf{Recorded result} & \textbf{What was covered}\\
\midrule
984 matching answers; 0 disagreements & Fixtures and slices up to 100,000 records (17.1M triples).\\
\addlinespace
4 comparisons not applicable & Two genotype questions on each of two empty-file artifacts; there are no records to compare.\\
\addlinespace
1,144 consistency checks passed & Relationships between results, such as component counts summing to the expected total.\\
\bottomrule
\end{tabularx}

Separate retrieval experiments also found matching query answers on the
657M-triple whole-genome graph. These runs check those answers; they do not run
the full set of structural checks described below.

\sub{B. Would a conversion error be detected?}
Passing on valid data is only useful if the checks can fail on bad data. We
therefore introduced 113 deliberate faults into test graphs, such as a wrong
allele, coordinate, sample index or phasing value.

\textbf{The query comparisons detected 96 of 113 faults (85\%).} The remaining
17 escaped because the queries do not inspect every relationship or value.
SHACL adds rules about the graph itself: which values and links must exist,
their datatypes, and whether related values agree. With all three SHACL rule
sets (\emph{profiles}) enabled, \textbf{113 of 113 faults were detected}; the two
unchanged control graphs still passed.

\textbf{The open experiment concerns the default settings.} The full rule set
is costly: on a roughly 2,000-triple graph, the two advanced profiles took 33.7
and 73.2 seconds, versus 1.7 seconds for the default profile. Routine validation
therefore uses the default, with the full set reserved for small inputs. The
default found no violations in 58 ordinary validations, but its detection rate
on the 113 faulty graphs is not yet reported. These are different questions.

\sub{C. Can the compressed output be read back?}
HDT and COTTAS are compressed RDF formats. All \textbf{152 artifacts} (118 HDT,
34 COTTAS) decoded successfully with the same triple count as their source graph.
This covers larger outputs too, but matching counts alone cannot show that every
value is preserved. In a separate round-trip test, compression and decompression
also reproduced the original content digest.

{\Large\bfseries Retrieval: the workload determines the benefit}

\hd{4. When is the extra cost worthwhile?}
\textbf{Repeated questions can repay the conversion cost; a single batch of
summaries does not in this experiment.} We tested the same 13 questions on a
100,000-record HG005 slice (17.1M triples), comparing a direct VCF reader
(\texttt{cyvcf2}) with QLever, a graph query engine. Answers agreed before timings
were compared; results below average three repetitions.

(a) Individual questions and the complete batch on the 17.1M-triple graph;

(b) Four engines on a smaller, 0.96M-triple graph, excluding setup.
(c) QLever after loading the same 17.1M-triple graph from three storage formats.
Panels (b) and (c) use different graph sizes.}

\sub{Read the speed-up together with its setup cost}
\begin{itemize}[itemsep=4pt]
\item \textbf{One question:} a VCF scan takes 11.5\,s; an indexed QLever query
takes 0.005--4.62\,s. However, conversion takes 423.7\,s and QLever indexing a
further 22.8\,s before the first query.
\item \textbf{All 13 questions together:} one VCF pass takes 12.4\,s, versus
17.1\,s of QLever query time, even before setup. Batching avoids repeated VCF scans.
\item \textbf{Repeated, separate questions:} QLever averages 1.32\,s per question,
saving about 10.2\,s per VCF scan. Recovering the roughly 447\,s conversion and
indexing cost takes \textbf{about 44 questions}, assuming this question mix and
reuse of the same graph. This is not a universal threshold.
\end{itemize}

QLever builds its own index from each format. Query times differ by under 5\%
(Figure 3c); HDT and COTTAS chiefly affect storage and transfer in this test.

{\Large\bfseries Cost trade-offs: region size and sample representation}

\sub{Indexed VCF is a stronger baseline for regional lookups}
Tabix indexes VCF records by genomic position, avoiding a whole-file scan. We
compared five regional questions over 20 windows per size, with three repetitions.
Across both tested graphs, 11,160 executions had no failures or disagreements.
On the 17.1M-triple graph:

\sub{Sample profiles change the amount of graph we need to build}
We held 10,000 variant records fixed and increased the sample columns from 1 to
2,504. \textbf{Expanded} stores each sample call as graph resources and values.
\textbf{Condensed} packs values into sample-ordered vectors: fewer triples, but
retrieving an individual sample value requires decoding its position.

\begin{center}
\includegraphics[width=0.83\textwidth]{figs/fig-samples.pdf}
\end{center}
\figcaption{\textbf{Figure 4. Fewer triples do not mean that sample data disappear.}
Condensed vectors lengthen as samples are added: their HDT grows from 10.2 to
59.2\,MB. At 2,504 samples, expanded has 432 times the triples but 69 times the
HDT bytes (4.10\,GB). The $\times390$ label in (a) instead measures expanded
growth from 1 to 2,504 samples.}

\sub{Storage and construction remain substantial costs}
In the whole-genome benchmark, producing 657M triples and compressed outputs took
\textbf{16.1 hours}, including 14.5 hours building HDT and COTTAS. HDT, its index
and COTTAS together occupied 10.88\,GB versus a 139\,MB compressed VCF download
(78 times larger). This is a different configuration from the clinical use
case's 53-minute conversion, which reports later stages separately.

\hd{6. Decisions for the coauthors}
\begin{enumerate}[itemsep=9pt]
\item \textbf{Is the demonstrated benefit convincing?} Are shared identifiers,
inspectable policies and checked release sufficient with simulated consents, or
do we need an external user or data-access partner? Rules take 72 authored lines
in RDF versus 131 in the baseline, but three of four tested changes are similarly
small in both. This does not establish a general usability advantage.
\item \textbf{How much validation is enough?} Are the two targeted runs above
sufficient with the reported scope, or is complete whole-genome validation
required? The latter needs more work on the costly structural checks.
\item \textbf{Do we need a measured converter comparison?} The current comparison
with other converters is based on documentation. Decide whether to add one
shared-input experiment and which outcomes it should compare.
\item \textbf{What belongs in the main story?} Keep conversion, validation and the
linked-data use case central; present HDT/COTTAS as measured storage choices.
Agree whether the policy component belongs here or warrants a separate paper,
and how this submission relates to the companion vocabulary paper.
\item \textbf{What can wait?} Federation with other graph services, alternative
variant identifiers, whole-cohort conversion and sample-level access control
in multi-sample files are future work unless essential to the central claim.
Choose which detailed tables move to the supplement.
\end{enumerate}
