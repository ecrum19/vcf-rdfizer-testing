\section{Documented capabilities of related tools}\label{sec:tools}
Table~\ref{tab:tools-evidence} expands Table~\ref{M-tab:tools} of the main text with the evidence behind each mark.
Each mark records what a tool's public documentation states: its repository and manual, the cited paper, and package registries, inspected in September 2026 and re-checked against those sources in October 2026.
A mark is not a measurement on a shared input, and an open mark means that a capability was not documented, not that it is impossible.
Where a tool was superseded, the version that reads VCF was assessed.
The columns are defined as follows; a partial mark applies the qualification given after each definition.
\begin{description}\setlength{\itemsep}{1pt}
\item[RDF model] The output uses a documented vocabulary. Partial: terms shown only by example, or a vocabulary that is no longer published.
\item[Header + genotype] VCF header metadata is kept in the RDF together with per-sample genotype and FORMAT data. Partial: only one of the two, or both only through user-written templates.
\item[Editable mappings] Users can change how VCF maps to RDF without changing the converter. Partial: configuration or plug-in hooks over a fixed mapping, or mappings that produce only part of the output.
\item[CLI] Documented command-line use suitable for pipelines. Partial: library, browser, or user-interface use only.
\item[Reproducible workflow] A documented VCF-to-RDF route that a third party can rerun. Partial: manual installation of several components, an unpublished package, an offline service, or an unmaintained runtime.
\item[Compressed RDF] The tool writes compressed RDF itself. Partial: only through a bundled wrapper.
\item[Public release] A versioned package, executable, or container. Partial: source code only.
\end{description}

\section{Representation and implementation details}\label{sec:model}
\subsection{Model and sample profiles}\label{subsec:model-profiles}
VCF-RDFizer uses the VCF Core vocabulary (\texttt{vcfc:}, \url{https://w3id.org/vcf-core/vocab\#}) to retain file and header assertions, variant records, and sample/genotype information~\cite{vcfc210}.
The model aligns with FALDO, the Sequence Ontology, HERO, and features of GA4GH VRS~\cite{faldo_2016,seq_ont_2005,hero-genomics_2025,ga4gh2025VRS}.
Its classes, properties, domains, and ranges describe the representation; SHACL supplies value and cardinality constraints rather than OWL restrictions.
Figure~\ref{fig:vcf-core-full} shows the emitted backbone, and Table~\ref{tab:capabilities} distinguishes implemented capabilities from assessed coverage.
The documentation-based converter comparison is now Table~\ref{M-tab:tools} of the main text.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\textwidth]{vcf-core-classes.pdf}
\caption{\textbf{Simplified VCF Core model emitted by the evaluated converter.}
All terms use the \texttt{vcfc:} prefix.
A versioned file resource connects header declarations, records, and sample information; values retain links to their interpretation context.
Expanded output exposes sample calls, genotypes, and allele calls, while condensed output uses sample-ordered vectors.
Structural-variant, phasing, local-allele, and value-typing classes are omitted; the complete vocabulary is documented at \url{https://ecrum19.github.io/vcf-core-vocabulary/}.} \label{fig:vcf-core-full}
\end{figure}

In expanded output, sample calls and their FORMAT values are addressable resources; condensed output stores the corresponding values in sample-ordered vectors.
Both retain the same file, header, and record context.
For $V$ records, $S$ samples, and $F$ FORMAT keys in a uniform layout, expanded output adds $VS$ sample calls and $VSF$ FORMAT-value resources, while condensed output adds $V$ matrices and $VF$ vectors.
Excluding shared structure and assuming bounded ploidy and value arity, their sample-layer triple counts scale as
\begin{equation}
\begin{aligned}
T_{\mathrm{expanded}} &= \mathcal{O}(S+VSF),\\
T_{\mathrm{condensed}} &= \mathcal{O}(S+VF).
\end{aligned}
\label{eq:sample-profile-scaling}
\end{equation}
Condensed output still contains all $VSF$ values inside literals, so its bytes grow with sample count even when its repeated triple structure does not.
Deterministic IRIs identify observations by source file and record position; linking supplies cross-file identity separately.
GA4GH VRS computed identifiers could complement the evaluated SPDI route, but were not implemented in this study~\cite{ga4gh2025VRS}.

\subsection{Conversion and incremental representation construction}\label{subsec:model-construction}
The conversion first derives record, header-line, and file-metadata TSV logical sources, because the implemented RML path does not read VCF directly.
Turtle-encoded RML mappings executed by RMLStreamer produce the record backbone~\cite{rml_2024,rmlstreamer_2022}.
Direct emitters add sample structures and content requiring per-value handling, including typed INFO and FORMAT values, QUAL, and header attributes.
RML contributes nine triples per record, 5.3\% of the HG005 graph; the emitters supply the other 94.7\%.
For example, the implemented path delegates datatype selection to emitters so that a missing QUAL becomes \texttt{vcfc:Null} rather than a decimal.
These figures describe this hybrid implementation, not an inherent limitation of every RML-based architecture.

Each part is appended to plain N-Triples or as one member of a concatenated-gzip N-Triples stream, then deleted (main Figure~\ref{M-fig:implementation}).
Standard gzip readers expose the members as one stream.
Storage, RDF compression, representation construction, and artifact packaging are separate options: \texttt{-{}-rdf-storage-mode}, \texttt{-{}-rdf-compression}, \texttt{-{}-representations}, and \texttt{-{}-artifact-compression}.
HDT and COTTAS can therefore be retained independently of additional transport packages.

\paragraph{Chunking and merging.}
Representation builders read the aggregate incrementally, respecting complete N-Triples lines and keeping at most one uncompressed chunk at a time.
Each selected builder consumes that chunk before it is deleted.
HDT parts are produced by \texttt{rdf2hdt} and merged pairwise in a balanced tree with \texttt{hdtc create}, using the logical merge of HDTCat under a fixed memory budget~\cite{hdtcpp,hdt_2013,hdtc_2026,Diefenbach2020HDTCat}.
Unpaired parts continue to the next round, merge scratch space is removed after use, and only the final sibling \texttt{.hdt.index.v1-1} index is retained.
COTTAS parts are built with pycottas and merged in one streaming $k$-way pass, avoiding a global in-memory hash table or full-size temporary spill~\cite{pycottas_2026}.
Version 3.1.0 writes an \texttt{spo} index; v3.2.0 adds other index orders.
Each operation uses an isolated temporary directory to avoid reusing a DuckDB scratch database.
Parts, indexes, and builder scratch space still require disk, but a full decompressed duplicate of the aggregate is not created.

Default chunk sizes are a 512\,MiB target, 128\,MiB minimum, and 1\,GiB maximum, controlled by \texttt{-{}-chunk-target-bytes}, \texttt{-{}-chunk-min-bytes}, and \texttt{-{}-chunk-max-bytes}.
Six memory-feasibility cells instead used 128, 64, and 256\,MiB, respectively, to trade additional chunks for lower peak workspace.
Construction, merging, final indexing, validation, and packaging are timed separately.
Before raw RDF is removed, each artifact is decoded with its native reader and its triple count compared with the source; a mismatch fails the run.
This checks decoding and counts, not complete RDF-term equality.
The native COTTAS query path uses a DuckDB-backed Comunica engine over its Parquet tables~\cite{comunica_cottas_2026}.
QLever instead decodes an input artifact and builds its own index, so its query timings do not measure native compressed-format access.

Table~\ref{tab:queries} defines the fields and summaries compared.
Fourteen preflight queries first inspect blank nodes, empty values, missing tokens, POS typing, core-property cardinality, sample representation, sample/genotype inventories, and triple counts.

Answers must be exactly equal after normalization: strings for Q7, and integer counts for the other queries.
Contig and sample identifiers are retained, \texttt{PASS} remains distinct from \texttt{.}, and missing, extra, or differing rows are reported.
Q5--Q6 require sample data with \texttt{GT}; each source is compared only with its own graph, not with inputs on another assembly.
Q11--Q13 bind values to record IRIs and count them in 256 buckets using the first byte of SHA-256.
Changes that preserve the bucket histogram can escape detection, so these checks extend coverage without establishing value-by-value equality.

The same SPARQL runs under QLever, Comunica over N-Triples, Comunica over HDT, and the DuckDB-backed COTTAS engine~\cite{qlever_2017,Taelman2018Comunica,comunica_file_docs_2026,comunica_hdt_docs_2026,comunica_cottas_2026}.
Artifact decoding permits each engine to be assessed through different input formats; \texttt{-{}-validation-engine all} records four-engine agreement.
The default SHACL profile checks cardinality and datatypes, and two deeper profiles check uniqueness and value agreement.
A pass establishes the specified summaries or enabled constraints, not call accuracy, biological interpretation, or completeness of the entire graph.

\subsection{Completed comparisons and the consumer WGS validation run}\label{subsec:validation-comparisons}
The base campaign (Section~\ref{subsec:repro-builds}) attempted 78 validations, in its Difficult inputs (20), Covering set (23), Equivalence (16), Query cost (18), and Modes (1) families, and completed 76, yielding 984 equal applicable query comparisons and four not-applicable genotype comparisons on empty-input artifacts (Table~\ref{tab:validation-results}).
The paired checks reached 17.1M triples; the two malformed sites-only validations did not complete.
The default shapes ran in 58 validations up to 0.96M triples, with no violations and durations of 0.8--396.8\,s.
A repeated conversion produced 17,098,746 triples with identical SHA-256 and no duplicate lines; packaging round trips preserved the digest, and re-indexing left the artifact unchanged.
These are repeatability checks for the tested configuration, not every later build.

The separate retrieval run on the complete HG005 VCF (all 3,856,856 records) compared all thirteen answers at 657,425,805 triples without SHACL (Table~\ref{tab:retrieval-scale}).
It is not included in the 984-comparison denominator.

With v3.1.0, a first attempt exhausted host memory under the default shapes (Section~\ref{sec:issues}), and a rerun without shapes agreed on ten of the thirteen answers.
Q9 and Q10 differed because the oracle omitted 30,910 phase sets emitted from \texttt{PS}, and Q11 differed because 1,998 QUAL values with trailing zeros were returned in canonical decimal form by QLever.
Direct comparison found every record field equal to the source VCF text, and canonicalizing QUAL reproduced QLever's digest buckets exactly, so all three differences lay in the validator rather than the conversion.
The corrected validator, released in v3.3.1, counts phase sets, structural-variant events, confidence intervals, and gVCF reference blocks as the emitters write them, drops a decimal QUAL's trailing zeros on both sides of the Q11 digest, and validates shape profiles whose constraints are local to a record in batches of whole records.
Rerun on the same graph, all thirteen answers agreed, and the default shapes reported no violations in 117 batches of about 500,000 triples, taking 89\,min with four workers while available memory stayed above 19.9\,GB.
Their 46 warnings are VCF~4.5's recommended Source and Version attributes, absent from the file's INFO declarations.
Measured on this graph, a batch costs about 2.4\,GB and 300\,s per million triples (1.26\,GB and 155\,s for 0.51M triples; 4.72\,GB and 607\,s for 2.0M).

\subsection{Fault sensitivity and oracle limitations}\label{subsec:validation-sensitivity}
The fault set contains 113 targeted corruptions, including changed coordinates, alleles, filters, file metadata, phasing, and sample indices.
Query comparisons detected 96; adding default shapes did not detect any of the remaining 17.
Those 17 span ten classes: allele kind, allele value, header attribute values, derived contig count, FORMAT-item-to-allele links, field-to-header links, record index, sample index, called allele, and phasing status.
All three shape profiles together detected the full set, while both unmutated controls passed under both sample profiles.
The deeper profiles took 33.7 and 73.2\,s on approximately 2,000 triples, against 1.7\,s for the default profile.
Thus their detection result is limited to the constructed fault set and small graphs, not an estimated error-detection rate for arbitrary genomic RDF.

Version 3.1.0 applies the default shapes automatically up to a 512\,MiB size gate and permits all profiles when explicitly requested with \texttt{-{}-shacl-profile full}, up to 16\,MiB.
Different modes used different size measures; the resulting failures and corrections are recorded in Section~\ref{sec:issues}.
The completed default-profile mutation rerun confirms 96/113 detection, rather than leaving its sensitivity as an open experiment.
Release v3.3.1 applies the default shapes at any size, in record batches, while the deeper profiles, whose SPARQL-based constraints compare records with one another, are still validated whole: on request up to 16\,MiB of VCF and, by default, not above 10M triples.

The graph and parser routes read separate representations but share some assumptions.
Census expectations encode the selected representation, allele counts share a counting definition, and the linked workflow shares preprocessing and its case definition.
The missing-allele defect required correction of both the emitter and its census expectation, illustrating a shared error (Section~\ref{sec:issues}).
Direct text comparison and structural checks therefore complement the oracle rather than make it infallible.
The v3.3.1 oracle adds expectations for phase sets, structural-variant events, and gVCF blocks; local-allele constructs remain an explicit coverage limit.

\section{Linked genomic workflow: protocol, policies, and detailed results}\label{sec:usecase}
\subsection{Scope, linking, and policy evaluation}\label{subsec:usecase-linksets}
The linked workflow combines source observations with external evidence and requester-specific release rules, and so tests core prerequisites of the three motivating use cases rather than implementing any of them in full (\main{subsec:eval-workflow}).
For clinical variant interpretation and reanalysis, it tests joins between source observations and separately maintained clinical assertions and population frequencies at fixed releases; tracking interpretation changes over time and case-level reanalysis would require additional work.
For pharmacogenomic clinical decision support, it tests the cross-resource linking that would carry source observations into an interpretation and clinical-context layer; medication orders, pharmacogenomic allele calling, and prescribing recommendations would require additional work.
For consent-aware genomic data reuse, it evaluates proposed uses against simulated purposes, withdrawals, and selection rules; real consent adjudication and authenticated access would require additional work.
Figure~\ref{fig:linking} traces the implemented path from VCF files to a permitted answer.

Two plug-ins extend the VCF RDF graph without modifying the converted source representation (\main{subsec:extensions}).

\paragraph{Linking.}
\texttt{vcf-rdfizer-link} executes linkers declared in Turtle, each defining a join strategy, a reference resource, and the relationship it emits, and writes the links to a separate N-Triples linkset with a report of coverage and skipped records.
Tier~1 rewrites existing tokens, such as rsIDs, into IRIs without confirming them.
Tier~2 joins a digest- and assembly-pinned reference: \texttt{spdi} minimally trims explicit alleles and uses RefSeq accessions, while \texttt{ensembl-genes-grch38} links calls to Ensembl~116 genes overlapped by their REF span~\cite{holmes2020spdi}.
Contig aliases are harmonized, but minimal trimming does not establish canonical identity in every repeat context.
Tier~3 uses a Python resolver to confirm identifiers through a live service, with declared request rates and budgets, digest-recorded cached responses, and no published partial linkset on failure.
The \texttt{rsid-myvariant} linker uses MyVariant.info~\cite{xin2016myvariant}.
For RDF inputs, join fields are read through SPARQL from an endpoint or a temporary Oxigraph store.

\paragraph{Policy evaluation.}
\texttt{vcf-rdfizer-policy} evaluates ODRL rules over files or declared graph selections, including genomic regions, named variants, and gene-linked records~\cite{odrl_2018}.
Ownership rules in its VCF Core profile define which dependent resources are removed when a file or record is withheld: a withheld record's calls, alleles, and sample calls, and a withheld file's header.
The profile applies default-deny and deny-overrides semantics; permitted purposes are drawn from a subset of DUO by default and can use other RDFS or SKOS vocabularies~\cite{lawson2021duo}.
Version~0.2.0 evaluates against an endpoint and materializes each release view by streaming the selected N-Triples in their original order, without rewriting them.
Release validation requires each release view to match the policy digest, contain no prohibited or unpermitted owned resources, have no dangling references, and return the same records as an oracle derived from the source VCF text.
The dangling-reference check queries a second endpoint serving the view.
An extra record is an unintended release, and a missing permitted record is over-withholding.
Released genotypes retain their source IRIs and are not anonymized; obligations are recorded but not enforced.

Selector parameters are inserted as an inline \texttt{VALUES} block inside the outer query group.
A trailing \texttt{VALUES} clause is joined after that group, which left the tested region selector empty and its prohibition ineffective.
The placement correction is necessary for the evaluated rule behavior; it does not replace tests of each newly declared selector.

\subsection{Application question, comparison workflows, and evaluation arms}\label{subsec:usecase-case}
\paragraph{Application question.}
The application asks which observed variants in the fixed 81-gene ACMG SF v3.2 secondary-findings set have a corresponding ClinVar classification, which participant and gene are associated with each match, and which matches may be released to each requester~\cite{miller2023acmg}.
ClinVar variants are included when they have at least one review star, regardless of classification.
Pathogenic and likely pathogenic (P/LP) matches are reported separately; they are not treated as reportable secondary findings, because the workflow does not evaluate the additional gene-, inheritance-, and variant-specific criteria required for clinical reporting.

\paragraph{RDF and conventional comparison workflows.}
The RDF workflow links the converted VCFs to ClinVar and gene resources with the SPDI and Ensembl-gene linkers, materializes a release view for each requester against QLever, and queries each view and ClinVar with SPARQL~\cite{qlever_2017}.
The conventional workflow harmonizes contig names, annotates \texttt{CLNSIG}, \texttt{CLNREVSTAT}, and \texttt{GENEINFO} with bcftools, and evaluates the same case definition and release conditions in a separate Python implementation~\cite{BCFtools}.
The two workflows are compared using sorted tuples defined by participant, gene, contig, position, and alleles, which must agree exactly for every requester before timings are reported.
Counts therefore represent participant--variant--gene matches, not unique participants or independently adjudicated findings.
Both workflows share preprocessing and the case definition; the downstream linking, policy evaluation, and query implementations are separate.

\paragraph{Evaluation arms and simulated release policies.}
Each experimental arm is a distinct dataset and policy scenario.
Arm~1 contains the ACMG gene-span regions of five single-sample VCFs from three sources: two Personal Genome Project donations (NB72462M and NG131FQA1I), the HG004 and HG005 GIAB benchmark VCFs, and an HG002 precisionFDA submission with unprefixed contig names~\cite{personal_genome_proj,giab_v421_2022}.
Arm~2 contains 104 unrelated high-coverage 1000 Genomes participants, four from each of 26 populations~\cite{byrska2022highcoverage}.
Arms~1 and~2 use normalized, split records restricted to the ACMG gene spans (7.1\,Mb of Ensembl~116 spans), with bcftools left-alignment and multiallelic splitting.
For Arm~2, repeated panel-level INFO describing all 3,202 panel samples is removed from individual participant files, and the required population frequencies are represented once in a separate sites-only graph.
Arm~3 processes the complete HG005 VCF without the region restriction (3,887,810 records after normalization); its result must equal the HG005 result from the restricted Arm~1 input.
Arm~4 processes the complete NB72462M VCF (5,063,417 records after normalization), described below.
All arms use the ClinVar release from 2026-09-13, restricted to the same gene spans~\cite{clinvar_vcf}.

All consent and access conditions are simulated.
In Arms~1--3, requesters represent clinical care (CC), disease-specific cardiovascular research (DS), and general research use (GRU).
File-level permissions, participant withdrawals (four in the seeded cohort policies), and a restriction that limits records in 28 cancer-predisposition genes to clinical care determine the resulting release views.
Arm~3 releases every record for CC and none for DS or GRU.
Each participant is represented by a single-sample VCF, so no arm assesses selective masking of samples within a multi-sample VCF.

Four additional rule changes test where policy configuration or execution logic changes in each workflow: a withdrawal, a new requester purpose, replacement of the cancer-gene panel with a cardiac panel, and restriction of HFE C282Y.
After each change, both workflows must release identical records on a fixture containing cancer, cardiac, other, and HFE records.
Line counts exclude blanks, comments, and docstrings; they describe these implementations, not usability or maintainability.

\paragraph{Arm 4: fine-grained release from one complete VCF.}
In Arms~1--3, release views are determined mostly per file: a participant's consent releases or withholds the whole file, and only the cancer-gene restriction selects within it, so Arm~3's release views of the complete HG005 VCF were all or nothing.
Arm~4 asks the same application question of the complete NB72462M VCF, a consumer WGS file from Nebula Genomics, with policies that produce different non-empty release views from the same file.
The simulated consent permits clinical care and general research use, which includes disease-specific research, and the participant's physician is a fourth requester.
The policies combine purpose-specific gene-panel, genomic-region, and single-variant rules with the cancer-gene restriction, which still limits records in the 28 cancer-predisposition genes to clinical care through their gene links.
The gene-panel rule limits disease-specific research to records whose REF span overlaps one of 40 cardiovascular genes.
It prohibits the panel's complement, declared as a SPARQL selection that fails closed when gene links are absent; a permission on the panel alone would also withhold the file and header resources from which the query starts.
The genomic-region rule releases APOE (chr19:44,903,787--44,909,396, Ensembl~116) only for care by the participant's physician, a purpose declared in the case vocabulary as narrower than clinical care.
ODRL has no ``everyone except'' assignee, so restricting by purpose rather than by requester keeps the rule closed to any other clinical requester.
Because a region is defined by coordinates on a named contig, the rule depends on the contig name written in the file; a file naming the contig \texttt{19} would escape a \texttt{chr19} rule.
The single-variant rule withholds one variant of uncertain significance, DSP chr6:7,569,314 C>G, from the GRU requester by assignee; it targets the variant's SPDI identity and therefore holds however the file names chromosome~6.
The conventional workflow applies the same rules in Python to every record of the VCF, so Arm~4 compares the number of records in each release view as well as the matches.

\section{Reproducibility and execution}\label{sec:repro}
\subsection{The base campaign}\label{subsec:repro-campaign}
The \emph{base campaign} is the set of benchmark runs that produced the main text's fidelity and scalability results: 143 runs (\emph{cells}) in 12 experiment families, all executed with the published VCF-RDFizer v3.1.0 release on two identical hosts, \texttt{vcf-bench-1} and \texttt{vcf-bench-2} (Sections~\ref{subsec:repro-builds} and~\ref{subsec:repro-hosts}).
Each family is one script of the benchmark harness in the testing repository, numbered as below; scripts \texttt{00} and \texttt{02} only record the environment and derive the ladder inputs, and are not counted.
Every family ran as a whole on one host, never split across hosts, with no other benchmark running, and every cell wrote its command, commit, image, exit status, and timings to a fresh output directory.
The families, with their inputs and what each varies, are:
\begin{description}\setlength{\itemsep}{1pt}
\item[Records scaling (\texttt{04}).] Prefixes of HG005 with 10,000, 100,000, and one million records, three replicates each, and the complete VCF (3,856,856 records) once (10 cells); main Section~\ref{M-subsubsec:results-samples} and Figure~\ref{fig:scaling}.
\item[Sample representation (\texttt{03}).] 10,000 records of the 1000 Genomes chromosome-20 call set at 1, 4, 16, 64, 256, 1,024, and 2,504 samples under both sample profiles (14 cells), three timing replicates at 1 and 2,504 samples in each profile (12), and four anchor cells on a single-sample and a multi-sample fixture; main Section~\ref{M-subsubsec:results-samples}.
\item[Storage mode (\texttt{01}).] Plain against space-optimized storage on 100,000 HG005 records, three replicates each, and on a 269M-triple test file once each (8 cells); main Section~\ref{M-subsubsec:results-artifacts} and Figure~\ref{fig:scaling}f.
\item[Corpus breadth (\texttt{05}).] HDT and COTTAS construction on the first 250,000 records of eight public inputs and on the complete HG005 VCF (10 cells); main Section~\ref{M-subsubsec:results-artifacts} and Figure~\ref{fig:artifacts}.
\item[Representation axes (\texttt{07}).] Raw against structured INFO on 100,000 HG005 records and on HGSVC2, three replicates each; basic against structured header output; and fixtures declaring VCF 4.1 to 4.5 or no version (20 cells); Sections~\ref{sec:inputs} and~\ref{sec:config}.
\item[Difficult inputs (\texttt{09}).] Eleven awkward fixtures, one conversion with the three demonstration linkers, and a custom-mapping cell (16 cells); Section~\ref{sec:inputs} and Table~\ref{tab:difficult-inputs}.
\item[Covering set (\texttt{11}).] Ten configuration rows on a 1,000-line fixture that together cover every value and every pair of values of seven options, each validated with shapes (10 cells); Section~\ref{sec:config}.
\item[Modes (\texttt{12}).] Each operating mode run on its own on the 1,000-line fixture and its artifacts: TSV, conversion, validation, compression, decompression, and HDT and COTTAS indexing (7 cells); Section~\ref{sec:config}.
\item[Feasibility (\texttt{10}).] One million HG005 records under three configurations, each with requested memory ceilings of 8, 16, and 31\,GB (9 cells); Section~\ref{sec:config}.
\item[Robustness (\texttt{08}).] Two identical conversions of 100,000 HG005 records, a convert--compress--decompress round trip, an index build and rebuild, and the 113-fault mutation score with the default and with all shape profiles (9 cells); main Section~\ref{M-subsec:results-fidelity} and Section~\ref{sec:validation}.

\item[Query cost (\texttt{13}).] The thirteen source-comparison queries against cyvcf2 on the 10,000-line fixture (0.96M triples) and on 100,000 HG005 records (17.1M triples), three replicates each (6 cells); main Section~\ref{M-subsubsec:results-retrieval} and Section~\ref{subsec:measurements-setup}.

\section{Defects, corrections, and remaining gaps}\label{sec:issues}
This section retains diagnostic evidence that is not visible in the aggregate pass counts.
Corrected outputs are used where stated; unsuccessful runs and unresolved failures have not been relabeled as passes.

\paragraph{Declared samples in a header-only input.}
The emitter learned the file identity from the first record and omitted \texttt{vcfc:SampleSet} and \texttt{vcfc:VCFSample} when there were no records.
Q9 and Q10 detected the omission.
Deriving the sample set from the header increased the graph from 181 to 189 triples and allowed validation to complete.
The preflight oracle also incorrectly expected a \texttt{vcfc:sampleId}, which belongs to a per-record \texttt{vcfc:SampleCall}; it was corrected to expect no calls in an empty file.

\paragraph{Allele references without allele resources.}
Three covering-set rows combined raw INFO with expanded samples, whose genotypes referenced alleles emitted only by the structured-INFO path.
A 1,000-record test contained 1,972 dangling references and produced 5,916 shape violations, although query counts did not follow the references.
The emitter and census expectations were corrected to include alleles when either representation requires them.
All ten rows then passed; the three affected rows gained 10,846 triples each, and the other seven remained byte-identical.
Regression tests cover all four INFO/sample combinations and require every referenced allele to be described.

\paragraph{Metadata retained after a file was withheld.}
The policy plug-in initially removed the correct records but retained a withdrawn file's header in every view.
Its own check detected the problem.
The ownership rule now determines the dependent context removed with each withheld resource rather than treating record subtrees as the complete release boundary.

\paragraph{Memory guards and query heaps.}
The v3.1.0 shape gate used packaged bytes although \texttt{pyshacl}'s in-memory cost depends on the graph.
The same 170,935,101-triple graph was admitted as 390.7\,MB COTTAS and killed at 30.7\,GiB resident memory on a 31.3\,GiB host, but skipped as 756.6\,MB gzip-framed N-Triples or 1.18\,GB HDT.
In full mode, the gate instead used VCF bytes, admitting the 58.2M-triple NG131FQA1I graph from a 63.8\,MB input and exhausting memory; the diagnostic rerun excluded shapes.
The corrected gate counts triples rather than packaging-dependent bytes.
The Comunica-backed endpoints also exhausted the JavaScript heap while approximately 25\,GB host memory remained free; the heap ceiling is now configurable.
Both corrections are released in v3.3.0, do not change conversion output, and leave the failing runs in the evidence record.
Release v3.3.1 lowers the whole-graph limit from 50M to 10M triples, about 24\,GB at the measured 2.4\,GB per million triples, and validates record-local shapes in batches whose memory follows the batch rather than the graph; with it, the NG131FQA1I graph passed the default shapes (Section~\ref{subsec:validation-comparisons}).

\paragraph{COTTAS execution and timeout handling.}
The initial pycottas/RDFLib path completed preflight and Q1--Q4 on condensed output but stalled on Q5.
Two attempts ran for approximately 41 and 10\,h at about 190\% CPU before being stopped; a 1,800-second query limit and 14,400-second budget did not interrupt the second in-process query.
Both runs are archived.
The replacement DuckDB-backed Comunica path reduced Q5 to 2--5\,s and the thirteen-query workload on 0.96M triples to 38\,s, against 1,402\,s through RDFLib.
Completed comparisons use the replacement path, with query execution placed where a timeout can terminate it.

\paragraph{Shape severity and missing tokens.}
The SHACL report parser initially treated recommendations as blocking and expected a violation format that pyshacl did not emit.
It was corrected to classify severity and block only \texttt{sh:Violation}, rather than reject valid INFO declarations without \texttt{Source}.
The missing-token preflight also flagged legitimate dots: \texttt{Number=.} denotes variable cardinality, and \texttt{.} can encode a missing genotype.
Excluding \texttt{vcfc:fieldNumber} and \texttt{vcfc:genotypeString} reduced 20 rows to ten header-attribute values carrying the same Number declaration.
A further correction excludes that attribute while retaining checks on others, but postdates v3.1.0.
Its reports in the base campaign therefore retain 608 checks, 599 passes, and nine flags with ten rows each; those flags do not represent malformed RDF.

\paragraph{Incomplete sites-only coverage.}
The fixture declared FORMAT without sample columns, which bcftools rejects.
It produced 245 triples and an HDT artifact, but both paired validations ended with \texttt{EXECUTION\_FAILED}.
This is incomplete fixture/oracle coverage, not a failed semantic comparison or a passed sites-only validation.
A conformant fixture remains necessary.

\paragraph{Legacy measurement corrections.}
An earlier six-file benchmark under-reported partitioned compression times; commit \texttt{fb48e50} corrected timing, and affected historical durations were reconstructed from logs and timestamps.
Its input-size column labeled \texttt{.vcf.gz} also held uncompressed bytes: NG131FQA1I contained 1,215,509,730 bytes, matching 1215.5\,MB.
The legacy HDT reduction of 92--95\% used uncompressed N-Triples as its denominator, unlike the present 1.36--1.82 ratio against gzip-framed N-Triples.
Those legacy tables are excluded from the current analysis rather than presented as directly comparable compression results.

\paragraph{Oracle failures on a consumer WGS VCF.}
The v3.1.0 oracle did not count phase sets and compared QUAL as written, so the consumer WGS validation run first reported three mismatches on a graph whose record fields equal the VCF text (Section~\ref{subsec:validation-comparisons}).
Release v3.3.1 corrects both and adds census expectations, checked against the emitters by unit tests, for structural-variant events, confidence intervals, and gVCF reference blocks; rerun with it, the same graph passed all thirteen comparisons.
Local-allele constructs remain outside the oracle.
These are distinct from the fixed sample, allele-resource, and ownership defects above.

\section{Conversion, storage, and retrieval measurements}\label{sec:measurements}
\subsection{Record and sample scaling}\label{subsec:measurements-scaling}
On the HG005 record ladder, triple production had a fitted exponent of $+0.999$ (95\% CI $[+0.991,+1.007]$), at 170.9--171.9 triples per record (Figure~\ref{fig:scaling}a).
Artifact bytes, peak workspace, and end-to-end time had exponents of $+1.033$, $+1.025$, and $+1.063$, respectively.
At 10,000, 100,000, and one million records, end-to-end times were 40.7, 423.7, and 5,476.0\,s, with replicate standard deviation at most 13.5\,s.
Mapping-stage resident memory remained 1.0--1.7\,GB across this hundredfold input increase.
RMLStreamer itself took 12.2--41.4\,s; HDT construction dominated total time, rising from 38\% of it at 10,000 records to 82\% for the complete VCF (Figure~\ref{fig:scaling}e).
These observations describe mapping memory on this ladder, not bounded memory for every downstream component.

The sample ladder holds 10,000 records and INFO fixed while varying $S$ from 1 to 2,504 (main Figure~\ref{M-fig:samples}).
Its triple counts are exactly $1{,}359{,}498+250{,}005S$ expanded and $1{,}439{,}498+5S$ condensed, reflecting 25 repeated triples per sample per record and five declaration triples per sample in the expanded path.
The expanded fitted exponent of $+0.795$ reflects the fixed record layer at low sample counts.
At 2,504 samples, expanded output contains 627,372,018 triples, $432\times$ condensed output.
The byte ratios instead are $322\times$ for gzip-framed N-Triples and $69\times$ for HDT.
Condensed HDT grows from 10.2 to 59.2\,MB ($5.8\times$), despite only 0.9\% triple growth, because its vectors lengthen.
It becomes smaller than uncompressed VCF from 256 samples; at one sample the sizes are 10.2 versus 1.5\,MB, and at 2,504 they are 59.2 versus 101.6\,MB.
Expanded HDT reaches 4.10\,GB, approximately $40\times$ the VCF, with an end-to-end time of 15,269\,s against 250\,s condensed.
Extrapolating expanded workspace to the full 1,812,841-record call set gives roughly 2\,TB against the 189\,GB volume available to that estimate, so the run is refused; this is an estimate, not a completed full-cohort measurement.

\subsection{Storage mode and optional artifacts}\label{subsec:measurements-storage}
Plain and space-optimized storage produced identical triples and final artifact sizes within one 4\,kB filesystem block.
Space-optimized storage reduced peak workspace from 2.98 to 0.325\,GB ($9.19\times$) on 100,000 records and from 43.40 to 5.65\,GB ($7.68\times$) on the 1,155,741-record NG131FQA1I prefix \texttt{test-larger}.
The end-to-end time costs were 5.2\% and 3.2\%, respectively (Figure~\ref{fig:scaling}f).
On the replicated input, mapping time met a prespecified $\pm10\%$ equivalence margin: observed difference $+0.0\%$, with a 90\% bootstrap CI of $[-1.9\%,+0.4\%]$.

Across the corpus, COTTAS occupied 0.37--0.55 times gzip-framed N-Triples and 0.27--0.37 times HDT, while HDT occupied 1.36--1.82 times gzip-framed N-Triples (Figure~\ref{fig:artifacts}).
COTTAS took 1.5--3.0 times longer than HDT to build, and peak workspace ranged from 4.7 to 30.3 times the uncompressed VCF input.
The v3.1.0 run on the complete HG005 VCF produced 657.4M triples in 16.07\,h, including 20,911\,s for HDT and 31,230\,s for COTTAS, approximately 14.5\,h together.
Its 146.8-second RML stage excludes emitters and other conversion work.
The retained HDT (4.63\,GB), HDT index (4.74\,GB), and COTTAS (1.50\,GB) formed a measured 10,879,410,176-byte output tree, or 10.88\,GB; rounded components sum to 10.87\,GB.
This is $78\times$ the 139\,MB compressed download, but includes alternative representations and an index rather than a minimum RDF footprint.
Gzip-framed N-Triples alone occupied 2.89\,GB.

\subsection{Query workloads and physical access paths}\label{subsec:measurements-queries}
On 17.1M triples, QLever's thirteen-query totals from N-Triples, HDT, and COTTAS were 17.0--17.1\,s, differing by less than 1\%; individual queries differed by at most 0.07\,s (main Figure~\ref{M-fig:retrieval}c).
These are queries over QLever's index, not native artifact access.
On the separate 0.96M-triple fixture, mean totals were 1.1\,s for QLever, 23.4\,s for Comunica over N-Triples, 38.2\,s for the COTTAS engine, and 45.1\,s for the HDT-backed engine, with answer agreement in every run.

For individual questions on 17.1M triples, full cyvcf2 parses took 11.5\,s, or 12.3\,s for the three sample-level questions, against 0.005--4.62\,s after QLever indexing.
The resulting $2.5$--$2300\times$ query-time ratio excludes the 22.8-second index build and conversion.
The tested individual cold-start questions therefore favored the parser.
One parsing pass answering all thirteen questions took 12.4\,s, against 17.1\,s of indexed queries before setup.

The large-graph workload took 1.13, 1.00, 0.96, and 0.97\,s per million triples at 0.96M, 17.1M, 171M, and 657M triples, respectively (Table~\ref{tab:retrieval-scale}).
Index construction took 1.27--1.35\,s per million above the smallest graph.
On the complete HG005 VCF, the queries took 634.6\,s after an 868.0-second build, with replicates within 0.7\% and every answer equal to the parser's.
Query times from the three artifacts differed by only 0.3\%, while one-time decoding costs differed substantially.
Both native compressed Comunica paths stopped at Q6 on 171M triples despite a 24\,GB heap; their reported totals cover only five answers.
On those five, COTTAS was $16.7\times$ faster than HDT, compared with less than $1.2\times$ on the small fixture, so small-graph rankings do not establish large-graph behavior.

\subsection{Setup amortization}\label{subsec:measurements-setup}
For an equivalent repeated workload with a positive per-query saving,
\begin{equation}
N_{\mathrm{break-even}}=\frac{\text{additional RDF setup}}{\text{VCF time per question}-\text{indexed RDF time per question}}.
\end{equation}
A three-replicate rerun on \texttt{vcf-bench-2} measured this scenario directly with the base campaign's release, image, and 100,000-record input.
It converted the records only to the gzip-framed N-Triples that QLever indexes (95.1--96.6\,s, mean 95.7\,s), then repeated the query-cost validation on them: QLever indexing took 25.0\,s, a full cyvcf2 parse a median 12.28\,s per question, and a QLever query a mean 1.43\,s, with all thirteen answers equal in every replicate.
These give $(95.7+25.0)/(12.28-1.43)\simeq11$ questions.
The base campaign's conversions also built HDT, which querying through QLever does not need; with it, the setup was 446.5\,s and the break-even 44 questions.
The estimate also assumes a full parse of the VCF for every question at the measured question mix, not a single parsing pass computing all answers.
No universal break-even count follows, and update costs for changing external evidence or policies were not measured.
Main Figure~\ref{M-fig:regional}a shows the cumulative costs behind this estimate; repeating a single question breaks even after 10 (seven of the thirteen questions) to 17 (Q12, the INFO digest) repetitions (Figure~\ref{fig:retrieval-detail}c).
For storage, the gzip-framed N-Triples were 75.8\,MB against a 3.1\,MB gzipped VCF for these records, and 2.89\,GB against 139.3\,MB for the complete HG005 VCF (main Figure~\ref{M-fig:regional}b); the gzipped VCF sizes were measured on the benchmark hosts because the run records hold uncompressed input sizes.


\section{Configuration coverage, operating modes, and memory feasibility}\label{sec:config}
A ten-row covering set exercised every value of seven axes: sample representation, INFO representation, storage mode, RDF compression, output representations, artifact compression, and HDT strategy.
Every row completed validation, including shapes.
Pairwise coverage excludes only three prohibited combinations: \texttt{-{}-hdt-strategy single} with space-optimized storage, COTTAS, or \texttt{hdt,cottas}.
Gzip and Brotli were exercised in both compression roles, but their ratios and throughput were not compared.

The \texttt{tsv}, \texttt{compress}, \texttt{decompress}, HDT-index, COTTAS-index, conversion-only, and validation-only modes each ran independently with exit code 0.
A feasibility sweep crossed requested 8, 16, and 31\,GB memory ceilings with three configurations on one million records.
All nine cells completed at 1.34--1.93\,GB resident memory, but the harness could not confirm that Docker limits were forwarded to all container invocations.
The result therefore shows low measured memory for those runs, not survival under verified enforced limits.

Structured INFO increased the structural-variant graph from 89.01M to 96.75M triples (8.7\%), N-Triples bytes by 7.4\%, and HDT bytes by 7.8\%.
On 100,000 HG005 records, the increase was from 12.52M to 17.10M triples (36.6\%).
Raw INFO still retains alleles needed by expanded sample calls after the dependency correction in Section~\ref{sec:issues}.
Structured header output added only 0.03\%: 17,098,746 versus 17,094,293 triples.

The cross-encoding experiment used a 10,000-line, 9,986-record single-sample fixture in both sample profiles and storage modes, with N-Triples, HDT, and COTTAS artifacts.
All sixteen validations passed the fourteen preflight checks and Q1--Q13 under all four engines, on graphs of 0.96M triples expanded and 0.79M condensed.
The complete condensed cell took 70.4\,min.
Two additional negative tests correctly refused single-HDT strategy with COTTAS or space-optimized storage, returning exit status 2.
