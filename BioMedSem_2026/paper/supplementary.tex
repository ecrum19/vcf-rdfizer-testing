\section{Documented capabilities of related tools}\label{sec:tools}
Table~\ref{tab:tools-evidence} summarizes the documented capabilities discussed in the main text and gives the evidence behind each mark.
Each mark records what a tool's public documentation states: its repository and manual, the cited paper, and package registries, inspected in September 2026 and re-checked against those sources in October 2026.
A mark is not a measurement on a shared input, and an open mark means that a capability was not documented, not that it is impossible.
Where a tool was superseded, the version that reads VCF was assessed.
The columns are defined as follows; a partial mark applies the qualification given after each definition.
\begin{description}\setlength{\itemsep}{1pt}
\item[RDF model] The output uses a documented vocabulary. Partial: terms shown only by example, or a vocabulary that is no longer published.
\item[Header + genotype] VCF header metadata is kept in the RDF together with per-sample genotype and FORMAT data. Partial: only one of the two, or both only through user-written templates.
\item[Editable mappings] Users can change how VCF maps to RDF without changing the converter. Partial: configuration or plug-in hooks over a fixed mapping, or mappings that produce only part of the output.
\item[CLI] Documented command-line use suitable for pipelines. Partial: library, browser, or user-interface use only.
\item[Reproducible workflow] A documented VCF-to-RDF route that a third party can rerun. Partial: manual installation of several components, an unpublished package, an offline service, or an unmaintained runtime.
\item[Compressed RDF] The tool writes compressed RDF itself. Partial: only through a bundled wrapper.
\item[Public release] A versioned package, executable, or container. Partial: source code only.
\end{description}

\section{Shared-input converter comparison}\label{sec:converters}
Table~\ref{tab:tools-evidence} records what each converter documents.
This section reports what four of them write when they convert the same inputs as VCF-RDFizer, measured with the paper's existing measurements: the validator's content questions Q1--Q8 against the oracle, conversion wall time and peak resident memory, triples per record, and gzipped N-Triples size (main Figure~\ref{M-fig:converters}).
The run is experiment~18 of \texttt{vcf-rdfizer-testing} at commit \texttt{e3743590}, on \texttt{vcf-bench-1} on 8~October 2026, with three replicates of every conversion; its records are archived in \texttt{benchmark-results/vcf-bench-1/18\_converter\_comparison/}.
The whole experiment runs from one Docker Compose file, so the host needs only Docker: \texttt{CONV\_DATA=\ldots{} benchmarks/converters/run.sh}.

\subsection{Converters, builds, and options}\label{subsec:converters-tools}
Each converter ran in its upstream release image wherever upstream publishes one, and with the options that make its output most complete rather than with its defaults (Table~\ref{tab:converters-tools}).
Images built for the experiment start from a Debian base pinned by digest and take their packages from \texttt{snapshot.debian.org} at a fixed date; every downloaded artifact was checked against a pinned SHA-256, and the run records the resolved Compose file and every image ID.
Converter containers ran without network access, as the calling user.
A static BusyBox \texttt{time -v}, mounted read-only into each container, measured wall time and peak resident set size, the quantities VCF-RDFizer's own run summary reports for its stages; VCF-RDFizer's wall time spans all its stages, including starting a container for each.
Apache Jena \texttt{riot} 6.2.0 streamed each native output to N-Triples, which were counted, gzipped, and indexed with the QLever build in the VCF-RDFizer image.

\subsection{Questions and ports}\label{subsec:converters-ports}
Every graph was compared by the same script, inside the VCF-RDFizer image, with that image's validator: the same oracle over the source VCF, QLever build, result normalization, and comparator.
Only the SPARQL differs: each converter's Q1--Q8 are ported to its vocabulary, and VCF-RDFizer's are its validator's own queries.
A question a graph cannot answer has no port; its reason, with evidence from the converter's source, is recorded instead and reported as not represented, and the script refuses to run when a question has neither.
Q9--Q13 were excluded: Q9 and Q10 count VCF Core predicates and classes, and Q11--Q13 hash VCF-RDFizer's record IRIs.

Ports read only what a graph states.
Where a converter writes two VCF values the same way, the port reads that state as the value the converter's code derives it from, and the comparison shows whether the conflation costs anything on these inputs:
JVarkit writes no FILTER triple for either PASS or `.' (read as PASS), writes no ploidy (haploid calls read as homozygous), and types neither a no-call nor a record without GT;
TogoVar replaces CHROM with a reference IRI from its configuration, which the Q1 port maps back through the same configuration;
SPARQLing Genomics writes no record node, so its calls are regrouped through the record index in their IRIs, as its manual documents, and it writes only the first ALT allele;
and BioInterchange writes a missing allele as REF, writes `*' as an empty string, and strips the \texttt{VCFv} prefix from \texttt{\#\#fileformat}.
TogoVar and SPARQLing Genomics lose the order of multiple FILTER codes.

\subsection{Results}\label{subsec:converters-results}
Every conversion and comparison completed (52 recorded steps, all with exit status~0).
VCF-RDFizer answered Q1--Q8 as the oracle did on both inputs; the other graphs' differences come from what they hold:
\begin{itemize}
\item \textbf{JVarkit.} Its record IRI is \texttt{urn:variant/CHROM:POS:REF}, so the five pairs of 1000 Genomes lines that share CHROM, POS, and REF (for example \texttt{20:283049 C>CGAT} and \texttt{C>T}, both with ID `.') merge: 9,995 records instead of 10,000, five more multiallelic records, and every later count shifted. On the HG005 slice it answered Q1--Q6 as the oracle did.
\item \textbf{TogoVar.} It drops alleles outside \texttt{[ACGTURYKMSWBDHVN]}: the 13 symbolic records of the 1000 Genomes slice disappear, and \texttt{chr1:1663386 C>*,T} on the HG005 slice becomes an SNV (Q2, Q3). The same five pairs merge, because TogoVar writes no record node. It writes no samples or header lines, by design.
\item \textbf{SPARQLing Genomics.} A call is written only when it carries an alternate allele, so the 1000 Genomes graph holds the 1,401 of 10,000 records with a carrier, no homozygous-reference calls, and allele numbers over carriers only (Q6); multiallelic records are recognized only through an allele index of 2 or more, 19 of 70. On the HG005 slice, where every call carries an alternate allele, it answered Q1--Q7 as the oracle did; htslib adds a PASS FILTER definition the file does not declare (Q8).
\item \textbf{BioInterchange.} Its header document for the HG005 slice (line~2 of 100,003) is not valid JSON, because the tool writes strings without escaping them, so the header is absent from that graph (Q7, Q8). All 100,001 record documents parse, and on the 1000 Genomes slice it answered all eight questions as the oracle did.
\end{itemize}

\paragraph{Replicates.}
Each converter's three outputs were byte-identical, with two exceptions.
VCF-RDFizer's gzip framing differed between replicates, but its sorted triples were identical in all three replicates of both inputs; on the HG005 slice they equal those of the v3.1.0 conversion (Table~\ref{tab:builds}).
BioInterchange's replicates differed only in their \texttt{Context} and \texttt{Summary} documents, which record run paths and timestamps.

\paragraph{IRI warnings.}
\texttt{riot} parsed every output, warning about three converters' IRIs: VCF-RDFizer's record IRIs, \texttt{file://<name>.vcf\#record/n}, place the file name where a URL's host would be (an ``unwise'' IRI; 23.6 million warnings on the HG005 graph); SPARQLing Genomics' \texttt{origin://<md5>@<k>} uses deprecated user information (3.1 million); and JVarkit's \texttt{urn:variant/\ldots} has an invalid URN namespace (0.6 million).
None prevented parsing or indexing; TogoVar's and BioInterchange's outputs drew no warnings.
\section{Representation and implementation details}\label{sec:model}
\subsection{Model and sample profiles}\label{subsec:model-profiles}
VCF-RDFizer uses the VCF Core vocabulary (\texttt{vcfc:}, \url{https://w3id.org/vcf-core/vocab\#}) to represent file and header assertions, variant records, and sample/genotype information~\cite{vcfc210}.
The model aligns selected terms with FALDO, the Sequence Ontology, HERO, and GA4GH VRS~\cite{faldo_2016,seq_ont_2005,hero-genomics_2025,ga4gh2025VRS}.
SHACL supplies value and cardinality constraints rather than OWL restrictions.
Figure~\ref{fig:vcf-core-full} shows the emitted backbone, and Table~\ref{tab:capabilities} separates implemented support from completed assessment.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\textwidth]{vcf-core-classes.pdf}
\caption{\textbf{Simplified VCF Core model emitted by the evaluated converter.}
A versioned file connects header declarations, records, and sample information, while values retain links to their interpretation context.
Expanded output exposes sample calls, genotypes, and allele calls, whereas condensed output uses sample-ordered vectors.
The complete vocabulary is documented at \url{https://ecrum19.github.io/vcf-core-vocabulary/}.}
\label{fig:vcf-core-full}
\end{figure}

Expanded output represents each sample call and FORMAT value as an addressable resource.
Condensed output stores corresponding values in sample-ordered vectors.
Both profiles retain the same file, header, and record context.
For $V$ records, $S$ samples, and $F$ FORMAT keys in a uniform layout, the sample-layer structure scales as
\begin{equation}
\begin{aligned}
T_{\mathrm{expanded}} &= \mathcal{O}(S+VSF),\\
T_{\mathrm{condensed}} &= \mathcal{O}(S+VF).
\end{aligned}
\label{eq:sample-profile-scaling}
\end{equation}
Condensed output still stores all $VSF$ values inside literals, so bytes increase with sample count even when repeated triple structure does not.
Deterministic IRIs identify observations by source file and record position, while linksets add cross-file identity separately.
GA4GH VRS computed identifiers could complement the evaluated SPDI route but were not implemented~\cite{ga4gh2025VRS}.

\subsection{Conversion and incremental representation construction}\label{subsec:model-construction}
Conversion derives record, header-line, and file-metadata TSV sources because the implemented RML path does not read VCF directly.
RMLStreamer applies Turtle-encoded mappings to the record backbone, while direct emitters add samples and values requiring row-specific datatype or structure handling~\cite{rml_2024,rmlstreamer_2022}.
RML contributes nine triples per record, or 5.3\% of the HG005 graph, and emitters contribute the remaining 94.7\%.
The percentages describe the evaluated hybrid implementation rather than a general limitation of RML.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\textwidth]{vcf2rdf-v3.pdf}
\caption{\textbf{VCF-RDFizer v3.1.0 implementation.}
RML mappings and direct emitters produce the source graph, which is appended incrementally as plain or gzip-framed N-Triples.
Optional HDT and COTTAS builders consume one record-safe chunk at a time before merging and indexing.
Native decoding, source-comparison queries, and enabled SHACL profiles assess different properties.}
\label{fig:implementation}
\end{figure}

Each part is appended to plain N-Triples or one member of a concatenated-gzip stream and then deleted.
Standard gzip readers expose the members as one N-Triples sequence.
HDT and COTTAS construction, RDF compression, and transport packaging are independent options.
The representation builders consume one complete-line chunk at a time, so the process avoids a second full decompressed aggregate.
HDT parts are merged pairwise with \texttt{hdtc}, while COTTAS parts are merged in one streaming $k$-way pass~\cite{hdtcpp,hdt_2013,hdtc_2026,Diefenbach2020HDTCat,pycottas_2026}.
Default chunk targets are 512\,MiB, bounded between 128\,MiB and 1\,GiB; six feasibility runs used smaller chunks.
Before raw RDF is removed, each artifact is decoded with its native reader and its triple count compared with the source graph.
The check covers decoding and count preservation, not complete RDF-term equality.
QLever decodes an input artifact and builds its own index, so QLever timings do not measure native HDT or COTTAS querying.
The native COTTAS route uses a DuckDB-backed Comunica engine over Parquet~\cite{comunica_cottas_2026}.

\subsection{Fault sensitivity and oracle limits}\label{subsec:validation-sensitivity}
The fault set contains 113 targeted changes to coordinates, alleles, filters, metadata, phasing, sample indexes, and relationships.
Source-comparison queries detected 96 faults.
The default shapes detected none of the remaining 17, while all three profiles together detected every fault and accepted both unmutated controls.
The 17 additional detections span ten classes, including allele links, header attributes, record and sample indexes, called alleles, and phasing.
The deeper profiles took 33.7 and 73.2 seconds on approximately 2,000 triples, compared with 1.7 seconds for the default profile.
The result therefore describes the defined fault set on a small graph rather than an estimated detection rate for arbitrary data.

Version~3.3.1 applies record-local default shapes in batches at any graph size, while deeper cross-record profiles retain a whole-graph limit.
The parser and graph routes read different representations but share selected definitions and representation expectations.
An incorrect dependency can therefore affect both the converter and its oracle, as occurred for the missing-allele defect.
Text comparisons, source-derived summaries, structural constraints, and fault injection provide complementary evidence rather than an infallible oracle.
Local-allele semantics remain outside the completed oracle coverage.
\section{Linked genomic workflow: protocol, policies, and detailed results}\label{sec:usecase}
\subsection{Scope, linking, and policy evaluation}\label{subsec:usecase-linksets}
The linked workflow tests relationships shared by the three motivating applications rather than implementing complete clinical or governance systems.
For reanalysis, the workflow joins observations to fixed ClinVar and population-frequency releases.
For pharmacogenomics, the workflow tests cross-resource linking but not diplotype interpretation, medication orders, or prescribing guidance.
For consent-aware reuse, the workflow evaluates simulated purposes, withdrawals, and record selections but not real consent adjudication or authenticated access.
Figure~\ref{fig:linking} summarizes the implemented path.

\paragraph{Linking.}
\texttt{vcf-rdfizer-link} executes Turtle-declared linkers and writes a separate N-Triples linkset with coverage and skipped-record reports.
Tier~1 rewrites existing identifiers, Tier~2 joins digest- and assembly-pinned references, and Tier~3 confirms identifiers through a rate-limited live service with cached responses.
The evaluated SPDI linker minimally trims explicit alleles and harmonizes contigs to RefSeq accessions, while the gene linker records Ensembl~116 genes overlapped by the REF span~\cite{holmes2020spdi}.
Minimal trimming supports the tested joins but does not establish canonical identity in every repeat context.
The live MyVariant.info linker confirms rsIDs and fails without publishing a partial linkset when its service fails~\cite{xin2016myvariant}.

\paragraph{Policy evaluation.}
\texttt{vcf-rdfizer-policy} evaluates ODRL rules over files or declared graph selections~\cite{odrl_2018}.
The VCF Core policy profile applies default-deny and deny-overrides semantics and uses a subset of DUO purposes by default~\cite{lawson2021duo}.
Ownership rules remove dependent calls, alleles, sample calls, and headers with a withheld source resource.
Each release view is checked against the policy digest, permitted and prohibited membership, dangling references, and a record oracle derived from the VCF text.
Released genotypes retain source IRIs and are not anonymized, and obligations are recorded but not enforced.
Selector parameters are placed inside the outer SPARQL group; a prior trailing placement produced an empty region selection and was corrected before the reported experiments.

\subsection{Application question, comparison workflows, and evaluation arms}\label{subsec:usecase-case}
The application asks which observed variants in the fixed ACMG SF v3.2 81-gene set have a ClinVar classification, which participant and gene belong to each match, and which matches each requester may receive~\cite{miller2023acmg}.
ClinVar records require at least one review star.
Pathogenic and likely pathogenic matches are reported separately but are not treated as reportable secondary findings.

The RDF workflow links converted VCFs to ClinVar and gene resources, materializes each requester view, and queries the view with SPARQL against QLever~\cite{qlever_2017}.
The conventional workflow harmonizes contigs, annotates \texttt{CLNSIG}, \texttt{CLNREVSTAT}, and \texttt{GENEINFO} with bcftools, and applies the same case definition and release rules in Python~\cite{BCFtools}.
Sorted tuples of participant, gene, contig, position, and alleles should agree before timings are reported.
The routes share preprocessing and the case definition but use separate downstream implementations.

Arm~1 contains ACMG gene-span slices from five single-sample VCFs, Arm~2 contains 104 high-coverage 1000 Genomes participants, Arm~3 contains the complete HG005 VCF, and Arm~4 contains the complete NB72462M VCF~\cite{personal_genome_proj,giab_v421_2022,byrska2022highcoverage}.
Arms~1 and~2 use normalized and split records within 7.1\,Mb of Ensembl~116 gene spans.
Arm~2 removes repeated panel-level INFO and stores the required frequencies once in a sites-only graph.
All arms use the 2026-09-13 ClinVar release~\cite{clinvar_vcf}.
Simulated release rules combine file permissions, four seeded withdrawals in Arm~2, a 28-gene cancer restriction, and requester purposes for clinical care, cardiovascular research, and general research.
Arm~4 adds care by the participant's physician and combines a 40-gene cardiovascular panel, an APOE region, and one DSP variant so that every requester receives a non-empty subset of the same complete VCF.
No arm tests selective masking of samples within a multi-sample VCF.

Four applied changes test a withdrawal, a new purpose, replacement of the cancer panel, and an HFE C282Y restriction.
After each change, both workflows should release the same fixture records.
Line counts describe the two implementations and do not measure usability or maintainability.

\section{Reproducibility and execution}\label{sec:repro}
\subsection{The base campaign}\label{subsec:repro-campaign}
The \emph{base campaign} is the set of benchmark runs that produced the main text's fidelity and scalability results: 143 runs (\emph{cells}) in 12 experiment families, all executed with the published VCF-RDFizer v3.1.0 release on two identical hosts, \texttt{vcf-bench-1} and \texttt{vcf-bench-2} (Sections~\ref{subsec:repro-builds} and~\ref{subsec:repro-hosts}).
Each family is one script of the benchmark harness in the testing repository, numbered as below; scripts \texttt{00} and \texttt{02} only record the environment and derive the ladder inputs, and are not counted.
Every family ran as a whole on one host, never split across hosts, with no other benchmark running, and every cell wrote its command, commit, image, exit status, and timings to a fresh output directory.
The families, with their inputs and what each varies, are:
\begin{description}\setlength{\itemsep}{1pt}
\item[Records scaling (\texttt{04}).] Prefixes of HG005 with 10,000, 100,000, and one million records, three replicates each, and the complete VCF (3,856,856 records) once (10 cells); main Section~\ref{M-subsec:results-costs} and Figure~\ref{fig:scaling}.
\item[Sample representation (\texttt{03}).] 10,000 records of the 1000 Genomes chromosome-20 call set at 1, 4, 16, 64, 256, 1,024, and 2,504 samples under both sample profiles (14 cells), three timing replicates at 1 and 2,504 samples in each profile (12), and four anchor cells on a single-sample and a multi-sample fixture; main Section~\ref{M-subsec:results-costs}.
\item[Storage mode (\texttt{01}).] Plain against space-optimized storage on 100,000 HG005 records, three replicates each, and on a 269M-triple test file once each (8 cells); main Section~\ref{M-subsec:results-costs} and Figure~\ref{fig:scaling}f.
\item[Corpus breadth (\texttt{05}).] HDT and COTTAS construction on the first 250,000 records of eight public inputs and on the complete HG005 VCF (10 cells); main Section~\ref{M-subsec:results-costs} and Figure~\ref{fig:artifacts}.
\item[Representation axes (\texttt{07}).] Raw against structured INFO on 100,000 HG005 records and on HGSVC2, three replicates each; basic against structured header output; and fixtures declaring VCF 4.1 to 4.5 or no version (20 cells); Sections~\ref{sec:inputs} and~\ref{sec:config}.
\item[Difficult inputs (\texttt{09}).] Eleven awkward fixtures, one conversion with the three demonstration linkers, and a custom-mapping cell (16 cells); Section~\ref{sec:inputs} and Table~\ref{tab:difficult-inputs}.
\item[Covering set (\texttt{11}).] Ten configuration rows on a 1,000-line fixture that together cover every value and every pair of values of seven options, each validated with shapes (10 cells); Section~\ref{sec:config}.
\item[Modes (\texttt{12}).] Each operating mode run on its own on the 1,000-line fixture and its artifacts: TSV, conversion, validation, compression, decompression, and HDT and COTTAS indexing (7 cells); Section~\ref{sec:config}.
\item[Feasibility (\texttt{10}).] One million HG005 records under three configurations, each with requested memory ceilings of 8, 16, and 31\,GB (9 cells); Section~\ref{sec:config}.
\item[Robustness (\texttt{08}).] Two identical conversions of 100,000 HG005 records, a convert--compress--decompress round trip, an index build and rebuild, and the 113-fault mutation score with the default and with all shape profiles (9 cells); main Section~\ref{M-subsec:results-fidelity} and Section~\ref{sec:validation}.
\item[Equivalence (\texttt{06}).] The 10,000-line (9,986-record) fixture in both storage modes and both sample profiles, validated on four SPARQL engines over three RDF artifacts, two HDT strategies, and two required refusals (8 cells); Section~\ref{sec:config}.
\item[Query cost (\texttt{13}).] The thirteen source-comparison queries against cyvcf2 on the 10,000-line fixture (0.96M triples) and on 100,000 HG005 records (17.1M triples), three replicates each (6 cells); main Section~\ref{M-subsec:results-costs} and Section~\ref{subsec:measurements-setup}.
\end{description}
The 78 validation runs of the base campaign come from five of these families: Difficult inputs (20), Covering set (23), Equivalence (16), Query cost (18), and Modes (1).

The base campaign took 96.16\,h of measured wall time (Table~\ref{tab:campaign}).
Every asserted expectation held, but not every cell completed successfully.
The truncated-gzip and sites-only fixtures exited non-zero and are recorded as outcomes; the two HDT single-strategy cells with COTTAS or with space-optimized storage were required refusals; and three cells were skipped by a guard: a 2,504-sample input under the expanded profile in two families (the 1000 Genomes call set in Corpus breadth and the multi-sample anchor in Sample representation), because its sample columns exceed the volume's sample limit, and the custom-mapping cell, because no custom rules file was supplied.
The two mutation-score cells record the host-side test-harness commit rather than a conversion-container execution.

\subsection{Hosts, measurements, and execution status}\label{subsec:repro-hosts}
The base experiments used two separate hosts, \texttt{vcf-bench-1} and \texttt{vcf-bench-2}, each with an Intel Xeon Silver 4309Y at 2.80\,GHz (8 cores), 33.6\,GB RAM without swap, a 210\,GB SSD, Ubuntu 24.04.4 LTS, kernel 6.8.0-85-generic, Docker 29.7.2, and Python 3.12.3.
Each complete experiment ran on one host without concurrent benchmark jobs.
Calibration produced identical triple sets, byte-identical COTTAS artifacts and HDT indexes, and differences only in N-Triples/HDT ordering and the HDT \texttt{dcterms:issued} timestamp.
Conversion nevertheless took 26 versus 37\,s, and validation 156 versus 208\,s, so timings are compared within hosts.
Large-graph retrieval ran separately on \texttt{vcf-bench-3}, with the same CPU, 8 cores, 31.3\,GiB RAM without swap, Ubuntu 22.04.5, and kernel 5.15.
It queried the v3.1.0 graphs with the v3.3.1 runner.

Each cell records its command, host, commit, image, exit status, and wall time in a fresh output directory.
Stage reports record resident memory, triple counts, artifact sizes, validation outcomes, and transient workspace separately.
Performance denominators use uncompressed VCF bytes; Table~\ref{tab:corpus} instead reports compressed download sizes.
Replicated comparisons describe variability, whereas single-run corpus results do not estimate run-to-run variation.

Commands, normalized answers, and comparison reports are maintained in the testing repository; the complete evaluated snapshots still require a persistent archive.
Tagged releases are distributed through PyPI, Conda-Forge, and Docker Hub under the MIT License, with installation instructions, examples, release notes, and issue tracking~\cite{jimenez_2017_f1000}.
The unit-test suite covers Linux, macOS, and Windows; the reported benchmarks used Ubuntu.

\paragraph{Versions and corpus processing.}
Fixtures declaring VCFv4.1--4.5, plus one with no \texttt{\#\#fileformat}, all converted.
Their generated RML mappings differ only in the file class, from \texttt{vcfc:VCF41File} to \texttt{vcfc:VCF45File}.
Version-specific fields are handled through the data: the two-record VCFv4.5 fixture carries \texttt{LAA} and \texttt{LAD}, and the VCFv4.4 fixture carries \texttt{PS}, yielding 252.5 and 210 triples per record, respectively.
This demonstrates retention of those fields, not interpretation of every version-specific construct; local-to-global allele resolution is not implemented.
The undeclared-version input uses the documented fallback.

Nine corpus inputs were processed with headers retained: the first 250,000 records of eight files, and HG005 whole.
Their HDT and COTTAS outputs passed decoding/count checks.
The harness skipped the complete 2,504-sample 1000 Genomes input because its expanded-profile corpus guard excludes files with more than 1,000 sample columns.
Both sample profiles were instead tested on 10,000-record slices containing all 2,504 samples.
Separately, the tool refuses an expanded conversion when its estimated workspace exceeds three quarters of free space and suggests condensed output.
Neither guard is evidence that the complete cohort was converted.

Nine of eleven fixtures converted and completed paired validation (Table~\ref{tab:difficult-inputs}).
The truncated gzip was refused during decompression, while a malformed sites-only fixture produced RDF but did not complete validation.
The separate sites-only frequency graph in the linking experiment demonstrates a working frequency join, not completion of the missing paired-validation test.

\section{Conversion, storage, and retrieval measurements}\label{sec:measurements}
\subsection{Record and sample scaling}\label{subsec:measurements-scaling}
On the HG005 record ladder, triple production had a fitted exponent of $+0.999$ (95\% CI $[+0.991,+1.007]$), with 170.9--171.9 triples per record (Figure~\ref{fig:scaling}).
Artifact bytes, peak workspace, and end-to-end time had fitted exponents of $+1.033$, $+1.025$, and $+1.063$.
End-to-end times were 40.7, 423.7, and 5,476.0 seconds at 10,000, 100,000, and one million records, with replicate standard deviation at most 13.5 seconds.
Mapping-stage resident memory remained 1.0--1.7\,GB.
HDT construction increased from 38\% of total time at 10,000 records to 82\% for the complete VCF.

\subsection{Storage mode and optional artifacts}\label{subsec:measurements-storage}
Plain and space-optimized storage produced identical triples and final artifact sizes within one filesystem block.
Space-optimized mode reduced peak workspace from 2.98 to 0.325\,GB on 100,000 records and from 43.40 to 5.65\,GB on a 1,155,741-record prefix, with time increases of 5.2\% and 3.2\%.
Mapping time met a prespecified $\pm10\%$ equivalence margin on the replicated input.

Across the corpus, COTTAS occupied 0.37--0.55 times gzip-framed N-Triples and 0.27--0.37 times HDT, while taking 1.5--3.0 times longer than HDT to build (Figure~\ref{fig:artifacts}).
The v3.1.0 complete-HG005 run produced 657.4 million triples in 16.07 hours, including approximately 14.5 hours for HDT and COTTAS construction.
The retained HDT, HDT index, and COTTAS tree occupied 10.88\,GB, while gzip-framed N-Triples alone occupied 2.89\,GB.
The later v3.3.1 use-case conversion produced 662.4 million genomic triples in 53 minutes, or 55 minutes with ClinVar, before linking, release processing, and indexing.
The measurements differ in version, input, and work performed and are not estimates of a speed-up.

\subsection{Setup amortization}\label{subsec:measurements-setup}
For an equivalent repeated workload with a positive per-question saving,
\begin{equation}
N_{\mathrm{break-even}}=\frac{\text{additional RDF setup}}{\text{VCF time per question}-\text{indexed RDF time per question}}.
\end{equation}
A three-replicate rerun measured the minimal QLever path on 100,000 records.
Conversion to gzip-framed N-Triples required a mean 95.7 seconds, QLever indexing 25.0 seconds, a full cyvcf2 parse a median 12.28 seconds per question, and an indexed query a mean 1.43 seconds.
The resulting crossover is approximately eleven separately executed questions.
Including the unnecessary HDT build raises setup to 446.5 seconds and the corresponding estimate to 44 questions.
The calculation assumes a full VCF parse for each question at the measured query mix, rather than one batch pass.
Per-question crossovers range from 10 to 17 repetitions.
The gzip-framed N-Triples occupied 75.8\,MB versus a 3.1\,MB gzipped VCF for 100,000 records and 2.89\,GB versus 139.3\,MB for complete HG005.
No universal break-even count follows, and update costs for changing evidence or policies were not measured.
\section{Configuration coverage, operating modes, and memory feasibility}\label{sec:config}
A ten-row covering set exercised every value of seven axes: sample representation, INFO representation, storage mode, RDF compression, output representations, artifact compression, and HDT strategy.
Every row completed validation, including shapes.
Pairwise coverage excludes only three prohibited combinations: \texttt{-{}-hdt-strategy single} with space-optimized storage, COTTAS, or \texttt{hdt,cottas}.
Gzip and Brotli were exercised in both compression roles, but their ratios and throughput were not compared.

The \texttt{tsv}, \texttt{compress}, \texttt{decompress}, HDT-index, COTTAS-index, conversion-only, and validation-only modes each ran independently with exit code 0.
A feasibility sweep crossed requested 8, 16, and 31\,GB memory ceilings with three configurations on one million records.
All nine cells completed at 1.34--1.93\,GB resident memory, but the harness could not confirm that Docker limits were forwarded to all container invocations.
The result therefore shows low measured memory for those runs, not survival under verified enforced limits.

Structured INFO increased the structural-variant graph from 89.01M to 96.75M triples (8.7\%), N-Triples bytes by 7.4\%, and HDT bytes by 7.8\%.
On 100,000 HG005 records, the increase was from 12.52M to 17.10M triples (36.6\%).
Raw INFO still retains alleles needed by expanded sample calls after the dependency correction in Section~\ref{sec:issues}.
Structured header output added only 0.03\%: 17,098,746 versus 17,094,293 triples.

The cross-encoding experiment used a 10,000-line, 9,986-record single-sample fixture in both sample profiles and storage modes, with N-Triples, HDT, and COTTAS artifacts.
All sixteen validations passed the fourteen preflight checks and Q1--Q13 under all four engines, on graphs of 0.96M triples expanded and 0.79M condensed.
The complete condensed cell took 70.4\,min.
Two additional negative tests correctly refused single-HDT strategy with COTTAS or space-optimized storage, returning exit status 2.
