\section{Documented capabilities of related tools}\label{sec:tools}
Table~\ref{tab:tools-evidence} reports documented capabilities, not shared-input measurements.
The assessment used repositories, manuals, papers, and package registries inspected in September 2026 and rechecked in October 2026.
An open mark means that a capability was not documented, not that the capability is impossible.
For superseded tools, we assessed the version that reads VCF.
The column definitions and partial-mark criteria are listed below.
\begin{description}\setlength{\itemsep}{1pt}
\item[RDF model] The output uses a documented vocabulary.
A partial mark indicates terms shown only by example or a vocabulary that is no longer published.
\item[Header + genotype] The RDF retains header metadata together with per-sample genotype and FORMAT data.
A partial mark indicates only header or genotype coverage, or combined coverage available only through user-written templates.
\item[Editable mappings] Users can change the VCF-to-RDF mapping without modifying the converter.
A partial mark indicates configuration or plug-in hooks over a fixed mapping, or mappings that generate only part of the output.
\item[CLI] The tool documents command-line use suitable for pipelines.
A partial mark indicates only library, browser, or user-interface access.
\item[Reproducible workflow] The tool documents a VCF-to-RDF workflow that a third party can rerun.
A partial mark indicates manual installation of several components, an unpublished package, an offline service, or an unmaintained runtime.
\item[Compressed RDF] The tool writes compressed RDF directly.
A partial mark indicates compression available only through a bundled wrapper.
\item[Public release] A versioned package, executable, or container is available.
A partial mark indicates source code only.
\end{description}

\section{Representation and implementation details}\label{sec:model}

\subsection{Model and sample profiles}\label{subsec:model-profiles}
VCF-RDFizer uses the VCF Core vocabulary (\texttt{vcfc:}, \url{https://w3id.org/vcf-core/vocab\#}) to represent the source file, header declarations, variant records, and sample data~\cite{vcfc210}.
A record describes a genomic site using its contig and position, reference allele (REF), and alternate alleles (ALT).
INFO contains record-level annotations, while FORMAT fields describe sample-level values, including genotype (GT).
The model aligns selected terms with FALDO, the Sequence Ontology, HERO, and GA4GH VRS~\cite{faldo_2016,seq_ont_2005,hero-genomics_2025,ga4gh2025VRS}.
Value and cardinality constraints use the W3C Shapes Constraint Language (SHACL), which checks graph content against declared rules, rather than OWL restrictions~\cite{shacl2017}.
Figure~\ref{fig:vcf-core-full} shows the represented classes and relationships.
Table~\ref{tab:capabilities} distinguishes implemented capabilities from completed evaluation.
\begin{figure}[!htbp]
\centering
\includegraphics[width=\textwidth]{vcf-core-classes.pdf}
\caption{\textbf{Simplified VCF Core model emitted by the evaluated converter.}
A versioned file connects header declarations, records, and sample information.
Values retain links to the context needed for interpretation.
Expanded output exposes sample calls, genotypes, and allele calls, whereas condensed output uses sample-ordered vectors.
The complete vocabulary is documented at \url{https://ecrum19.github.io/vcf-core-vocabulary/}.}
\label{fig:vcf-core-full}
\end{figure}

VCF-RDFizer assigns each source record a deterministic Internationalized Resource Identifier (IRI) based on the source file and record position.
The same alteration reported in two files therefore remains two source observations.
A separate \emph{linkset}, an N-Triples file of links to external identifiers, can connect the observations to a shared variant identity.
\emph{Linkers} apply the rules that generate those links (Section~\ref{subsec:usecase-linksets}).
The evaluated variant links use SPDI, NCBI's Sequence:Position:Deletion:Insertion notation~\cite{holmes2020spdi}.
GA4GH VRS computed identifiers are a possible extension, not an implemented capability~\cite{ga4gh2025VRS}.

Two sample profiles balance direct query access against graph size.
The \emph{expanded} profile creates individual sample-call and FORMAT-value resources, allowing direct queries without decoding a vector.
The \emph{condensed} profile declares samples once and stores values in sample-ordered vectors.
Retrieving one sample's genotype therefore requires decoding the corresponding vector.
Both profiles retain the same VCF information and file, header, and record context.
Each converted file declares the selected profile through \texttt{vcfc:representationProfile}.

Expanded output suits single-sample and smaller multi-sample files.
In larger cohorts, repeating sample-level resources increases graph size and the associated memory, storage, and indexing work.
For $V$ records, $S$ samples, and $F$ FORMAT keys in a uniform layout, the sample-layer triple counts scale as
\begin{equation}
\begin{aligned}
T_{\mathrm{expanded}} &= \mathcal{O}(S+VSF),\\
T_{\mathrm{condensed}} &= \mathcal{O}(S+VF).
\end{aligned}
\label{eq:sample-profile-scaling}
\end{equation}
Equation~\ref{eq:sample-profile-scaling} describes repeated graph structure, not the number of retained sample values.
The VCF-RDFizer sample-representation guide gives worked examples, growth calculations, and profile-selection guidance (\url{https://github.com/ecrum19/VCF-RDFizer/blob/v3.3.1/docs/sample-representation-guide.md}).

\subsection{Conversion and incremental representation construction}\label{subsec:model-construction}
Main Figure~\ref{M-fig:implementation} summarizes the conversion pipeline.
VCF-RDFizer first creates tab-separated tables (TSV) for records, header lines, and file metadata because the implemented mapping path does not read VCF directly.
RDF Mapping Language (RML) rules describe how source fields become triples.
RMLStreamer executes the Turtle-encoded rules to produce the record backbone~\cite{rml_2024,rmlstreamer_2022}.
Direct emitters write sample structures and values requiring per-value datatype or structure handling.
RML produces nine triples per record, or 5.3\% of the HG005 graph, while emitters produce 94.7\%.
The split describes this hybrid implementation, not a general limitation of RML.

Each conversion stage writes an output part that is appended to plain N-Triples or compressed as one member of a concatenated-gzip stream.
The temporary part is then deleted.
Standard gzip readers read the members as one N-Triples sequence.
HDT and COTTAS construction, RDF compression, and transport packaging remain independent options.
The HDT and COTTAS builders process chunks of complete N-Triples lines, avoiding a full decompressed copy of gzip-framed output.
HDT parts are merged pairwise with \texttt{hdtc}.
COTTAS parts are merged in one streaming $k$-way pass~\cite{hdtcpp,hdt_2013,hdtc_2026,Diefenbach2020HDTCat,pycottas_2026}.
Chunks target 512\,MiB, with bounds of 128\,MiB and 1\,GiB.
Six feasibility runs used smaller chunks.

Before raw RDF is removed, native readers decode each artifact and compare the decoded triple count with the N-Triples source graph.
The check establishes readability and count preservation, not complete RDF-term equality.
QLever decodes an input artifact and builds a separate query index.
QLever timings therefore describe indexed graph access rather than native HDT or COTTAS queries.
The native COTTAS path uses a DuckDB-backed Comunica engine over Parquet~\cite{comunica_cottas_2026}.

\section{Reproducibility and execution}\label{sec:repro}

\subsection{The core benchmark}\label{subsec:repro-campaign}
The \emph{core benchmark} supplies RQ1 groups A and B, the main fault-injection runs in E, and the core scalability measurements.
The benchmark contains 143 configured runs, called \emph{cells}, across 12 experiment families.
Each family corresponds to one numbered harness script.
All core runs used the published VCF-RDFizer v3.1.0 release on \texttt{vcf-bench-1} or \texttt{vcf-bench-2}, which have identical hardware (Sections~\ref{subsec:repro-builds} and~\ref{subsec:repro-hosts}).
The harness and reported run records are archived on Zenodo as v1.0.0 (\url{https://doi.org/10.5281/zenodo.23301186}, with all versions at \url{https://doi.org/10.5281/zenodo.23301185}).
Scripts \texttt{00} and \texttt{02} record the environment and derive scaling inputs and are excluded from the 143 cells.
Each family ran on one host without concurrent benchmarks.
Each cell recorded its command, commit, image, exit status, and timings in a fresh output directory.
The families use public VCF subsets and small purpose-built test VCFs, termed fixtures in the scripts.
\begin{description}\setlength{\itemsep}{1pt}
\item[Records scaling (\texttt{04}).]
HG005 prefixes contain 10,000, 100,000, and one million records, each with three replicates.
The complete VCF (3,856,856 records) was processed once, giving 10 cells in total.
Results appear in main Section~\ref{M-subsec:results-costs} and Figure~\ref{fig:scaling}.
\item[Sample representation (\texttt{03}).]
Both sample profiles (Section~\ref{subsec:model-profiles}) process 10,000 records from the 1000 Genomes chromosome-20 call set at 1, 4, 16, 64, 256, 1,024, and 2,504 samples (14 cells).
Three timing replicates at 1 and 2,504 samples under both profiles add 12 cells.
Four additional cells apply both profiles to a complete 10,000-line single-sample test VCF and a complete 2,504-sample test VCF.
The expanded 2,504-sample cell was skipped, as described below.
Results appear in main Section~\ref{M-subsec:results-costs}.
\item[Storage mode (\texttt{01}).]
Plain mode writes uncompressed N-Triples.
Space-optimized mode appends compressed output parts and deletes each temporary part, avoiding a full uncompressed copy.
The two modes are compared on 100,000 HG005 records with three replicates per mode.
Each mode also processes a 1,155,741-record prefix of the \texttt{NG131FQA1I} consumer WGS VCF (269.3 million triples) once, giving 8 cells in total.
Results appear in main Section~\ref{M-subsec:results-costs} and Figure~\ref{fig:scaling}f.
\item[Corpus breadth (\texttt{05}).]
Nine cells build HDT and COTTAS from eight 250,000-record public VCF subsets and the complete HG005 VCF.
The tenth cell, the complete 1000 Genomes call set, was skipped by the sample-count guard.
Results appear in main Section~\ref{M-subsec:results-costs} and Figure~\ref{fig:artifacts}.
\item[Representation axes (\texttt{07}).]
Raw and structured INFO are compared on 100,000 HG005 records and HGSVC2 with three replicates per setting.
Other cells compare basic with structured header output and convert test VCFs that declare VCF 4.1 to 4.5 or no version.
The family contains 20 cells (Sections~\ref{sec:inputs} and~\ref{sec:config}).
\item[Difficult inputs (\texttt{09}).]
The family contains 11 difficult-input cells, four cells converting and linking a 100-record synthetic VCF, and one custom-mapping cell, totaling 16.
The synthetic VCF tests the example linkers distributed since v3.0.0: \texttt{rsid-dbsnp}, \texttt{gene-demo} with synthetic intervals, and the live \texttt{rsid-ensembl}.
The linkers produced 86, 0, and 0 links, respectively.

\subsection{Queries, normalization, and engines}\label{subsec:validation-queries}
VCF-RDFizer compares 13 SPARQL \emph{source-comparison queries} (\texttt{Q1}--\texttt{Q13}) with answers computed directly from the source VCF using cyvcf2 and, for exact FILTER text, \texttt{bcftools query}~\cite{vcf_intro,BCFtools,cyvcf2_2017}.
The source-derived answers form the \emph{oracle}.
Fourteen preflight integrity queries first check missing values, POS datatypes, core-property cardinalities, sample representation, graph inventories, and triple counts.
Table~\ref{tab:queries} defines the 13 content comparisons.
Each query summarizes a VCF component as counts, histograms, or hash-bucket digests rather than returning full record lists (main Table~\ref{M-tab:contract}).
The summaries keep results compact and allow the oracle to recompute expected answers without reading RDF.
Queries use standard SPARQL~1.1, including \texttt{SHA256}, and avoid order-dependent \texttt{GROUP\_CONCAT}.

One declarative test specification generates a purpose-built VCF, its expected graph, and a hand-derived reference summary.
The test records cover a transition and a transversion SNV, a deletion, multiallelic and no-ALT sites, PASS and failed FILTER values, and missing and non-diploid genotypes.
Continuous-integration tests compare the computed oracle with the hand-derived summary and run the queries in process with RDFLib.
Container tests run the same queries with Comunica, QLever, and the native HDT and COTTAS engines and check for identical answers.
Fault injection measures undetected errors separately (Section~\ref{subsec:validation-sensitivity}).
Main Figure~\ref{M-fig:query-oracle} illustrates \texttt{Q3} and its oracle.
The results site provides every full query and oracle.

Normalization parses counts as integers and sorts result rows by their keys.
The comparator retains contig and sample identifiers, distinguishes \texttt{PASS} from \texttt{.}, and reports missing, extra, or differing rows.
\texttt{Q5}--\texttt{Q6} apply to inputs with sample data and \texttt{GT}.
\texttt{Q11}--\texttt{Q13} hash each record, INFO value, or FORMAT value together with its own IRI using SHA-256.
The first hash byte assigns each item to one of 256 buckets.
The comparator checks the bucket counts from the graph against the counts derived from VCF.
Changed values usually move between buckets, but changes that preserve the histogram can remain undetected.

The same SPARQL text runs under QLever, Comunica over N-Triples, Comunica over HDT, and the DuckDB-backed COTTAS engine~\cite{qlever_2017,Taelman2018Comunica,comunica_file_docs_2026,comunica_hdt_docs_2026,comunica_cottas_2026}.
The default SHACL profile, \texttt{core}, checks cardinality and datatypes.
The deeper \texttt{consistency} profile compares related values, such as GT text and called alleles.
The \texttt{vocabulary-sparql} profile checks index uniqueness and record ordering.
All three profiles form the \texttt{full} set.
A passing result establishes only the specified summary or enabled constraint.

\subsection{B: Artifact decoding}\label{subsec:validation-decoding}
The core benchmark produced 118 HDT and 34 COTTAS artifacts with native decoding checks.
All 152 decoded triple counts matched the N-Triples source graph.
Equal counts establish readability and count preservation, not equality of every triple.
Groups A and D separately compare query answers for selected artifacts.
Core robustness tests also produced identical sorted triples in two conversions, with 17,098,746 triples, matching SHA-256 digests, and no duplicate lines.
Compression and decompression preserved the digest, and re-indexing left the artifact unchanged.

\subsection{C: Consumer WGS validation}\label{subsec:validation-consumer}
The consumer WGS validation used 250,000 records from \texttt{NG131FQA1I}, a single-sample VCF produced by Dante Labs and donated through the Personal Genome Project (Table~\ref{tab:corpus}).
The slice produced 58,231,176 triples.
VCF-RDFizer v3.3.1 matched all 13 oracle answers and reported no default-shape violations across 117 batches.
Default shapes assess a resource and its neighboring triples.
Each batch contains whole records and the referenced file-level triples, preserving the context required by those record-local checks.
The shapes reported 46 non-blocking recommendations for missing VCF~4.5 \texttt{Source} and \texttt{Version} attributes.
SHACL validation took 91 minutes with four workers, and available memory never fell below 19.5\,GB.
The result covers a consumer VCF slice, not the complete file.

\subsection{D: Large-graph query agreement}\label{subsec:validation-large}
Large-graph retrieval compared \texttt{Q1}--\texttt{Q13} with source-derived answers on one million HG005 records (170,935,101 triples) and the complete HG005 VCF (3,856,856 records and 657,425,805 triples).
All answers agreed in three QLever runs per graph from gzip-framed N-Triples.
The complete graph also passed three runs each from HDT and COTTAS.
The two graph sizes and four input paths produced 12 runs and 156 agreeing query executions.
Main Figure~\ref{M-fig:validation} reports the 13 distinct complete-HG005 queries rather than counting replicates as different questions.

Archived \texttt{parser.json} and \texttt{sparql.json} files contain normalized answers, and each \texttt{summary.json} records \texttt{answersAgree=true}.
The runs are labeled \texttt{TIMING\_ONLY} because preflight checks and SHACL were omitted, not because answer agreement was unchecked.
Group D is excluded from Group A's 1,006-comparison denominator.
At one million records, native HDT queries completed only \texttt{Q1}--\texttt{Q4}, while native COTTAS queries completed \texttt{Q1}--\texttt{Q5}.
Section~\ref{subsec:measurements-queries} reports execution limits and retrieval costs.

\subsection{E: Fault-injection sensitivity}\label{subsec:validation-sensitivity}
The fault-injection experiment applies 113 changes individually to correct expanded and condensed graphs generated from a test VCF.
Faults alter coordinates, alleles, filters, metadata, phasing, sample indexes, and relationships.
Source-comparison queries detected 96 faults.
Default SHACL shapes detected none of the remaining 17.
All three profiles together detected every fault and accepted both uncorrupted control graphs.

The 17 additional detections cover 10 fault classes.
Seven classes occur in both profiles: allele kind, allele value, per-allele INFO links, record index, contig count, header attributes, and field-declaration ownership.
Three occur only in expanded output: called-allele links, sample index, and phasing status.
For example, the phasing fault changes \texttt{vcfc:phasingStatus} from phased to unphased without changing GT text.
\texttt{Q5} maps \texttt{|} to \texttt{/} when classifying genotypes, and \texttt{Q13} hashes the unchanged text.
Neither query therefore detects the altered phasing relationship.

The deeper profiles took 33.7 and 73.2 seconds on approximately 2,000 triples, compared with 1.7 seconds for the default profile.
Detection rates describe the defined fault set, not arbitrary data.
Version~3.3.1 batches record-local default shapes at any graph size.
Cross-record profiles compare records across the graph, load the whole graph into memory, and retain a graph-size limit.

Source and graph comparisons use different representations but share selected definitions and expected structures.
A shared incorrect assumption can therefore affect the converter and oracle together.
VCF-text comparisons, query summaries, SHACL constraints, and fault injection provide complementary evidence rather than an infallible oracle.
Local-allele semantics remain outside the completed oracle coverage.

\section{Linked genomic workflow (RQ2)}\label{sec:usecase}

\subsection{Scope, linking, and policy evaluation}\label{subsec:usecase-linksets}
The linked workflow evaluates shared requirements of the three motivating applications.
For clinical reanalysis, the experiment joins observations to fixed ClinVar and population-frequency releases.
For pharmacogenomic decision support, the experiment tests cross-resource linking, not diplotype interpretation, medication orders, or prescribing guidance.
For consent-aware reuse, the experiment evaluates simulated purposes, withdrawals, and record selections, not consent adjudication or authenticated access.
Figure~\ref{fig:linking} summarizes the workflow.

\paragraph{Linking.}
\texttt{vcf-rdfizer-link} executes Turtle-declared rules and writes separate N-Triples linksets with coverage and skipped-record reports.
Tier~1 rewrites existing identifiers without confirmation, as \texttt{rsid-dbsnp} does for rsIDs.
Tier~2 computes links using reference data pinned by checksum and genome assembly, as the SPDI and Ensembl-gene linkers do.
Tier~3 confirms identifiers through rate-limited web-service requests and caches the responses.

The SPDI linker harmonizes contigs to RefSeq accessions and removes shared leading and trailing REF and ALT bases~\cite{holmes2020spdi}.
Eligible explicit alleles are written as bases rather than symbolic values such as \texttt{<DEL>}, breakends, or the spanning-deletion marker \texttt{*}.
Minimal trimming supports the tested joins but does not establish canonical identity throughout repeat regions.
The gene linker identifies Ensembl~116 genes overlapping each record's REF span.
The MyVariant.info linker confirms rsIDs~\cite{xin2016myvariant}.
Service failure stops the linker without publishing a partial linkset.

\paragraph{Policy evaluation.}
\texttt{vcf-rdfizer-policy} evaluates ODRL rules over files or declared graph selections~\cite{odrl_2018}.
The VCF Core profile withholds anything not explicitly permitted and gives prohibitions precedence over conflicting permissions.
The default purposes are general research use, health/medical/biomedical research, disease-specific research, and clinical care from DUO~\cite{lawson2021duo}.
Ownership rules identify dependent resources removed with a withheld source, including calls, alleles, sample calls, and headers.

For each requester, the plug-in materializes a \emph{release view}, a graph copy containing the triples selected for release.
Release validation compares the recorded policy digest with the applied policy.
The validator checks that every included resource has permission, no applicable prohibition selects an included resource, and no triple points to a withheld source resource.
Released records are then compared with records selected under the same policy from a minimal graph built directly from the VCF text.
The VCF-text route bypasses the converter but shares the gene links used by the policy evaluator.
Released genotypes retain source IRIs and are not anonymized.
The plug-in records additional ODRL obligations, such as deleting released data after use, without enforcing the obligations.
Selector parameters are placed inside the outer SPARQL group.
A previous trailing placement produced an empty region selection and was corrected before the reported experiments.

\subsection{Application question, comparison workflows, and evaluation scenarios}\label{subsec:usecase-case}
The fixed 81-gene ACMG Secondary Findings v3.2 list defines the workflow's clinically motivated scope~\cite{miller2023acmg}.
The query identifies participant--variant--gene matches between observed alleles and ClinVar classifications and determines which matches each requester may receive.
ClinVar records require at least one review star.
All classifications are included, with pathogenic and likely pathogenic matches reported separately.
The workflow does not apply the additional criteria for reportable clinical secondary findings.

The RDF workflow links converted VCFs to ClinVar and gene resources, materializes requester-specific views, and queries the views with SPARQL in QLever~\cite{qlever_2017}.
The conventional workflow harmonizes contigs, annotates \texttt{CLNSIG}, \texttt{CLNREVSTAT}, and \texttt{GENEINFO} with bcftools, and applies the same case definition and release rules in Python~\cite{BCFtools}.
The comparison requires exact agreement on sorted participant, gene, contig, position, and allele tuples.
The workflows share preprocessing and the case definition but use separate downstream implementations.

Four scenarios assess heterogeneous inputs, cohort integration, complete-VCF scale, and fine-grained release.
Scenario~1 uses ACMG gene-span slices from five single-sample VCFs: the PGP donations \texttt{NB72462M} and \texttt{NG131FQA1I}, the precisionFDA HG002 file, and GIAB benchmark files HG004 and HG005.
Scenario~2 uses 104 unrelated high-coverage 1000 Genomes participants.
Scenarios~3 and~4 use the complete HG005 and NB72462M VCFs, respectively~\cite{personal_genome_proj,giab_v421_2022,byrska2022highcoverage}.
Scenarios~1 and~2 retain normalized, split records within the 81 Ensembl~116 gene spans, totaling 7.1\,Mb.

Scenario~2 replaces repeated panel-level INFO with a separate sites-only frequency graph.
A sites-only VCF contains variant records without sample columns.
The frequency graph retains AF and five population-specific AF fields.
AC and AN are omitted because sample subsetting recalculated the counts for the cohort rather than the reference panel.
The rare-variant query joins participant observations, ClinVar, and frequencies through SPDI and retains panel $\mathrm{AF}<0.01$.
The conventional workflow applies the same threshold through a position-and-allele lookup.
All scenarios use the 2026-09-13 ClinVar release~\cite{clinvar_vcf}.

Simulated policies combine file permissions, four seeded withdrawals in Scenario~2, a 28-gene cancer restriction, and clinical-care, cardiovascular-research, and general-research purposes.
HG005's simulated consent permits only clinical care, leaving the Scenario~3 DS and GRU views empty.
Scenario~4 adds care by the participant's physician and combines a 40-gene cardiovascular panel, an APOE region, and one DSP variant.
Every Scenario~4 requester receives a distinct, non-empty view.
No scenario selectively masks samples within a multi-sample VCF.

Four applied rule changes test a withdrawal, a new purpose, replacement of the cancer panel, and an HFE C282Y restriction.
After each change, the comparison tests exact agreement on released records from a purpose-built test VCF.
Line counts describe the implementations, not usability or maintainability.

\subsection{Stage costs}\label{subsec:usecase-costs}
Conversion and linking run once per scenario.
View materialization, validation, indexing, and querying run per requester.
After shared preprocessing, the conventional workflow harmonized contigs, annotated with ClinVar, selected records, and applied all requesters' release rules in 4--91 seconds per scenario.
RDF conversion and linking alone took 5.7--105 minutes.
Queries over non-empty views took 171--233 seconds across views containing 6,397 to 5.06 million records.
The two empty Scenario~3 views returned in 0.07 seconds.
Similar non-empty query times suggest a dominant fixed ClinVar join, not generally scale-independent retrieval.

Scenario~2 view writing took 59--81 seconds per requester, compared with 20--27 minutes in pre-release builds.
Combining applicable rule selections, filtering input files in parallel, and caching each resource's ancestor IRIs reduced runtime without changing view bytes.
Ancestor IRIs determine whether a selection covers a resource.
Scenario~3 peaked at 11.2\,GB of host memory in use and 31\,GB of disk.
Scenario~4 required 88.7 minutes for conversion, 16.5 minutes for linking, and 55--70 minutes to write each view.

\section{Shared-input converter comparison (RQ3)}\label{sec:converters}
Table~\ref{tab:tools-evidence} describes documented capabilities.
The shared-input experiment measures four other converters against VCF-RDFizer on a 100,000-record HG005 slice and a 10,000-record, 16-sample 1000 Genomes chromosome-20 slice (main Figure~\ref{M-fig:converters}).
Measures include agreement with the source-derived oracle for \texttt{Q1}--\texttt{Q8}, conversion time, peak resident memory, triples per record, and gzipped N-Triples size.
The oracle derives expected answers directly from VCF using cyvcf2 and bcftools.
Table~\ref{tab:queries} and Section~\ref{subsec:validation-queries} define the questions.

Experiment~18 ran on \texttt{vcf-bench-1} on 8~October 2026 with harness commit \texttt{e3743590} and three replicates per conversion.
Run records are archived in \nolinkurl{benchmark-results/vcf-bench-1/18_converter_comparison/}.
The command \texttt{CONV\_DATA=\ldots{} benchmarks/converters/run.sh} runs the experiment through one Docker Compose file.
The host requires only Docker.

VCF-RDFizer reports the same stage metrics, with total time including container startup for each stage.
Apache Jena \texttt{riot} 6.2.0 streamed native outputs to N-Triples for counting and gzip compression.

\subsection{Shared validation protocol and query adaptation}\label{subsec:converters-ports}
The same script evaluated every graph inside the VCF-RDFizer image using a common validator, source-VCF oracle, QLever build, normalization procedure, and comparator.
Only the queries differed: \texttt{Q1}--\texttt{Q8} were adapted to each vocabulary, while VCF-RDFizer used the validator's supplied queries.
A question was \emph{not represented} when the graph lacked the required information.
Every unimplemented query has a reason supported by the converter's source code.
The script refuses to run without an adapted query or documented reason.
\texttt{Q9}--\texttt{Q13} were excluded because \texttt{Q9}--\texttt{Q10} count VCF Core predicates and classes, while \texttt{Q11}--\texttt{Q13} hash VCF-RDFizer record IRIs.

Adapted queries use only graph content.
When a converter merges distinct VCF states, the query follows the interpretation in the converter's code.
The comparison then exposes any resulting disagreement.
JVarkit emits no FILTER triple for PASS or \texttt{.}, so the query interprets absence as PASS.
JVarkit omits ploidy, leading the adapted query to read haploid calls as homozygous, and leaves no-calls and records without GT untyped.
TogoVar replaces CHROM with a configured reference IRI, which \texttt{Q1} maps back through the same configuration.
SPARQLing Genomics emits no record node, so the queries group calls by the record index encoded in call IRIs, following the manual.
The converter also writes only the first ALT allele.
BioInterchange writes missing alleles as REF, \texttt{*} as an empty string, and \texttt{fileformat} without the \texttt{VCFv} prefix from \texttt{\#\#fileformat}.
TogoVar and SPARQLing Genomics lose the order of multiple FILTER codes.

\subsection{Results}\label{subsec:converters-results}
Every conversion and comparison completed, giving 52 recorded steps with exit status~0.
VCF-RDFizer matched the oracle for \texttt{Q1}--\texttt{Q8} on both inputs.
The remaining differences reflect the content of each converter's graph.
\begin{itemize}
\item \textbf{JVarkit.}
Record IRIs use \texttt{urn:variant/CHROM:POS:REF}.
Five pairs of 1000 Genomes records share CHROM, POS, and REF and therefore merge.
For example, \texttt{20:283049 C>CGAT} and \texttt{C>T} both have ID `.'.
Merging produced 9,995 records rather than 10,000, added five multiallelic records, and shifted every subsequent count.
JVarkit matched the oracle for \texttt{Q1}--\texttt{Q6} on HG005.
\item \textbf{TogoVar.}
The converter drops alleles outside \texttt{[ACGTURYKMSWBDHVN]}.
The 13 symbolic records in the 1000 Genomes slice disappeared.
In HG005, \texttt{chr1:1663386 C>*,T} became an SNV, affecting \texttt{Q2} and \texttt{Q3}.
The same five record pairs merged because TogoVar emits no record node.
Sample data and header lines are omitted by design.
\item \textbf{SPARQLing Genomics.}
The converter emits only calls containing an alternate allele.
The 1000 Genomes graph therefore retained 1,401 of 10,000 records and omitted homozygous-reference calls, so the allele numbers that \texttt{Q6} recomputed counted carriers only.
Multiallelic records were recognized only when a call included an allele index of 2 or more, representing 19 of 70 such records.
Every HG005 call contains an alternate allele, and \texttt{Q1}--\texttt{Q7} matched the oracle on HG005.
For \texttt{Q8}, the graph listed 10 FILTER header lines rather than 9, because htslib, the library through which the converter reads the VCF, adds a PASS declaration (\texttt{\#\#FILTER=<ID=PASS>}) that the source header lacks.
\item \textbf{BioInterchange.}
The HG005 header document, line~2 of 100,003, was invalid JSON because the converter did not escape strings.
The resulting graph lacked the header information required for \texttt{Q7} and \texttt{Q8}.
All 100,000 record documents (lines 3--100,002) parsed, as did the context and summary documents (lines 1 and 100,003).
BioInterchange matched the oracle for all eight questions on the 1000 Genomes slice.
\end{itemize}

\subsection{Record and sample scaling}\label{subsec:measurements-scaling}
RDF output grew approximately linearly across the HG005 record-count series (Figure~\ref{fig:scaling}).
A least-squares power-law fit on log--log axes, triples $\propto \text{records}^{b}$, gave $b=+0.999$ (95\% CI $[+0.991,+1.007]$).
An exponent of 1 denotes linear growth.
Triple yield was 170.5--171.9 per record.
The corresponding exponents were $+1.033$ for artifact bytes, $+1.025$ for peak workspace, and $+1.063$ for end-to-end time.
Processing 10,000, 100,000, and one million records took 40.7, 423.7, and 5,476.0 seconds, with replicate standard deviation no greater than 13.5 seconds.
Mapping-stage resident memory remained 1.0--1.7\,GB.
The series built HDT but not COTTAS.
HDT construction increased from 38\% of runtime at 10,000 records to 82\% for the complete VCF.

\subsection{Setup amortization}\label{subsec:measurements-setup}
For an equivalent repeated workload with a positive per-question saving,
\begin{equation}
N_{\mathrm{break-even}}=\frac{\text{additional RDF setup}}{\text{VCF time per question}-\text{indexed RDF time per question}}.
\end{equation}
A three-replicate rerun measured minimal RDF setup on 100,000 records: gzip-framed N-Triples and a QLever index, without HDT or COTTAS.
Mean conversion time was 95.7 seconds and mean indexing time 25.0 seconds.
A full cyvcf2 parse took a median 12.28 seconds per question, compared with a mean 1.43 seconds per indexed query.
The cumulative times crossed after approximately 11 separately executed questions.

The core benchmark also built HDT, although QLever does not require HDT.
That setup took 446.5 seconds, comprising 423.7 seconds for conversion and 22.8 seconds for indexing.
With a median 11.57 seconds per VCF parse and a mean 1.32 seconds per indexed query, the corresponding crossover was 44 questions.
Both estimates assume the measured query mix and a separate full VCF parse per question, not one batched pass.
Individual-question crossovers ranged from 10 to 17 repetitions under minimal setup.

Gzip-framed N-Triples occupied 75.8\,MB for 100,000 records, compared with 3.1\,MB for gzipped VCF.
Complete-HG005 sizes were 2.89\,GB and 139.3\,MB, respectively.
The experiment establishes a workload-specific crossover, not a universal threshold.
Update costs for changing evidence or policies were not measured.

\section{Configuration coverage, operating modes, and memory feasibility}\label{sec:config}
\paragraph{Configuration coverage.}
A 10-row covering set tests every value of seven options and every allowed pair of option values.
The options are sample representation (expanded or condensed), INFO representation (raw or structured), storage mode (plain or space-optimized), N-Triples compression (gzip or Brotli), output representations (HDT, COTTAS, or both), artifact compression (gzip or Brotli), and HDT strategy (\texttt{partitioned}, \texttt{single}, or \texttt{auto}).
Artifact compression packages the HDT and COTTAS files.
The default \texttt{auto} strategy uses partitioned construction.
Every configuration completed validation, including shapes.

Three prohibited pairs are excluded: \texttt{-{}-hdt-strategy single} with space-optimized storage, COTTAS, or \texttt{hdt,cottas}.
Single-HDT construction requires an uncompressed N-Triples file, which space-optimized mode does not produce.
COTTAS requires chunks, so selecting COTTAS already invokes partitioned processing.
Gzip and Brotli were tested in both compression roles without comparing ratios or throughput.

\paragraph{Operating modes and memory.}
The \texttt{tsv}, \texttt{compress}, \texttt{decompress}, HDT-index, COTTAS-index, conversion-only, and validation-only modes each ran independently with exit code 0.
The memory-feasibility sweep combined requested limits of 8, 16, and 31\,GB with three configurations on one million HG005 records: defaults, smaller chunks, and smaller chunks with condensed samples.
All nine cells completed with 1.34--1.93\,GB resident memory.
The harness could not confirm that every container received the Docker limits.
The measurements therefore establish low observed memory use, not successful execution under verified limits.

\paragraph{INFO and header representation.}
Structured INFO increased the complete HGSVC2 graph from 89.01M to 96.75M triples (8.7\%).
N-Triples and HDT sizes increased by 7.4\% and 7.8\%, respectively.
For 100,000 HG005 records, the graph grew from 12.52M to 17.10M triples (36.6\%).
The raw-INFO count includes allele resources required by expanded sample calls after the dependency correction in Section~\ref{sec:issues}.
Structured headers added 0.03\%, giving 17,098,746 rather than 17,094,293 triples.

\paragraph{Cross-encoding agreement.}
The Equivalence experiment converted a 10,000-line, 9,986-record single-sample test VCF under both sample profiles and storage modes into N-Triples, HDT, and COTTAS.
All 16 validations passed the 14 preflight checks and \texttt{Q1}--\texttt{Q13} under all four engines.
Expanded graphs contained 0.96M triples and condensed graphs 0.79M.
The complete condensed cell took 70.4\,min.
Two additional negative tests correctly rejected single-HDT construction with COTTAS or space-optimized storage, returning exit status 2.
