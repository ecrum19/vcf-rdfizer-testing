\section{Documented capabilities of related tools}\label{sec:tools}
Table~\ref{tab:tools-evidence} summarizes the documented capabilities discussed in the main text and gives the evidence behind each mark.
The assessment used repositories, manuals, cited papers, and package registries inspected in September 2026 and rechecked in October 2026.
The marks describe documented capabilities, not measurements on shared inputs.
An open mark indicates that a capability was not documented, not that the capability is impossible.
For superseded tools, the assessment used the version that reads VCF.
The following definitions explain each column and the criteria for a partial mark.
\begin{description}\setlength{\itemsep}{1pt}
\item[RDF model] The output uses a documented vocabulary.
A partial mark indicates terms shown only by example or a vocabulary that is no longer published.
\item[Header + genotype] The RDF retains header metadata together with per-sample genotype and FORMAT data.
A partial mark indicates only header or genotype coverage, or combined coverage available only through user-written templates.
\item[Editable mappings] Users can change the VCF-to-RDF mapping without modifying the converter.
A partial mark indicates configuration or plug-in hooks over a fixed mapping, or mappings that generate only part of the output.
\item[CLI] The tool documents command-line use suitable for pipelines.
A partial mark indicates only library, browser, or user-interface access.
\item[Reproducible workflow] The tool documents a VCF-to-RDF workflow that a third party can rerun.
A partial mark indicates manual installation of several components, an unpublished package, an offline service, or an unmaintained runtime.
\item[Compressed RDF] The tool writes compressed RDF directly.
A partial mark indicates compression available only through a bundled wrapper.
\item[Public release] A versioned package, executable, or container is available.
A partial mark indicates source code only.
\end{description}

\grp{Dedicated VCF-to-RDF converters}
\textbf{VCF-RDFizer} (this study) & \capY & \capY & \capP & \capY & \capY & \capY & \capY \\*
\ev{VCF-RDFizer uses the public VCF Core vocabulary to retain headers, records, alleles, and expanded or condensed sample data.
Editable mappings cover only part of the output.
RML (the RDF Mapping Language, whose declarative rules map source fields to triples) generates the record backbone, the nine triples per record that create each record and its fixed-datatype fields, or 5.3\% of the HG005 graph.
Emitters, converter code that writes triples directly rather than through mappings, generate samples, INFO, QUAL, and headers and are configured through options (Section~\ref{subsec:model-construction}).
VCF-RDFizer uses a pinned Docker image and is released on PyPI, Docker Hub, and conda-forge.
It produces HDT, a compressed binary RDF format, and COTTAS (Columnar Triple Table Storage), which stores triples in compressed Parquet tables; both can be queried without decompression~\cite{hdt_2013,cottas_2025}.}

\section{Shared-input converter comparison}\label{sec:converters}
Table~\ref{tab:tools-evidence} records what each converter documents.
The shared-input experiment compares four converters with VCF-RDFizer on the same two inputs, a 100,000-record HG005 slice and a 10,000-record, 16-sample slice of the 1000 Genomes chromosome-20 call set, using the same assessment measures (main Figure~\ref{M-fig:converters}).
The measures are agreement with the oracle for \texttt{Q1}--\texttt{Q8}, conversion wall time, peak resident memory, triples per record, and gzipped N-Triples size.
The oracle is the set of expected answers computed directly from the source VCF with cyvcf2 and bcftools, and \texttt{Q1}--\texttt{Q8} are the content questions of Table~\ref{tab:queries} (Section~\ref{subsec:validation-queries}).
Experiment~18 ran on \texttt{vcf-bench-1} on 8~October 2026 using \texttt{vcf-rdfizer-testing} commit \texttt{e3743590}.
Each conversion had three replicates.
The run records are archived in \texttt{benchmark-results/vcf-bench-1/18\_converter\_comparison/}.
One Docker Compose file runs the complete experiment, so the host requires only Docker.
The command is \texttt{CONV\_DATA=\ldots{} benchmarks/converters/run.sh}.

\subsection{Converters, builds, and options}\label{subsec:converters-tools}
Each converter used an upstream release image when available and the options that produced the most complete output, rather than necessarily the defaults (Table~\ref{tab:converters-tools}).
Images built for the experiment used a digest-pinned Debian base and packages from \texttt{snapshot.debian.org} at a fixed date.
Every downloaded artifact was checked against a pinned SHA-256.
Run records retain the resolved Compose file and every image ID.
Converter containers ran without network access and as the calling user.
A static BusyBox \texttt{time -v}, mounted read-only in each container, measured wall time and peak resident set size.
VCF-RDFizer reports the same quantities for each stage.
VCF-RDFizer's wall time covers all stages, including container startup for each stage.
Apache Jena \texttt{riot} 6.2.0 streamed each native output to N-Triples.
The N-Triples were then counted, gzipped, and indexed with the VCF-RDFizer image's build of QLever, a SPARQL engine that answers queries from its own index of the graph~\cite{qlever_2017}.

\subsection{Shared validation protocol and query adaptation}\label{subsec:converters-ports}
The same comparison script evaluated every graph inside the VCF-RDFizer image.
Every comparison used the image's validator, source-VCF oracle, QLever build, normalization procedure, and comparator.
Only the SPARQL queries differed.
Queries \texttt{Q1}--\texttt{Q8} were adapted to each converter's vocabulary, while VCF-RDFizer used the queries supplied with the validator.
When a graph lacked the required information, the question had no adapted query and was reported as \emph{not represented}.
Each missing query has a recorded reason supported by the converter's source code.
The script refuses to run when a question has neither an adapted query nor a documented reason.
\texttt{Q9}--\texttt{Q13} were excluded because \texttt{Q9} and \texttt{Q10} count VCF Core predicates and classes, while \texttt{Q11}--\texttt{Q13} hash VCF-RDFizer's record IRIs.

Adapted queries read only information present in the graph.
When a converter represents different VCF values identically, the query interprets the shared representation according to the converter's source code.
The comparison then measures the effect of the conflation on the tested inputs.
JVarkit emits no FILTER triple for either PASS or `.', so the query reads an absent FILTER triple as PASS.
JVarkit omits ploidy, so haploid calls are read as homozygous.
JVarkit also leaves no-calls and records without GT untyped.
TogoVar replaces CHROM with a configured reference IRI, which the \texttt{Q1} query maps back using the same configuration.
SPARQLing Genomics emits no record node.
The queries therefore group calls by the record index encoded in call IRIs, as documented in the manual.
SPARQLing Genomics also writes only the first ALT allele.
BioInterchange writes a missing allele as REF, writes `*' as an empty string, and strips the \texttt{VCFv} prefix from \texttt{\#\#fileformat}.
TogoVar and SPARQLing Genomics lose the order of multiple FILTER codes.

\subsection{Results}\label{subsec:converters-results}
Every conversion and comparison completed, giving 52 recorded steps with exit status~0.
VCF-RDFizer matched the oracle for \texttt{Q1}--\texttt{Q8} on both inputs.
The remaining differences reflect the content of each converter's graph.
\begin{itemize}
\item \textbf{JVarkit.}
Record IRIs use \texttt{urn:variant/CHROM:POS:REF}.
Five pairs of 1000 Genomes records share CHROM, POS, and REF and therefore merge.
For example, \texttt{20:283049 C>CGAT} and \texttt{C>T} both have ID `.'.
Merging produced 9,995 records rather than 10,000, added five multiallelic records, and shifted every subsequent count.
JVarkit matched the oracle for \texttt{Q1}--\texttt{Q6} on HG005.
\item \textbf{TogoVar.}
The converter drops alleles outside \texttt{[ACGTURYKMSWBDHVN]}.
The 13 symbolic records in the 1000 Genomes slice disappeared.
In HG005, \texttt{chr1:1663386 C>*,T} became an SNV, affecting \texttt{Q2} and \texttt{Q3}.
The same five record pairs merged because TogoVar emits no record node.
Sample data and header lines are omitted by design.
\item \textbf{SPARQLing Genomics.}
The converter emits only calls containing an alternate allele.
The 1000 Genomes graph therefore retained 1,401 of 10,000 records and omitted homozygous-reference calls, so the allele numbers that \texttt{Q6} recomputed counted carriers only.
Multiallelic records were recognized only when a call included an allele index of 2 or more, representing 19 of 70 such records.
Every HG005 call contains an alternate allele, and \texttt{Q1}--\texttt{Q7} matched the oracle on HG005.
For \texttt{Q8}, the graph listed 10 FILTER header lines rather than 9, because htslib, the library through which the converter reads the VCF, adds a PASS declaration (\texttt{\#\#FILTER=<ID=PASS>}) that the source header lacks.
\item \textbf{BioInterchange.}
The HG005 header document, line~2 of 100,003, was invalid JSON because the converter did not escape strings.
The resulting graph lacked the header information required for \texttt{Q7} and \texttt{Q8}.
All 100,000 record documents (lines 3--100,002) parsed, as did the context and summary documents (lines 1 and 100,003).
BioInterchange matched the oracle for all eight questions on the 1000 Genomes slice.
\end{itemize}

\paragraph{Replicates.}
For each converter, the three outputs were byte-identical apart from two exceptions.
VCF-RDFizer's gzip framing differed, but sorted triples were identical across all three replicates of both inputs.
For HG005, the sorted triples also matched the v3.1.0 output (Table~\ref{tab:builds}).
BioInterchange outputs differed only in the \texttt{Context} and \texttt{Summary} documents, which record run paths and timestamps.

\paragraph{IRI warnings.}
The \texttt{riot} parser accepted every output but warned about IRIs from three converters.
VCF-RDFizer's \texttt{file://<name>.vcf\#record/n} IRIs place the file name in the URL host position.
The parser classified the IRIs as ``unwise'' and issued 23.6 million warnings for HG005.
SPARQLing Genomics' \texttt{origin://<md5>@<k>} IRIs use deprecated user information and produced 3.1 million warnings.
JVarkit's \texttt{urn:variant/\ldots} IRIs have an invalid URN namespace and produced 0.6 million warnings.
No warning prevented parsing or indexing.
TogoVar and BioInterchange outputs produced no warnings.
\section{Representation and implementation details}\label{sec:model}
\subsection{Model and sample profiles}\label{subsec:model-profiles}
VCF-RDFizer uses the VCF Core vocabulary (\texttt{vcfc:}, \url{https://w3id.org/vcf-core/vocab\#}) to represent file and header assertions, variant records, and sample/genotype information~\cite{vcfc210}.
The model aligns selected terms with FALDO, the Sequence Ontology, HERO, and GA4GH VRS~\cite{faldo_2016,seq_ont_2005,hero-genomics_2025,ga4gh2025VRS}.
Value and cardinality constraints are declared as SHACL shapes (the W3C Shapes Constraint Language, which checks a graph against declared rules~\cite{shacl2017}), not as OWL restrictions in the vocabulary.
Figure~\ref{fig:vcf-core-full} shows the emitted backbone, and Table~\ref{tab:capabilities} separates implemented support from completed assessment.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\textwidth]{vcf-core-classes.pdf}
\caption{\textbf{Simplified VCF Core model emitted by the evaluated converter.}
A versioned file connects header declarations, records, and sample information.
Values retain links to the context needed for interpretation.
Expanded output exposes sample calls, genotypes, and allele calls, whereas condensed output uses sample-ordered vectors.
The complete vocabulary is documented at \url{https://ecrum19.github.io/vcf-core-vocabulary/}.}
\label{fig:vcf-core-full}
\end{figure}

VCF stores sample-level FORMAT values in a table, with each record containing values for every sample and FORMAT field.
The expanded profile represents individual sample calls and FORMAT values as directly addressable RDF resources.
This allows consumers to query individual values without decoding a vector, making the expanded profile suitable for single-sample and smaller multi-sample files.
For larger cohorts, however, the repeated structure increases graph size, memory use, storage requirements, and indexing costs with $VSF$ (Equation~\ref{eq:sample-profile-scaling}).
For $V$ records, $S$ samples, and $F$ FORMAT keys in a uniform layout, the sample-layer structure scales as
\begin{equation}
\begin{aligned}
T_{\mathrm{expanded}} &= \mathcal{O}(S+VSF),\\
T_{\mathrm{condensed}} &= \mathcal{O}(S+VF).
\end{aligned}
\label{eq:sample-profile-scaling}
\end{equation}
The condensed profile reduces this overhead by declaring samples once and storing FORMAT values in sample-ordered vectors.
The trade-off is that individual values require decoding rather than direct graph access.
Both profiles preserve the same VCF information but offer different balances between direct access and compactness.
Each converted file identifies its profile through \texttt{vcfc:representationProfile}.
The VCF-RDFizer sample-representation guide provides detailed examples, scaling calculations, and guidance for choosing a profile (\url{https://github.com/ecrum19/VCF-RDFizer/blob/v3.3.1/docs/sample-representation-guide.md}).

Deterministic observation IRIs incorporate the source file and record position.
Separate linksets add cross-file variant identity.
A linkset is an N-Triples file, kept apart from the converted graph, that holds the links written by \emph{linkers}, declared rules that connect VCF records or their alleles to external identifiers (Section~\ref{subsec:usecase-linksets}).
GA4GH VRS computed identifiers could complement the evaluated SPDI route (NCBI's Sequence:Position:Deletion:Insertion variant notation~\cite{holmes2020spdi}) but were not implemented~\cite{ga4gh2025VRS}.

\subsection{Conversion and incremental representation construction}\label{subsec:model-construction}
Main Figure~\ref{M-fig:implementation} summarizes the conversion pipeline.
Conversion derives record, header-line, and file-metadata TSV sources because the implemented RML path does not read VCF directly.
RMLStreamer applies Turtle-encoded mappings to the record backbone, while direct emitters add samples and values requiring row-specific datatype or structure handling~\cite{rml_2024,rmlstreamer_2022}.
RML contributes nine triples per record, or 5.3\% of the HG005 graph, and emitters contribute the remaining 94.7\%.
The percentages describe the evaluated hybrid implementation rather than a general limitation of RML.

Each output part, the triples written by one conversion stage, is appended either to a plain N-Triples file or, as a separate gzip member, to a concatenated-gzip stream.
The part is deleted after appending.
Standard gzip readers expose the members as one N-Triples sequence.
HDT and COTTAS construction, RDF compression, and transport packaging are independent options.
The HDT and COTTAS builders read the graph one chunk of complete N-Triples lines at a time, so gzip-framed output is never expanded into a full uncompressed copy.
HDT parts are merged pairwise with \texttt{hdtc}, while COTTAS parts are merged in one streaming $k$-way pass~\cite{hdtcpp,hdt_2013,hdtc_2026,Diefenbach2020HDTCat,pycottas_2026}.
Default chunks target 512\,MiB, with bounds of 128\,MiB and 1\,GiB.
Six feasibility runs used smaller chunks.
Before raw RDF is removed, each artifact is decoded with the corresponding native reader.
The decoded triple count is compared with the source graph.
The check covers decoding and count preservation, not complete RDF-term equality.
QLever decodes an input artifact and builds its own index, so QLever timings do not measure native HDT or COTTAS querying.
The native COTTAS route uses a DuckDB-backed Comunica engine over Parquet~\cite{comunica_cottas_2026}.

\subsection{Queries, normalization, and engines}\label{subsec:validation-queries}
Validation compares 13 SPARQL results with answers derived from the source VCF using cyvcf2 and exact FILTER text from \texttt{bcftools query}~\cite{vcf_intro,BCFtools,cyvcf2_2017}.
Fourteen preflight queries first inspect syntax-independent graph properties, including missing values, POS typing, core-property cardinality, sample representation, inventories, and triple counts.
Table~\ref{tab:queries} defines the source-comparison questions.
Each query summarizes one part of the VCF (main Table~\ref{M-tab:contract}) as counts, histograms, or hash-bucket digests rather than as full record lists, so its result stays small on graphs of any size and its expected answer can be recomputed from the VCF text without reading RDF.
The queries use only standard SPARQL~1.1, including \texttt{SHA256} for the digests and no order-dependent \texttt{GROUP\_CONCAT}, so the same query text runs on every engine.
Queries and oracle were developed against one declarative test fixture from which the test VCF, its expected graph, and its expected oracle summary are all derived.
Its records exercise every query branch: a transition and a transversion SNV, a deletion, a multiallelic and a no-ALT site, PASS and failed FILTER values, and missing and non-diploid genotypes.
A continuous-integration test checks that the oracle computed from that VCF equals the hand-derived summary, and the queries also run in process under rdflib, an independent SPARQL implementation.
A container test then runs every query on Comunica, QLever, and the native HDT and COTTAS engines and requires identical answers, and fault injection (Section~\ref{subsec:validation-sensitivity}) measures which corruptions the queries miss.
Main Figure~\ref{M-fig:query-oracle} shows \texttt{Q3} next to its oracle, and the results site shows every query and its oracle.

Normalization parses count fields as integers and sorts rows by their key fields before comparison.
Normalized results retain contig and sample identifiers, distinguish \texttt{PASS} from \texttt{.}, and report missing, extra, or differing rows.
\texttt{Q5}--\texttt{Q6} apply only to inputs with sample data and \texttt{GT}.
\texttt{Q11}--\texttt{Q13} hash each record, INFO value, or FORMAT value together with its own IRI using SHA-256, place it in one of 256 buckets according to the first byte of the hash, and compare the per-bucket counts from the graph and the VCF.
The digest summaries extend value coverage: a changed value usually moves its item to another bucket, but changes that preserve the bucket histogram, such as two that offset each other, can go unnoticed.

The same SPARQL text runs under QLever, Comunica over N-Triples, Comunica over HDT, and the DuckDB-backed COTTAS engine~\cite{qlever_2017,Taelman2018Comunica,comunica_file_docs_2026,comunica_hdt_docs_2026,comunica_cottas_2026}.
The default SHACL profile (\texttt{core}) checks cardinality and datatypes, while two deeper profiles check that related values agree (\texttt{consistency}, for example GT text and called alleles) and that indices are unique and records ordered (\texttt{vocabulary-sparql}); all three together form the \texttt{full} set.
A passing query or shape result establishes only the specified summary or enabled constraint.

\subsection{C: Consumer WGS validation}\label{subsec:validation-consumer}
The first 250,000 records of \texttt{NG131FQA1I}, a single-sample consumer whole-genome sequencing VCF from Dante Labs donated through the Personal Genome Project (Table~\ref{tab:corpus}), produced 58,231,176 triples.
The published v3.3.1 image matched all 13 expected query results and reported no default-shape violations across 117 batches.
These shapes are record-local: each constraint judges one resource from its neighboring triples, and each batch holds whole records plus the file-level triples they reference, so batching does not change the verdict.
The shapes issued 46 non-blocking recommendations for missing VCF~4.5 \texttt{Source} and \texttt{Version} attributes.

\subsection{E: Fault-injection sensitivity}\label{subsec:validation-sensitivity}
The fault set applies 113 targeted changes, one at a time, to small, correct expanded and condensed graphs of a fixture VCF; the changes alter coordinates, alleles, filters, metadata, phasing, sample indexes, and relationships.
Source-comparison queries detected 96 faults.
The default shapes detected none of the remaining 17 faults.
All three profiles together detected every fault and accepted both controls, the uncorrupted graph in expanded and in condensed form.
The 17 additional detections span 10 fault classes: seven injected in both sample profiles (allele kind, allele value, per-allele INFO item links, record index, contig count, header attribute values, and field-declaration ownership) and three injected only in the expanded profile (called-allele links, sample index, and phasing status).
The phasing fault changed one genotype's \texttt{vcfc:phasingStatus} from phased to unphased while leaving its GT text unchanged, so neither \texttt{Q5}, which classifies the GT text after mapping \texttt{|} to \texttt{/}, nor the \texttt{Q13} digest of that text could detect it.
The deeper profiles took 33.7 and 73.2 seconds on approximately 2,000 triples, compared with 1.7 seconds for the default profile.
The detection rate applies to the defined fault set on a small graph, not to arbitrary data.

Version~3.3.1 applies record-local default shapes in batches at any graph size.
The deeper profiles are cross-record: they compare records with each other, so the whole graph must be loaded into memory, and a graph-size limit still applies.
The parser and graph routes read different representations but share selected definitions and representation expectations.
An incorrect shared expectation can therefore affect both the converter and its oracle.
Text comparisons, source-derived summaries, structural constraints, and fault injection provide complementary evidence rather than an infallible oracle.
Local-allele semantics remain outside the completed oracle coverage.
\section{Linked genomic workflow: protocol, policies, and detailed results}\label{sec:usecase}
\subsection{Scope, linking, and policy evaluation}\label{subsec:usecase-linksets}
The linked workflow tests relationships shared by the three motivating applications rather than implementing complete clinical or governance systems.
For reanalysis, the workflow joins observations to fixed ClinVar and population-frequency releases.
For pharmacogenomics, the workflow tests cross-resource linking but not diplotype interpretation, medication orders, or prescribing guidance.
For consent-aware reuse, the workflow evaluates simulated purposes, withdrawals, and record selections but not real consent adjudication or authenticated access.
Figure~\ref{fig:linking} summarizes the implemented path.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\textwidth]{fig-linking-framework.pdf}
\caption{\textbf{The implemented path from VCF files to a permitted answer.}
The diagram follows the use-case runner, policy generator, linker definitions, and SPARQL files.

\paragraph{Linking.}
\texttt{vcf-rdfizer-link} executes Turtle-declared linkers and writes a separate N-Triples linkset with coverage and skipped-record reports.
Linkers belong to three tiers.
Tier~1 rewrites identifiers already in the VCF without checking them, as the \texttt{rsid-dbsnp} linker does when it turns rsIDs into dbSNP IRIs.
Tier~2 computes links against reference data pinned by checksum and genome assembly, as the SPDI and Ensembl-gene linkers do.
Tier~3 confirms identifiers with a live web service, sending rate-limited requests and caching the responses.
The evaluated SPDI linker~\cite{holmes2020spdi} harmonizes contigs to RefSeq accessions and minimally trims each explicit allele, removing the leading and trailing bases that REF and ALT share.
Explicit alleles are ALT alleles written as bases, not symbolic alleles such as \texttt{<DEL>}, breakends, or the spanning deletion \texttt{*}.
The gene linker records Ensembl~116 genes overlapped by the REF span.
Minimal trimming supports the tested joins but does not establish canonical identity in every repeat context.
The live MyVariant.info linker confirms rsIDs~\cite{xin2016myvariant}.
Service failure stops the linker without publishing a partial linkset.

\paragraph{Policy evaluation.}
\texttt{vcf-rdfizer-policy} evaluates ODRL rules over files or declared graph selections~\cite{odrl_2018}.
The VCF Core policy profile applies default-deny semantics, so anything not explicitly permitted is withheld, and deny-overrides semantics, so a prohibition wins over a conflicting permission.
By default, it uses four DUO purposes: general research use, health/medical/biomedical research, disease-specific research, and clinical care~\cite{lawson2021duo}.
When a source resource is withheld, ownership rules also remove the calls, alleles, sample calls, and headers that depend on it.
Each release view is checked in four ways: its recorded policy digest must match the policy; it must contain nothing that an applicable prohibition covers and nothing that no applicable permission covers; none of its triples may point to a source resource missing from the view; and its records must equal those released when the same policy is applied to a minimal graph built directly from the VCF text, bypassing the converter.
Released genotypes retain source IRIs and are not anonymized.
The plug-in records obligations (ODRL duties, such as deleting released data after use) but does not enforce them.
Selector parameters are placed inside the outer SPARQL group.
An earlier trailing placement produced an empty region selection and was corrected before the reported experiments.

\subsection{Application question, comparison workflows, and evaluation scenarios}\label{subsec:usecase-case}
The application identifies observed variants with a ClinVar classification in the fixed ACMG SF v3.2 81-gene set~\cite{miller2023acmg}.
The application also identifies the participant and gene associated with each match and the matches each requester may receive.
ClinVar records require at least one review star.
Pathogenic and likely pathogenic matches are reported separately but are not treated as reportable secondary findings.

The RDF workflow links converted VCFs to ClinVar and gene resources, materializes each requester view, and queries the view with SPARQL against QLever~\cite{qlever_2017}.
The conventional workflow harmonizes contigs, annotates \texttt{CLNSIG}, \texttt{CLNREVSTAT}, and \texttt{GENEINFO} with bcftools, and applies the same case definition and release rules in Python~\cite{BCFtools}.
The comparison requires exact agreement between the workflows' sorted tuples of participant, gene, contig, position, and alleles.
The workflows share preprocessing and the case definition but use separate downstream implementations.

Scenario~1 contains ACMG gene-span slices from five single-sample VCFs: two consumer VCFs donated to the Personal Genome Project (\texttt{NB72462M} and \texttt{NG131FQA1I}) and three VCFs of GIAB samples (the precisionFDA HG002 file and the HG004 and HG005 benchmark VCFs).
Scenario~2 contains 104 high-coverage 1000 Genomes participants.
Scenarios~3 and~4 contain the complete HG005 and NB72462M VCFs, respectively~\cite{personal_genome_proj,giab_v421_2022,byrska2022highcoverage}.
Scenarios~1 and~2 use only records inside the 81 ACMG gene spans from Ensembl~116 (7.1\,Mb in total), after normalization and splitting of multiallelic records.
Scenario~2 removes repeated panel-level INFO and stores the required frequencies once in a sites-only graph.
This graph retains AF and the five population-specific AF fields; AC and AN are omitted because sample subsetting recalculated them for the cohort rather than the reference panel.
The rare-variant query extends the participant--ClinVar SPDI join with the frequency graph and requires panel $\mathrm{AF}<0.01$; the conventional workflow applies the same threshold using a position-and-allele lookup.
All scenarios use the 2026-09-13 ClinVar release~\cite{clinvar_vcf}.
Simulated release rules combine file permissions, four seeded withdrawals in Scenario~2, a 28-gene cancer restriction, and requester purposes for clinical care, cardiovascular research, and general research.
The simulated consent for HG005 permits only clinical care, so the Scenario~3 views for DS and GRU are empty.
Scenario~4 adds care by the participant's physician.
The policies combine a 40-gene cardiovascular panel, an APOE region, and one DSP variant.
In Scenario~4, every requester receives a non-empty subset of the same complete VCF.
No scenario tests selective masking of samples within a multi-sample VCF.

Four applied changes test a withdrawal, a new purpose, replacement of the cancer panel, and an HFE C282Y restriction.
The comparison tests whether both workflows release the same fixture records after each change.
Line counts describe the two implementations and do not measure usability or maintainability.

\subsection{Stage costs}\label{subsec:usecase-costs}
Conversion and linking run once per scenario.
View materialization, validation, indexing, and querying run separately for each requester.
The conventional workflow runs once per scenario for all requesters: it harmonized contigs, annotated with ClinVar, selected records, and applied the release rules in 4--91 seconds, against 5.7--105 minutes for the RDF workflow's conversion and linking alone.
Queries over non-empty views took 171--233 seconds across the four scenarios, whether a view held 6,397 or 5.06 million records; the two empty Scenario~3 views, with no observations to join, returned in 0.07 seconds.
The similar times are consistent with the fixed ClinVar join dominating the workload, not with generally scale-independent retrieval.
Scenario~2 release writing took 59--81 seconds per requester, compared with 20--27 minutes in pre-release builds.
Three changes reduced runtime and left the views byte-identical: the selections of all applicable rules are merged once, input files are filtered in parallel, and each resource's ancestor IRIs, which determine whether a selection covers it, are found once rather than once per rule.
Scenario~3 peaked at 11.2\,GB of host memory in use and 31\,GB of disk.
For Scenario~4, conversion required 88.7 minutes, linking 16.5 minutes, and each selective view 55--70 minutes to write.

\section{Reproducibility and execution}\label{sec:repro}
\subsection{The core benchmark}\label{subsec:repro-campaign}
The \emph{core benchmark} supplies RQ1 groups A and B, the main fault-injection runs in E, and the core scalability measurements.
It contains 143 runs (\emph{cells}) in 12 experiment families, executed with the published VCF-RDFizer v3.1.0 release on two identical hosts, \texttt{vcf-bench-1} and \texttt{vcf-bench-2} (Sections~\ref{subsec:repro-builds} and~\ref{subsec:repro-hosts}).
Each family corresponds to one numbered script in the testing repository's benchmark harness.
The harness and the run records of every reported result are archived on Zenodo as version v1.0.0 (\url{https://doi.org/10.5281/zenodo.23301186}; all versions: \url{https://doi.org/10.5281/zenodo.23301185}).
Scripts \texttt{00} and \texttt{02} record the environment and derive scaling inputs and are excluded from the count.
Each complete family ran on one host without concurrent benchmarks.
Every cell recorded the command, commit, image, exit status, and timings in a fresh output directory.
The experiment families are defined below.
\begin{description}\setlength{\itemsep}{1pt}
\item[Records scaling (\texttt{04}).]
HG005 prefixes contain 10,000, 100,000, and one million records, each with three replicates.
The complete VCF (3,856,856 records) was processed once, giving 10 cells in total.
Results appear in main Section~\ref{M-subsec:results-costs} and Figure~\ref{fig:scaling}.
\item[Sample representation (\texttt{03}).]
Both sample profiles (Section~\ref{subsec:model-profiles}) process 10,000 records from the 1000 Genomes chromosome-20 call set at 1, 4, 16, 64, 256, 1,024, and 2,504 samples (14 cells).
Three timing replicates at 1 and 2,504 samples under both profiles add 12 cells.
Four anchor cells cover two complete files under both profiles, the 10,000-line single-sample fixture and a 2,504-sample fixture, to check the same contrast outside the derived slices; the expanded 2,504-sample cell was skipped (below).
Results appear in main Section~\ref{M-subsec:results-costs}.
\item[Storage mode (\texttt{01}).]
Plain storage writes uncompressed N-Triples, whereas space-optimized storage streams each output part into gzip-framed N-Triples and deletes the part, so no full uncompressed copy exists.
The two modes are compared on 100,000 HG005 records with three replicates per mode.
Each mode also processes a 1,155,741-record prefix of the \texttt{NG131FQA1I} consumer WGS VCF (269.3 million triples) once, giving 8 cells in total.
Results appear in main Section~\ref{M-subsec:results-costs} and Figure~\ref{fig:scaling}f.
\item[Corpus breadth (\texttt{05}).]
HDT and COTTAS are built from the first 250,000 records of eight public inputs and from the complete HG005 VCF; a tenth cell, the complete 1000 Genomes call set, was skipped by the cohort-scale guard (10 cells).
Results appear in main Section~\ref{M-subsec:results-costs} and Figure~\ref{fig:artifacts}.
\item[Representation axes (\texttt{07}).]
Raw and structured INFO are compared on 100,000 HG005 records and HGSVC2 with three replicates per setting.
Other cells compare basic with structured header output and convert fixtures that declare VCF 4.1 to 4.5 or no version.
The family contains 20 cells (Sections~\ref{sec:inputs} and~\ref{sec:config}).
\item[Difficult inputs (\texttt{09}).]
The family includes 11 difficult-input fixtures (11 cells), a 100-record synthetic fixture linked with the three example linkers distributed since v3.0.0 (\texttt{rsid-dbsnp}, \texttt{gene-demo} with synthetic gene intervals, and the live \texttt{rsid-ensembl}; 86, 0, and 0 links; 4 cells), and a custom-mapping cell (1 cell), 16 cells in total.
The SPDI, Ensembl-gene, and MyVariant linkers used in the linked workflow were added in v3.3.0.
The sites-only cell was rerun with a corrected fixture (Section~\ref{sec:issues}).
Results appear in Section~\ref{sec:inputs} and Table~\ref{tab:difficult-inputs}.
\item[Covering set (\texttt{11}).]
The 10 configuration rows on a 1,000-line fixture use every value of seven options at least once, and every allowed pair of values from any two options appears together in at least one row; the full set of combinations is not tested.
Each row is validated with shapes, giving 10 cells (Section~\ref{sec:config}).
\item[Modes (\texttt{12}).]
Operating modes are tested independently on the 1,000-line fixture and derived artifacts (7 cells).
The modes are TSV, conversion, validation, compression, decompression, HDT indexing, and COTTAS indexing (Section~\ref{sec:config}).
\item[Feasibility (\texttt{10}).]
One million HG005 records are processed under three configurations with requested memory ceilings of 8, 16, and 31\,GB.
The family contains 9 cells (Section~\ref{sec:config}).
\item[Robustness (\texttt{08}).]
Tests cover two identical conversions of 100,000 HG005 records, a convert--compress--decompress round trip, and an index build and rebuild.
The family also measures detection of 113 injected faults with the default profile and with all three profiles.
The family contains 9 cells (main Section~\ref{M-subsec:results-fidelity} and Section~\ref{sec:validation}).
\item[Equivalence (\texttt{06}).]
The 10,000-line (9,986-record) fixture is converted under both storage modes and both sample profiles.
Validation covers four SPARQL engines, three RDF artifacts, and two HDT construction strategies: \texttt{partitioned}, which builds HDT from chunks and merges the parts, and \texttt{single}, which builds it in one \texttt{rdf2hdt} pass over uncompressed N-Triples.
Two further cells test configurations the tool must refuse.
The family contains 8 cells (Section~\ref{sec:config}).
\item[Query cost (\texttt{13}).]
The 13 source-comparison queries are compared with cyvcf2 on the 10,000-line fixture (0.96M triples) and 100,000 HG005 records (17.1M triples).
Three replicates per input give 6 cells (main Section~\ref{M-subsec:results-costs} and Section~\ref{subsec:measurements-setup}).
\end{description}
Five families contribute the 78 validation runs: Difficult inputs (20), Covering set (23), Equivalence (16), Query cost (18), and Modes (1).
A cell contains one validation run per artifact it validates (N-Triples, HDT, or COTTAS), so a family can have more validation runs than cells.

The core benchmark took 96.17\,h of measured wall time (Table~\ref{tab:campaign}).
Every asserted expectation held, but not every cell completed successfully.
The truncated-gzip fixture exited non-zero, and the exit was recorded as an outcome.
Two cells required refusal of the single-HDT strategy with COTTAS or space-optimized storage.
Three cells were skipped.
Two skips involved a 2,504-sample input under the expanded profile: the complete 1000 Genomes call set in Corpus breadth and the multi-sample anchor in Sample representation.
Both are complete 2,504-sample files, which the harness's cohort-scale guard skips under the expanded profile; the sample-count series uses 10,000-record slices and is not guarded.
The custom-mapping cell was skipped because no custom rules file was supplied.
The two fault-injection cells record the host-side test-harness commit rather than a conversion-container execution.

\paragraph{Versions and corpus processing.}
Fixtures declaring VCFv4.1--4.5, plus one with no \texttt{\#\#fileformat}, all converted.

The two-record VCFv4.5 fixture contains \texttt{LAA} and \texttt{LAD}, the local-allele FORMAT fields of VCF~4.5, while the VCFv4.4 fixture contains the phase-set field \texttt{PS}.
The fixtures produce 252.5 and 210 triples per record, respectively.
The results demonstrate field retention, not interpretation of every version-specific construct.
Local-to-global allele resolution through \texttt{LAA} is implemented for the expanded profile, but the fixture does not exercise it, because it declares \texttt{LAD} with \texttt{Number=R} rather than \texttt{Number=LR}.
The undeclared-version input uses the documented fallback.

Neither guard is evidence that the complete cohort was converted.

\section{Conversion, storage, and retrieval measurements}\label{sec:measurements}
\subsection{Record and sample scaling}\label{subsec:measurements-scaling}
RDF output grew approximately linearly across the HG005 record-count series (Figure~\ref{fig:scaling}).
A power law, triples $\propto \text{records}^{b}$, fitted by least squares on log-log axes gave $b=+0.999$ (95\% CI $[+0.991,+1.007]$), where $b=1$ means linear growth, with 170.5--171.9 triples per record.
The same fit gave $b=+1.033$ for artifact bytes, $+1.025$ for peak workspace, and $+1.063$ for end-to-end time.
End-to-end times were 40.7, 423.7, and 5,476.0 seconds for 10,000, 100,000, and one million records.
Replicate standard deviation did not exceed 13.5 seconds.
Mapping-stage resident memory remained between 1.0 and 1.7\,GB.
The record-count series built HDT but not COTTAS; HDT construction increased from 38\% of total time at 10,000 records to 82\% for the complete VCF.

\subsection{Storage mode and optional artifacts}\label{subsec:measurements-storage}
Plain and space-optimized storage produced identical triples.
Final artifact sizes differed by no more than one filesystem block.
Space-optimized mode reduced peak workspace from 2.98 to 0.325\,GB on 100,000 records, with a 5.2\% increase in runtime.
On the same 1,155,741-record \texttt{NG131FQA1I} prefix (269.3 million triples), workspace fell from 43.40 to 5.65\,GB, with a 3.2\% runtime increase.
Mapping time met a prespecified $\pm10\%$ equivalence margin on the replicated input.

Across the corpus, COTTAS occupied 0.37--0.55 times the storage of gzip-framed N-Triples and 0.27--0.37 times the storage of HDT.
COTTAS construction took 1.5--3.0 times longer than HDT construction (Figure~\ref{fig:artifacts}).
The v3.1.0 complete-HG005 run of the Corpus breadth family, which built both HDT and COTTAS, produced 657.4 million triples in 16.07 hours, including approximately 14.5 hours for HDT and COTTAS construction.
The retained HDT, HDT index, and COTTAS tree occupied 10.88\,GB, while gzip-framed N-Triples alone occupied 2.89\,GB.
The later v3.3.1 use-case conversion produced 662.4 million genomic triples in 53 minutes, or 55 minutes with ClinVar, before linking, release processing, and indexing.
The runs differ in software version, input, and processing stages.
The timing difference does not measure a speed-up.

\subsection{Setup amortization}\label{subsec:measurements-setup}
For an equivalent repeated workload with a positive per-question saving,
\begin{equation}
N_{\mathrm{break-even}}=\frac{\text{additional RDF setup}}{\text{VCF time per question}-\text{indexed RDF time per question}}.
\end{equation}
A three-replicate rerun measured the minimal RDF setup, gzip-framed N-Triples and a QLever index without HDT or COTTAS, on 100,000 records.
Conversion to gzip-framed N-Triples required a mean of 95.7 seconds, and QLever indexing a mean of 25.0 seconds.
A full cyvcf2 parse took a median of 12.28 seconds per question, compared with a mean of 1.43 seconds per indexed query.
The resulting crossover is approximately 11 separately executed questions.
The core benchmark's conversion also built HDT, which QLever does not need; with its setup of 446.5 seconds (423.7 seconds of conversion and a 22.8-second index build) and its per-question times (a median of 11.57 seconds per parse and a mean of 1.32 seconds per indexed query), the estimate is 44 questions.
The calculation uses the measured query mix and assumes a full VCF parse per question rather than one batched pass.
Per-question crossovers range from 10 to 17 repetitions.
For 100,000 records, gzip-framed N-Triples occupied 75.8\,MB, compared with 3.1\,MB for gzipped VCF.
For complete HG005, the corresponding sizes were 2.89\,GB and 139.3\,MB.
The experiment does not establish a universal break-even count.
Costs of updating evidence or policies were not measured.
\section{Configuration coverage, operating modes, and memory feasibility}\label{sec:config}
A 10-row covering set exercised every value of seven options: sample representation (expanded, condensed); INFO representation (raw, structured); storage mode (plain, space-optimized); RDF compression of the N-Triples output (gzip, Brotli); output representations (HDT, COTTAS, or both); artifact compression of the HDT and COTTAS files (gzip, Brotli); and HDT strategy (\texttt{partitioned}, \texttt{single}, or the default \texttt{auto}, which uses the partitioned path).
Every row completed validation, including shapes.
Pairwise coverage excludes only three prohibited combinations: \texttt{-{}-hdt-strategy single} with space-optimized storage, COTTAS, or \texttt{hdt,cottas}.
The tool refuses them because the single strategy reads one uncompressed N-Triples file, which space-optimized storage never writes, and COTTAS always requires chunked construction, so the partitioned path would run regardless.
Gzip and Brotli were tested in both compression roles without comparing compression ratios or throughput.

The \texttt{tsv}, \texttt{compress}, \texttt{decompress}, HDT-index, COTTAS-index, conversion-only, and validation-only modes each ran independently with exit code 0.
A feasibility sweep combined three requested memory ceilings (8, 16, and 31\,GB) with three configurations (the defaults, smaller chunks, and smaller chunks with condensed samples) on one million HG005 records.
All nine cells completed with 1.34--1.93\,GB resident memory.
The harness could not confirm that Docker limits reached every container invocation.
The measurements therefore establish low memory use, not successful execution under verified memory limits.

In the Representation axes family, structured INFO increased the graph of the complete HGSVC2 structural-variant VCF from 89.01M to 96.75M triples (8.7\%).
N-Triples size increased by 7.4\%, and HDT size increased by 7.8\%.
On 100,000 HG005 records, the increase was from 12.52M to 17.10M triples (36.6\%).
Since the dependency correction in Section~\ref{sec:issues}, raw-INFO graphs still contain the allele resources that expanded sample calls reference, so the 12.52M figure includes them.
Structured header output added only 0.03\%: 17,098,746 versus 17,094,293 triples.

The Equivalence family used a 10,000-line, 9,986-record single-sample fixture in both sample profiles and storage modes, with N-Triples, HDT, and COTTAS artifacts.
All 16 validations passed the 14 preflight checks and \texttt{Q1}--\texttt{Q13} under all four engines.
Expanded graphs contained 0.96M triples, and condensed graphs contained 0.79M triples.
The complete condensed cell took 70.4\,min.
Two additional negative tests correctly refused single-HDT strategy with COTTAS or space-optimized storage, returning exit status 2.
