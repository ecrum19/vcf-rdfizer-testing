\abstract{
\textbf{Purpose:} 
The Variant Call Format (VCF) is the dominant standard for representing genomic variation and underpins population genomics, clinical sequencing, and precision-medicine workflows. 
As VCF datasets are increasingly interpreted together with sample metadata, clinical observations, public biomedical resources, and governance information, a Resource Description Framework (RDF) representation can provide a common graph model for linkage and declarative querying. 

\textbf{Methods:} 
We present VCF-RDFizer, a command-line tool distributed through PyPI, Conda-Forge, and Docker that converts VCF into RDF using a public VCF-oriented vocabulary and modular RML mappings. 
In addition to raw N-Triples and general-purpose gzip/Brotli artifacts, the current workflow produces two queryable compressed representations: HDT and COTTAS. A storage-aware chunk pipeline incrementally reads a plain or concatenated-gzip RDF aggregate, materializes only one newline-safe uncompressed chunk at a time, converts that chunk into the selected representation(s), deletes the chunk, and merges the representation parts. 
We evaluate VCF-RDFizer v3.1.0 on a ten-file public corpus, record and sample scaling series, and purpose-built fixtures. Validation combines native representation decoding with thirteen paired SPARQL/VCF-parser queries and SHACL checks on designated inputs; a mutation experiment tests detection of 113 injected corruptions.

\textbf{Results:} 
Eight corpus files converted as 250,000-record slices, and a ninth, a 2.36\,GB Genome in a Bottle VCF, converted whole (657M triples). The tenth, a 2,504-sample cohort, was exercised through 10,000-record slices. COTTAS was the smallest queryable artifact throughout, at 0.37--0.55$\times$ the gzip-compressed N-Triples, while uncompressed HDT was 1.36--1.82$\times$ larger than those N-Triples. Space-optimized storage cut peak workspace by 7.7--9.2$\times$ for a 3--5\% time cost, and memory stayed at 1.0--1.7\,GB across a hundredfold change in input. Of 988 paired comparisons, 984 were exactly equal and 4 were verified not-applicable; all completed cross-engine comparisons agreed across both sample encodings and all three artifact types. The queries alone detected 96 of 113 injected corruptions; adding the shapes detected all 113. Per question, SPARQL answered 2.5--2300$\times$ faster than a VCF parser; a single parser pass remained faster for all thirteen questions together.

\textbf{Conclusion:} 
VCF-RDFizer provides a reproducible route from VCF to interoperable and optionally queryable compressed RDF, supporting both semantic integration and testable preservation of core variant and genotype information.%
}

\section{Introduction}\label{sec1}

%% VCF Intro - what is it? how can we improve its usage?
\textbf{Variant Call Format}.
The Variant Call Format (VCF) is the dominant standard for representing and exchanging genomic variants across research and clinical sequencing pipelines, including pharmacogenomics and precision medicine applications \cite{vcf_spec_2024,pharmcat,souche_recommendations_2022}. 
As clinical sequencing expands, variant datasets are increasingly interpreted alongside external biomedical resources, patient or sample metadata, and governance constraints controlling access to sensitive genomic information. 
Operational semantic-genomics initiatives already demonstrate the value of linking variant observations to curated biomedical databases and controlled-access frameworks \cite{togovar_2022,sphn_semantic_2023}.

These emerging use cases expose limitations of the traditional VCF representation.
First, clinical interpretation frequently requires linking variants to external knowledge sources such as protein annotations, disease databases, or pharmacogenomic resources. 
While VCF supports annotation fields, it provides limited mechanisms for structured, machine-interpretable linkage between variant records and external resources. 
Second, genomic datasets frequently require fine-grained privacy controls, such as restricting access to particular genomic regions or subsets of variants, which the VCF specification does not natively support.
Third, querying variant collections across multiple VCF files, for example, identifying clinically relevant mutations or retrieving variants within genomic position intervals, typically relies on specialized command-line utilities (e.g., bcftools \cite{BCFtools}) or custom pipelines rather than interoperable, declarative query mechanisms.

In other domains, semantic web and policy frameworks, such as Linked Data \cite{W3CLinkedDataWiki} and the Open Digital Rights Language (ODRL) \cite{odrl_2018}, enable structured linkage between datasets, external knowledge resources, and access control policies. 
Applying similar approaches to genomic variant data could enable richer integration with biomedical knowledge bases and more expressive query capabilities.


%% RDF Intro - What is it? How can it help enrich VCF data?
\textbf{Resource Description Framework and Knowledge Graphs}.
The Resource Description Framework (RDF) \cite{rdf} provides a widely adopted graph-based data model for representing relationships between entities identified by globally unique identifiers (IRIs).
Such graph-structured data can be organized as \textit{knowledge graphs}, in which nodes represent entities of interest and edges capture relationships between them, with the graph serving to accumulate and convey knowledge \cite{hogan_knowledge_graphs_2021}.
For variant data, RDF enables (i) structured linkage between variant data and external biomedical resources \cite{bio2rdf_2008,openbiolink_2019,sib_2024}, (ii) native declarative querying via the SPARQL query language \cite{sparqllang}, and (iii) fine-grained privacy policy enforcement over variant data and linkages \cite{odrl_2018}.
In practice, this could enable, for instance, a user to query a collection of VCF-derived datasets to identify variants whose alternative alleles occur in a specific gene, are associated with a given phenotype, and are accessible under particular policy restrictions.


%% How do we turn VCF into RDF? Why is it hard?
\textbf{From VCF to RDF}.
Transforming VCF into RDF requires \textit{semantic lifting}: converting the row-based structure of VCF files into graph statements. 
Relevant VCF elements such as genomic position, alleles, genotypes, and sample identifiers are assigned IRIs, and fields are translated into subject–predicate–object triples. 
Ontology-aligned predicates provide consistent semantics which enable datasets to be queried and linked.

This transformation requires two components: 
(i) a semantic vocabulary describing VCF concepts and relationships, and 
(ii) a mapping process that converts VCF file content into RDF using this vocabulary. 
Such mappings must be systematic and reproducible due to the structural heterogeneity permitted by the VCF specification \cite{vcf_spec_2024}. 
INFO fields may contain semi-structured annotations, FORMAT and genotype columns vary across datasets, and multi-sample files aggregate multiple genotypes within shared variant records, complicating the creation of consistent semantic representations.

Several efforts have explored semantic representations of VCF and genomic-variation data, ranging from direct VCF-to-RDF converters to systems that expose genomic variation through RDF and SPARQL interfaces.

Early approaches include the \textit{rdf-vcf} reader and the web-based \textit{VCF2RDF}, the latter introducing an isomorphic mapping between VCF and RDF/JSON-LD \cite{ruby_rdf_vcf,vcfr_2017}.
The 2013 BioHackathon produced another early \textit{vcf2rdf}, a JRuby converter that describes positions with FALDO and alleles and genotypes with tool-specific terms \cite{katayama2019biohackathon}.
Dedicated conversion utilities include JVarkit's \textit{VcfToRdf}, the Rust-based \textit{VCF2RDF} utility developed for TOGOvar \cite{JVarkit_2015,togovar_2022}, and the \textit{vcf2rdf} component of SPARQLing Genomics \cite{sparqling_genomics_2020,sparqling_genomics_software}.
More general genomic-format tools also reach RDF: \textit{BioInterchange} emits the Genomic Feature and Variation Ontology (GFVO) from GFF3, GVF and VCF, although its VCF reader extends its GFF3 reader, so records become generic features, and it reads VCF 4.1--4.2 only \cite{baran2015gfvo}; and \textit{bio-vcf} can serialize VCF-derived information as RDF or JSON-LD through configurable output templates \cite{bio_vcf}.
VCF-derived graphs are also built inside larger knowledge-graph pipelines. VariantKG annotates VCFs with SnpEff, converts them with SPARQLing Genomics' \textit{vcf2rdf}, and adds its own ontology for CADD scores and patient metadata to support graph machine learning \cite{variantkg_2025}; AgroLD names a VCF2RDF component of the ETL that feeds its plant-science knowledge graph \cite{larmande2025agrold}, but that component's code could not be located in the cited repository.
In contrast to these materializing approaches, \textit{Semantic Beacons} uses declarative RML mappings to expose genomic-variation data obtained through the Beacon API as RDF, enabling federated SPARQL access without functioning as a conventional VCF-to-RDF converter \cite{semantic_beac_2025}.

Table~\ref{tab:intro-tool-comparison} compares these approaches according to their semantic modeling, transformation workflow, support for metadata and genotype information, extensibility, compression, and software distribution.
The comparison illustrates that previous systems address different portions of the VCF-to-semantic-data workflow.
Some prioritize lightweight and efficient conversion, others provide highly customizable serialization or virtual semantic access, while several expose only a subset of VCF structure or rely on implementation-specific RDF models.
VCF-RDFizer is designed to combine these concerns within a single reproducible workflow by being grounded in a publicly documented VCF semantic model, declarative and extensible mappings, systematic representation of record-, metadata-, and sample-level information, and integrated production of both conventional and compressed queryable RDF representations.


%% Public semantic vocabulary

\textbf{Open Challenges}.

%% Explicit semantic definitions
\textit{First}, existing VCF-to-RDF approaches differ substantially in how explicitly and completely they define the semantics of the generated RDF.
Some systems document an RDF representation or mapping of VCF concepts, such as the isomorphic VCF-to-RDF model of the web-based VCF2RDF \cite{vcfr_2017} or BioInterchange's GFVO output \cite{baran2015gfvo}, while others use lightweight or implementation-specific RDF structures optimized for particular conversion or application requirements \cite{togovar_2022,JVarkit_2015,katayama2019biohackathon}. Pipelines such as VariantKG inherit whichever structure their converter emits and extend it for their own application \cite{variantkg_2025}.
More general tools such as \textit{bio-vcf} allow users to define custom RDF serializations, but do not prescribe a reusable semantic model of VCF structure.

Consequently, a remaining challenge is the availability of a standalone, publicly documented vocabulary that systematically captures the structural semantics of VCF itself, including file- and header-level metadata, variant records, INFO and FORMAT definitions and values, sample-level calls, and genotype relationships.
Existing genomic ontologies and data models such as GA4GH Variant Representation \cite{ga4gh_varschema_2021}, FALDO \cite{faldo_2016}, the Sequence Ontology \cite{seq_ont_2005}, GFVO \cite{baran2015gfvo}, GENO, and SNPO provide important semantics for genomic locations, variation, and biological entities, but were not designed to represent the complete structure and serialization semantics of a VCF document.
A dedicated VCF semantic layer can therefore complement these resources while reusing their established biological concepts where appropriate.

%% Declarative modular mappings
\textit{Second}, extensibility is supported through different mechanisms across existing converters, but semantic transformation rules are often coupled to implementation logic, configuration files, or application-specific templates.
For example, TOGOvar's \textit{VCF2RDF} exposes configurable namespaces, INFO-field selection, and reference mappings through YAML configuration \cite{togovar_2022}, while \textit{bio-vcf} provides highly flexible output templates capable of generating customized RDF representations.
Such mechanisms are useful for adapting output, but the resulting transformation semantics remain closely associated with the particular software or template implementation.

Declarative mapping languages provide a complementary approach by representing transformation rules independently from the execution engine.
RML (RDF Mapping Language) \cite{rml_2024} supports mappings from heterogeneous data sources into RDF and enables mapping definitions to be reused, inspected, versioned, and extended independently of the software executing them.
This approach is also employed by Semantic Beacons, which uses RML mappings to transform Beacon API responses into RDF for on-demand semantic access \cite{semantic_beac_2025}.
The RML ecosystem additionally includes engines such as RMLStreamer \cite{rmlstreamer_2022}, which support scalable execution of declarative mappings.
For VCF conversion, separating the semantic model and mapping rules from procedural parsing logic provides a mechanism for adapting dataset-specific INFO, FORMAT, metadata, or ontology alignments without requiring modifications to the core conversion implementation.

%% RDF compression
\textit{Third}, most existing VCF-to-RDF workflows do not integrate strategies for addressing the storage expansion introduced by semantic lifting.
Expanding compact genomic formats such as VCF into explicit RDF triples can substantially increase storage requirements, particularly because identifiers and structural relationships that are implicit in VCF become explicit and may be repeated across large numbers of triples \cite{rdf}.

Compression strategies therefore play an important role, but archival and queryable compression address different requirements.
General-purpose compressors such as gzip and Brotli \cite{brotli_2019} can substantially reduce storage and transfer costs, but the resulting artifacts ordinarily require decompression before they can be queried as RDF.
In contrast, RDF-specific representations such as HDT (Header--Dictionary--Triples) \cite{hdt_2013} combine compression with indexed triple-pattern access.
More recently, COTTAS represents RDF as a columnar triple table using Apache Parquet and block-range indexes, enabling triple-pattern evaluation directly over the compressed representation \cite{cottas_2025}.
Integrating both archival and queryable representations within a VCF-to-RDF workflow therefore allows users to select storage strategies according to whether the resulting genomic knowledge graph is intended primarily for distribution, long-term storage, direct querying, or a combination of these purposes.


%% So what + Aims of study
% (1) semantic completeness and reuse, (2) mapping portability and extensibility, and (3) storage and queryability
\textbf{Study Aims}.
Taken together, these limitations motivate the development of a reusable and reproducible VCF-to-RDF transformation tool whose output can be independently validated. 
Here we present \textit{VCF-RDFizer}, which integrates a publicly documented vocabulary, modular RML-based mappings, storage-aware conversion, general-purpose compression, and queryable HDT and COTTAS representations.
As summarized in Table~\ref{tab:intro-tool-comparison}, VCF-RDFizer combines capabilities that are typically disconnected in existing approaches: a standalone CLI \url{https://github.com/ecrum19/VCF-RDFizer}, the public VCF Core Vocabulary \url{https://w3id.org/vcf-core/vocab\#} \cite{vcfc210}, modular declarative mappings, a reproducible pipeline, queryable compressed outputs, and public packaging \url{https://pypi.org/project/vcf-rdfizer/}. 
In addition to measuring conversion and compression costs, this study defines a paired SPARQL/VCF-parser workload to determine whether the RDF representation reproduces established variant and genotype summaries exactly.


\section{VCF-RDFizer CLI Tool}\label{sec2}
VCF-RDFizer is a command-line tool that converts input VCF files into semantically enriched RDF using a reproducible mapping pipeline. 
The workflow integrates pre-processing, mapping, RDF conversion, compression/decompression functionalities, graph validation functionalities, graph data linking plug-in architecture, and other features. 
An overview of these workflows is shown in Figure~\ref{fig1}.

\subsection{Semantic Model}\label{subsec2.1}
VCF-RDFizer emits RDF in the VCF Core Vocabulary (\texttt{vcfc:}, \url{https://w3id.org/vcf-core/vocab\#}) \cite{vcfc210}, a separately maintained vocabulary that models the VCF specification itself, version by version, for VCFv4.1 through VCFv4.5. 
It is described and evaluated in its own right in a companion paper \cite{crum_vcfcore_2027}; here it is the target model of the conversion. 
Its terms align with established resources for genomic coordinates (FALDO \cite{faldo_2016}), variant typing (the Sequence Ontology \cite{seq_ont_2005}), genotype and sample constructs (HERO \cite{hero-genomics_2025}), and features of the GA4GH VRS schema v2.0.1 \cite{ga4gh2025VRS}, so that VCF-specific structure is kept without duplicating mature ontology terms.

The model preserves three information layers: file and header assertions, variant-record assertions, and sample and genotype assertions. 
Sample-level data can be emitted in two profiles. 
In the \emph{expanded} profile every sample value is its own resource, which makes genotypes directly queryable. 
In the \emph{condensed} profile values are stored as sample-ordered vectors, reducing the number of RDF resources while requiring decoding for access to individual sample values.
Both profiles keep the same file, header and record context. 

\textbf{Sample-profile scaling.}
Let $V$ be the number of variant records, $S$ the number of samples, and $F$ the number of FORMAT keys per record.
Both profiles describe the $S$ samples once per file.
For a uniform FORMAT layout, expanded representation adds $VS$ sample-call resources and $VSF$ FORMAT-value resources, whereas condensed representation adds $V$ cohort matrices and $VF$ value vectors.
Excluding the record and header structure common to both profiles, and assuming bounded ploidy and FORMAT-value arity, the sample-layer triple counts therefore scale as
\begin{equation}
\begin{aligned}
T_{\mathrm{expanded}}  &= \mathcal{O}(S + VSF),\\
T_{\mathrm{condensed}} &= \mathcal{O}(S + VF).
\end{aligned}
\label{eq:sample-profile-scaling}
\end{equation}
The condensed profile removes the per-sample factor from the repeated RDF structure, but still stores all $VSF$ values inside vector literals, so its size in bytes keeps growing with $S$ even though its triple count does not (Section~\ref{subsec3.3}).
Consequently, a nearly constant triple count as $S$ increases does not imply constant file size or sample-access cost.
This trade-off motivates retaining expanded representation for direct sample-level RDF queries and condensed representation for cohort-scale storage, and measuring triple counts, artifact bytes, and peak workspace separately.

The vocabulary itself carries classes, properties, domains and ranges but no OWL restrictions.
Value and cardinality constraints are expressed as SHACL shapes, which VCF-RDFizer v3.1.0 bundles from vocabulary commit \texttt{5bfd19d} and applies during validation (Section~\ref{subsec3.5}).

Core entities are minted from deterministic IRI templates derived from the source file and record position, so identifiers are reproducible across runs. 
Section~\ref{subsec3.5} confirms this with byte-identical repeated conversions. 
A simplified view of the core classes is shown in Figure~\ref{fig2}, and the full vocabulary, with worked single- and multi-sample examples, is documented at \url{https://ecrum19.github.io/vcf-core-vocabulary/}.

\subsection{Tool Workflow}\label{subsec2.2}
VCF-RDFizer is implemented as a Python command-line tool that coordinates five stages: 
(1) conversion of each VCF into records, header-line, and file-metadata TSV logical sources; 
(2) TSV-to-RDF transformation with modular RML mappings and RMLStreamer; 
(3) construction of one the materialized N-Triples graph (either plain or space-optimized); 
(4) optional creation of raw-RDF gzip/Brotli artifacts and/or queryable HDT/COTTAS representations; and 
(5) native representation validation, packaging, cleanup, and run-metric reporting. 
The command-line interface separates these concerns through \texttt{--rdf-storage-mode}, \texttt{--rdf-compression}, \texttt{--representations}, and \texttt{--artifact-compression}. 
Thus, an unwrapped \texttt{.hdt} or \texttt{.cottas} file can be retained for querying while an additional \texttt{.gz} or \texttt{.br} package is created for transport or archival storage.

Mapping rules are authored in Turtle as modular RML rule sets~\cite{rml_2024} that mediate the conversion from VCF to RDF. 
This modularity allows rules to be extended or modified without rewriting the full pipeline. 
To execute the mappings, we use RMLStreamer~\cite{rmlstreamer_2022}, version 2.5.0, through its standalone command-line interface.

\textbf{Aggregate storage modes.}
In \texttt{plain} mode, RMLStreamer outputs are appended to one uncompressed \texttt{<sample>.nt} graph and the partitioned RMLStreamer outpus are deleted after incorporation. 
In \texttt{space-optimized} mode, each line-oriented RMLStreamer ouput is gzip-compressed, appended as a member of one concatenated-gzip \texttt{<sample>.nt.gz} stream, and then deleted. 
Standard gzip readers expose the concatenated members as one logical N-Triples sequence. 
This avoids retaining all RMLStreamer parts and a second full uncompressed aggregate simultaneously.

\textbf{One-chunk-at-a-time compressed graph representation construction.}
The current implementation incrementally reads the plain or gzip aggregate, respects newline-terminated N-Triples record boundaries, and materializes one raw chunk in a Docker-managed workspace. 
Each selected representation builder consumes that chunk before the raw chunk is deleted and the next chunk is created:

Consequently, at most one uncompressed RDF chunk exists at a time. 
The final HDT/COTTAS parts, merge intermediates, indexes, and converter scratch space still require storage, but the pipeline does not create a full decompressed duplicate of the aggregate.

\textbf{HDT construction.}
Each chunk is converted with \texttt{rdf2hdt} from hdt-cpp \cite{hdtcpp,hdt_2013}. 
Intermediate HDT files are then merged pairwise in a balanced tree with \texttt{hdtc create} \cite{hdtc_2026}, which performs the same logical merge as HDTCat \cite{Diefenbach2020HDTCat} under a fixed memory budget and without Java; an unpaired file is carried into the next merge round, and each merge's scratch directory is removed as soon as that merge completes. 
The final HDT artifact is indexed by \texttt{hdtc}, producing the sibling \texttt{.hdt.index.v1-1} index without executing a query. Intermediate indexes are not retained because the final merged dictionary and triple layout are authoritative.

\textbf{COTTAS construction.}
COTTAS encodes RDF in an Apache Parquet triple table and supports compressed triple-pattern evaluation through columnar pruning and indexes \cite{cottas_2025}. 
VCF-RDFizer converts each chunk with pycottas~\cite{pycottas_2026} and then merges all chunk files in a single streaming $k$-way merge rather than pairwise, so no global in-memory hash table or full-size temporary spill is built.
The merged output carries an \texttt{spo} index, which is fixed rather than user-selectable in v3.1.0. (This will change in future version) 
Each COTTAS operation runs in an isolated temporary working directory so that its local DuckDB scratch database cannot be reused by a later chunk or merge. 
COTTAS artifacts are queried through a Comunica engine that evaluates SPARQL over the Parquet table with DuckDB \cite{comunica_cottas_2026}. 

\textbf{Validation and metrics.}
Before packaging or raw-RDF cleanup, every base HDT or COTTAS artifact is opened with its native reader (\texttt{hdt2rdf}, \texttt{pycottas.cottas2rdf}) and decoded as a stream. 
The decoded triple count is compared with the source count recorded by RMLStreamer or the partition planner.
No full decoded RDF file is written for this check. 
A missing decoder, unreadable artifact, or count mismatch fails the representation stage and prevents source cleanup. 
Chunk conversion, merging, final indexing, validation, and packaging are timed separately, while sample-level metrics report cumulative wall/user/system time, maximum resident set size, output sizes, and cleanup status.

Gzip and Brotli \cite{brotli_2019} are available for raw RDF and artifact packaging; their configuration values are exercised in the covering-set experiment (Section~\ref{subsec3.8}).

\textbf{Chunk sizes.} 
By default a chunk targets 512\,MiB of uncompressed N-Triples, bounded below by 128\,MiB and above by 1\,GiB (\texttt{--chunk-target-bytes}, \texttt{--chunk-min-bytes}, \texttt{--chunk-max-bytes}). 
For constrained workspaces the documented lower-peak setting is 128\,MiB target, 64\,MiB minimum and 256\,MiB maximum, trading additional chunks and merges for a lower temporary peak. 
Every experiment in Section~\ref{sec3} used the defaults except six cells of the memory-feasibility sweep, which used the lower-peak setting (Section~\ref{subsec3.8}).

\textbf{Pinned toolchain.} 
VCF-RDFizer v3.1.0 fixes its dependencies inside the container image: RMLStreamer 2.5.0, hdtc 1.1.0, pycottas 1.1.0, DuckDB 1.5.5, cyvcf2 0.34.0, pyshacl 0.30.1, Comunica 5.3.0 for N-Triples, \texttt{@comunica/query-sparql-hdt} 5.0.1, the COTTAS Comunica engine 0.1.0, bcftools from the base distribution, and QLever pinned by image digest. 
\texttt{rdf2hdt} and \texttt{hdt2rdf} are compiled from the hdt-cpp repository at image build time, so their exact revision is fixed by the image digest rather than by a version number; the resolved image for each benchmark run is recorded with its command and metrics (Section~\ref{subsec2.3}).

The implementation, default RML mappings, and more in-depth documentation about the functionalities and approaches described above are available at \url{https://github.com/ecrum19/VCF-RDFizer}. 

From a user-experience perspective, each tagged VCF-RDFizer version is published across PyPI, Conda-Forge, and DockerHub so users can choose pip-, conda-, or container-based installation with matched versions.
The GitHub README serves as the primary user guide, including quick-start commands, end-to-end usage examples, command-line option documentation, and troubleshooting notes.
For maintainability, the project follows a release-oriented workflow with versioned changelogs, public issue triage, planned periodic dependency/container updates, and extensive unit-testing within the tool to preserve reproducibility over time.

\textbf{Input selection and experimental scope.}
The corpus-breadth experiment uses the first 250,000 records of each input, with complete headers retained, except for \texttt{HG005\_GRCh38}, which is processed whole. 
The expanded-representation arm excludes corpus inputs with more than 1,000 sample columns, so the 2,504-sample 1000 Genomes file is assessed separately through 10,000-record slices. 
The resulting corpus measurements comprise eight 250,000-record conversions and one whole-file conversion. 
All use space-optimized storage and build both HDT and COTTAS from the same RDF graph (Figure~\ref{fig:representations}).

Record scaling uses \texttt{HG005\_GRCh38} at 10,000, 100,000, and one million records, with three replicates at each size, followed by one whole-file run. 
Sample scaling uses \texttt{1000G\_phase3\_chr20} held at 10,000 variant records and varies the sample count from 1 to 2,504 under both expanded and condensed representations. 
Holding variant content fixed isolates the sample-count dependence in Equation~\ref{eq:sample-profile-scaling}, while testing both profiles quantifies the cost of exposing individual sample values as RDF resources.
Source INFO fields are held fixed when sample columns are selected, so these derived inputs measure structural scaling rather than the consistency of INFO allele summaries with the selected samples. 
Paired storage-mode runs compare peak workspace and wall time on identical inputs. 
Separate experiments exercise INFO and header representations, all seven configuration axes, individual operating modes, requested memory ceilings, and the three linking tiers.

\textbf{Version and difficult-input coverage.}
Nine public inputs declare VCFv4.2, and \texttt{1000G\_phase3\_chr20} declares VCFv4.1. 
Dedicated version fixtures extend coverage through VCFv4.5 and include an absent file-format declaration \cite{vcf_spec_2024}. 
Eleven additional fixtures exercise CRLF line endings, symbolic and breakend alleles, mixed ploidy, missing and partially missing genotypes, unused header declarations, FILTER states, a header-only file, a sites-only input, and a truncated gzip stream. 
These small inputs isolate specific format features; production-scale evidence for VCFv4.3--4.5 remains outside the public corpus.

\textbf{Validation and query measurements.}
Every constructed HDT and COTTAS artifact is decoded with its native reader and checked against the source triple count. 
The paired query suite in Table~\ref{tab:semantic-queries} is run on designated validation inputs: the difficult-input fixtures, a 10,000-record multi-sample fixture under both sample representations and all three artifact types, and a 100,000-record slice of \texttt{HG005\_GRCh38}. 
These inputs also support graph-integrity checks, SHACL validation, cross-engine comparisons, and determinism and round-trip tests. 
A separate mutation experiment measures detection of 113 injected corruptions. 
The corpus-breadth cells supply native decode and triple-count evidence; the full paired workload is not run on those cells. 
Retrieval measurements use three replicates and report engine setup separately from query execution and representation construction.

\textbf{Execution environment and measurement protocol.}
The tagged benchmark configuration uses VCF-RDFizer v3.1.0 (commit \texttt{d3b34d5}) from \texttt{ecrum19/vcf-rdfizer:v3.1.0}, with resolved image digest \texttt{sha256:1904e96dde12ab2e2e70d8ee1267765c\-293ab100a8bd1b14d5b009b2bf8e34aa}. 
Image rebuilding is disabled during execution so that all cells in the tagged run use the same container. 
The per-cell manifests retain the actual commit and image identifiers used for each measurement.

Experiments run on two physically separate, identically specified hosts (\texttt{vcf-bench-1} and \texttt{vcf-bench-2}): 
Ubuntu 24.04.4 LTS, kernel 6.8.0-85-generic, Intel Xeon Silver 4309Y at 2.80\,GHz (8 cores), 33.6\,GB RAM with swap disabled, a 210\,GB SSD, Docker 29.7.2, and Python 3.12.3. 
Each complete experiment is assigned to one host and executed without concurrent benchmark jobs, keeping comparisons within-host. 
Both hosts execute an identical calibration workload; its results are reported in Section~\ref{subsec3.1}.

The harness creates a fresh output directory for each cell and records its command, host, tool commit, container image, exit status, and wall time. 
Tool reports provide stage timings, peak resident set size, triple counts, artifact sizes, and validation outcomes; workspace monitoring records transient disk use separately from final artifact size. 
Input sizes used in performance comparisons are uncompressed VCF bytes, while Table~\ref{tab:test-corpus} reports compressed download sizes. 
Replicated comparisons report variability or confidence intervals; single-run corpus measurements describe the tested input and configuration without estimating run-to-run variation. 
The per-cell records, normalized query results, and comparison reports are archived in the testing repository.

Q1--Q4 apply to every file because they use fixed VCF fields represented by the current mapping. 
Q5--Q6 apply only when the source contains sample columns and a \texttt{GT} FORMAT field; an empty result is accepted only after header preflight confirms that GT is genuinely absent. 
Each input is validated only against the graph converted from it: results are never pooled across files, so inputs on different reference assemblies (GRCh37 and GRCh38) are never compared with one another. A graph is queried as a single source even when it was written as several RMLStreamer parts or built from several chunks, because those are merged into one aggregate or artifact before validation runs.

The same SPARQL text is executed by four engines: QLever, which is the default; the local-file Comunica package \texttt{@comunica/query-sparql-file} for N-Triples \cite{Taelman2018Comunica,comunica_file_docs_2026}; \texttt{@comunica/query-sparql-hdt}, which accepts an \texttt{hdt@path/to/file.hdt} source \cite{comunica_hdt_docs_2026}; and a Comunica engine that evaluates SPARQL over COTTAS files with DuckDB \cite{comunica_cottas_2026}. 
Each engine can be pointed at any of the three artifacts, and \texttt{--validation-engine all} runs all four and records whether they agree. 
On the VCF side, cyvcf2 provides the primary programmatic oracle, while \texttt{bcftools query} preserves the exact FILTER token needed for Q4 \cite{BCFtools,cyvcf2_2017}.

The primary correctness contract is exact equality of normalized query results: metadata strings for Q7 and integer counts for the remaining queries, including the digest-bucket counts in Q11--Q13. 
Ratios such as Ti/Tv, call rate, and allele frequency are derived only after their underlying counts agree. 
The comparator preserves contig and sample identifiers, distinguishes \texttt{PASS} from \texttt{.}, applies the same rules to phased/unphased and missing genotypes, and emits missing/extra/differing rows for localization. 
Preflight checks additionally validate N-Triples syntax, one-to-one cardinality of core record properties, position datatypes, source/output hashes, tool versions, and record/triple counts.

\textbf{Coverage of QUAL, INFO and FORMAT.} 
QUAL is emitted for every record as a typed literal, with a missing QUAL written as \texttt{"."\textasciicircum\textasciicircum vcfc:Null}; it is produced by the tool's record-detail emitter rather than the RML mapping, because RML cannot switch a literal's datatype per row. 
INFO is emitted in the structured representation by default --- one typed value resource per record and key, decomposed into per-allele items for Number=A/R/G fields --- with the complete source string kept alongside as \texttt{vcfc:infoRaw}; \texttt{--info-representation raw} keeps the string alone. 
Q1--Q6 do not inspect QUAL, INFO, or FORMAT fields other than GT. 
The digest queries Q11--Q13 in Table~\ref{tab:semantic-queries} extend this coverage: Q11 hashes each record's fields and raw INFO string together with its IRI; Q12 hashes structured INFO values with their IRIs; and Q13 hashes per-sample FORMAT values in the expanded representation or sample-ordered FORMAT vectors in the condensed representation. 
Each query compares a histogram over the first byte of SHA-256, allowing detection of value changes that ordinary counts miss without requiring a full value listing; agreement of these finite histograms does not guarantee value-by-value equality.

This workload establishes \emph{representation equivalence} for the stated fields: a SPARQL engine and a conventional VCF parser should derive the same deterministic summaries from two representations of the same source. 
It does not establish that the source calls are biologically correct, normalized, left-aligned, or concordant with a truth set. 
The GIAB inputs can support a later reference-aware truth-concordance layer, but that requires confident regions and normalization beyond the present semantic-equivalence test.

The query files, cyvcf2 oracle, normalizer and comparator are committed and were executed 78 times across the campaign; Section~\ref{subsec3.5} reports the outcomes. 
Every validation runs the thirteen-query workload in Table~\ref{tab:semantic-queries}, preceded by fourteen graph-integrity preflight queries. 
The cross-engine experiment includes N-Triples, HDT, and COTTAS under both sample profile representations.

\subsection{Input and version coverage}\label{subsec3.2}
\textbf{Declared VCF versions}. 
Six single-purpose fixtures covering VCFv4.1 through VCFv4.5, plus one file with no \texttt{\#\#fileformat} declaration, all converted with exit code 0. 
The generated RML mapping for each version is byte-identical apart from the asserted file class (\texttt{vcfc:VCF41File} through \texttt{vcfc:VCF45File}), which locates version awareness in the typed file resource rather than in field-level rules. 
Field handling is therefore data-driven: the VCFv4.5 fixture's local-allele \texttt{FORMAT} keys (\texttt{LAA}, \texttt{LAD}) and the VCFv4.4 fixture's phase-set key (\texttt{PS}) are carried through as ordinary FORMAT entries, raising the per-record triple yield from 210 (4.4) to 252.5 (4.5) on otherwise matched two-record fixtures. 
This is preservation, not interpretation: nothing in the graph resolves a local allele index to a global allele, so VCFv4.4/4.5 support should be described as lexical carry-through pending a dedicated local-allele semantics layer. 
The undeclared-version file also converted, via the documented fallback.

\textbf{Real cohorts}. 
Nine of ten corpus files converted end to end, with HDT and COTTAS built and decode-checked for each (Figure~\ref{fig:representations}). 
The tenth, the 2,504-sample 1000 Genomes chromosome-20 call set, was skipped by the benchmark harness rather than refused by the tool: the harness withholds any corpus file with more than 1{,}000 sample columns from the expanded arm, because the expanded representation emits one call resource per record and sample. 
The resulting sample-dependent growth in RDF structure is described in Section~\ref{subsec2.1}.
The whole file was therefore not converted in either representation. Its full sample dimension was exercised instead through 10{,}000-record slices carrying all 2{,}504 samples, which converted in both representations, and Section~\ref{subsec3.3} quantifies why the expanded arm cannot be run on the whole file at this disk budget. The tool also applies a workspace check: before converting, it estimates the expanded workspace from the record and sample counts and refuses the run when that estimate exceeds three quarters of the free space, naming the condensed representation as the alternative. The completed corpus runs cover eight 250{,}000-record slices and one whole file (\texttt{HG005\_GRCh38}, 2.36\,GB uncompressed). Together with the 1000 Genomes sample slices, they provide feature coverage across ten public inputs.

\textbf{Difficult inputs}. Eleven adversarial fixtures were run (Table~\ref{tab:awkward}; fixture files are named \texttt{awkward\_*} in the testing repository). Nine converted and passed validation, including CRLF line endings, symbolic alleles, breakend ALT syntax, ploidy 4 and 3 in the same file, half-calls and haploid calls, missing values in every optional field, header keys declared but never used, the three-way \texttt{PASS}/\texttt{.}/failed-filter distinction, and a header-only file with no data records. Two cells exited non-zero. One is a refusal to convert: the truncated gzip stream, rejected in 0.58\,s at the decompression stage with a clear diagnostic, which is the intended behaviour. The sites-only file produced 245 triples and an HDT artifact, but its paired validation was not completed.

\subsection{Scaling with records, samples, and storage mode}\label{subsec3.3}
\textbf{Records}. A four-rung ladder derived from \texttt{HG005\_GRCh38} (10\,k, 100\,k, 1\,M records, then the whole 2.36\,GB file) was run in triplicate at the first three rungs (Figure~\ref{fig:scaling}a). Triple production is exactly linear in records: the fitted exponent is $+0.999$ (95\% CI $[+0.991,+1.007]$, $R^2 = 1.0000$), and the per-record yield is constant at 170.9--171.9 triples. Final artifact bytes scale at $+1.033$ and peak workspace at $+1.025$; end-to-end wall time scales at $+1.064$ from 10\,k to 1\,M records (40.7\,s, 423.7\,s, 5{,}476.0\,s; replicate sd $\leq 11.0$\,s). Peak resident memory of the mapping stage is effectively flat at $+0.115$, staying between 1.0 and 1.7\,GB across a hundredfold change in input --- the streaming design is memory-bounded, and it is disk, not RAM, that scales with the data. The one exception is the queryable-representation build on the whole 2.36\,GB file, which peaked at 4.9\,GB. The RMLStreamer mapping stage itself accounts for only 12.2--41.4\,s of that time; end-to-end cost is dominated by the downstream queryable-representation build.

\textbf{Samples}. The same 10{,}000 variant records were re-emitted against a sample ladder of 1, 4, 16, 64, 256, 1024 and 2504 columns, holding variant content fixed (Figure~\ref{fig:samples}a). The two sample representations separate exactly as the semantic model predicts: condensed triple production has a fitted exponent of $+0.001$ (95\% CI $[+0.000,+0.002]$) --- 1{,}439{,}503 triples at one sample and 1{,}452{,}018 at 2{,}504, a 0.9\% increase over a 2{,}504-fold change --- while expanded production has an exponent of $+0.795$ (95\% CI $[+0.649,+0.940]$), reaching 627{,}372{,}018 triples, $432\times$ the condensed graph for the same variants. End-to-end wall time follows: exponent $+0.183$ condensed versus $+0.788$ expanded (250\,s versus 15{,}269\,s at 2{,}504 samples), and the stored artifact grows from 67\,MB to 8.77\,GB. Triple counts understate what the condensed profile stores, because its per-sample values move into vector literals rather than disappearing (Figure~\ref{fig:samples}b). From 1 to 2{,}504 samples its HDT grows $5.8\times$ (10.2\,MB to 59.2\,MB) while its triples grow 0.9\%; its gzip-framed N-Triples grow only $1.25\times$ (6.5\,MB to 8.1\,MB), because sample-ordered genotype vectors compress well. Measured in bytes, the expanded-to-condensed gap at 2{,}504 samples is $322\times$ in gzip-framed N-Triples and $69\times$ in HDT, against $432\times$ in triples (Figure~\ref{fig:samples}c). The condensed HDT nevertheless stays smaller than the uncompressed input VCF (59.2\,MB against 101.6\,MB), whereas the expanded HDT is $40\times$ larger than it (4.10\,GB). Extrapolating the expanded representation to the full 1{,}812{,}841-record chromosome-20 call set gives roughly 2\,TB against a 189\,GB volume, which is the measured basis for the guard described in Section~\ref{subsec3.2}. Under the tested disk budget, condensed encoding is the feasible option for extending conversion to the full cohort.

\textbf{Storage mode}. The plain and space-optimized storage modes were run paired on two inputs (Figure~\ref{fig:scaling}b). They are indistinguishable in output --- identical triple counts (17{,}098{,}746 and 269{,}272{,}677) and the same final artifact size, to within one 4\,kB filesystem block --- and differ only in transient disk. Peak host workspace falls by $9.19\times$ (2.98\,GB to 0.325\,GB) on the 100\,k-record input and by $7.68\times$ (43.40\,GB to 5.65\,GB) on the larger one, at a time cost of $+5.2\%$ and $+3.2\%$ end to end. A pre-registered two-one-sided-test style equivalence check on the mapping stage at a $\pm10\%$ margin returns $+0.0\%$ with a 90\% bootstrap CI of $[-1.9\%,+0.4\%]$, i.e.\ equivalent, on the replicated input; the single-replicate larger input is indeterminate by construction. The storage-mode effect is therefore a reduction in peak workspace while preserving final output size and content.

\subsection{Semantic validation and graph reproducibility}\label{subsec3.5}
The tool ships a validation stage that executes SPARQL against the graph it just wrote and compares every answer with an independently computed VCF-side result from cyvcf2, with \texttt{bcftools} supplying exact FILTER text. Across the campaign this stage ran 78 times over 143 cells, on N-Triples, HDT and COTTAS artifacts, under four SPARQL engines (QLever, Comunica, an HDT-backed engine and the DuckDB-backed COTTAS engine). In v3.1.0 it also applies the vocabulary's SHACL shapes by default (Section~\ref{subsec2.1}); the default profile ran on 58 validations and passed all of them with no violations, at 0.8--396.8\,s each. The query-cost cells run without shapes, so that their timings measure the queries alone. Table~\ref{tab:validation-evidence} summarizes what that produced. The complete thirteen-query workload is defined in Table~\ref{tab:semantic-queries}: Q1--Q6 summarize records and genotypes, Q7--Q10 check metadata and graph structure, and Q11--Q13 compare digest summaries of record, INFO, and FORMAT values. Fourteen further graph-integrity preflight queries run before them.

Of 988 paired query comparisons, 984 returned exact equality and 4 returned a verified not-applicable: the two genotype questions on each of the zero-record fixture's two artifacts, since a file with no records has no genotypes. None mismatched. All 1{,}144 cross-check invariants passed. Engine agreement was recorded as true in all 76 completed validations, including the 25 in which all four engines answered independently; the two sites-only validations were incomplete and contribute no paired-comparison result. The tool's own native decode check --- stream the built representation back and compare source and decoded triple counts --- passed 152 times out of 152 across 118 HDT and 34 COTTAS artifacts. Syntactic validation by \texttt{rapper} passed on all 76 artifacts it reached.

Three graph-stability properties were tested directly rather than assumed. Two conversions of the same input produced byte-identical N-Triples (SHA-256 \texttt{661578e7\ldots}, 17{,}098{,}746 triples, zero duplicate lines). A compress-then-decompress round trip reproduced that same digest exactly. Rebuilding the index over an already-indexed artifact left its digest unchanged.

\textbf{How much would this validation catch?} A mutation-score experiment injected 113 targeted corruptions into the graph --- wrong allele, wrong coordinate, wrong filter token, wrong file metadata, blank nodes, flipped phasing, corrupted sample index --- and measured how many the validation suite detects. With all three SHACL profiles enabled it detected all 113, a score of 1.000. The two layers contribute differently, and the split is the useful part of the result. The comparison queries alone detect 96 (0.850); the other 17 fall into ten classes that the queries structurally cannot see --- allele kind and value are counted but never compared against the raw ALT column, header attribute values and the derived contig count are counted but not read, and record index, sample index, called allele and phasing status have no oracle --- and the shapes catch every one of them. Both unmutated controls pass in both sample representations, so the shapes are not simply rejecting conformant graphs. The perfect score has a price: the two profiles that check uniqueness and value agreement self-join the graph and cost 33.7\,s and 73.2\,s on a 2{,}000-triple graph, against 1.7\,s for the default profile, which checks cardinality and datatypes only. v3.1.0 therefore applies the default profile to every validation and reserves the full set for inputs up to 16\,MiB.

\subsection{Retrieval cost: SPARQL against a VCF parser on identical work}\label{subsec3.6}
Figure~\ref{fig:retrieval} reports the retrieval experiments. The protocol, fixed before the run: three replicates; a cold start per cell; identical question scope on both sides; cyvcf2 as the VCF-side oracle with \texttt{bcftools query} for exact FILTER text; engine setup time reported separately from query time; and representation-build time excluded from both columns and reported instead in Section~\ref{subsec3.4}. Result equality was verified before any timing was compared --- every comparison in Figure~\ref{fig:retrieval} is a \texttt{PASS}.

The dominant finding is that the artifact barely matters and the engine matters a great deal. On the 17.1M-triple graph, per-query times against N-Triples, HDT and COTTAS differ by under 5\% for the same engine (Figure~\ref{fig:retrieval}c), because each engine materializes what it needs. Across engines on the 0.96M-triple graph, the same thirteen questions cost a mean of 1.1\,s under QLever, 23.4\,s under Comunica, 38.2\,s under the COTTAS engine and 45.1\,s under the HDT-backed engine (Figure~\ref{fig:retrieval}b), with all four engines agreeing in every run. QLever is the outlier, 20--40$\times$ faster than the rest, while the other three lie within a factor of two of one another.

The comparison with the VCF parser depends on whether one question or the complete workload is evaluated. For a \emph{single} question against the 17.1M-triple graph, cyvcf2 must scan the VCF and costs 11.5\,s regardless of which question it is, whereas QLever answers in 0.005--4.62\,s: SPARQL is $2.5\times$ to $2300\times$ faster per question (Figure~\ref{fig:retrieval}a). For the \emph{whole thirteen-question batch}, cyvcf2 answers all of them in one 12.4\,s pass, while QLever needs 17.1\,s of query time plus 22.8\,s of one-time setup. The RDF path wins on selective, repeated and ad hoc interrogation; the parser wins on a single exhaustive sweep. These timings exclude the one-time conversion and representation-build costs reported in Section~\ref{subsec3.4}.

\subsection{External linking}\label{subsec3.7}
The tool exposes external linking as a separate \texttt{--mode link} stage with three tiers, and all three were exercised on the same 86-record fixture (Table~\ref{tab:linking}). These measurements characterize execution and provenance capture on the test fixture; they do not establish linking accuracy on a real cohort.

Tier 1, identifier rewriting, works and is cheap: on an 86-record graph the \texttt{rsid-dbsnp} linker emitted 86 \texttt{linking:sameVariantAs} triples to \texttt{identifiers.org} dbSNP IRIs in 2.5\,ms with no network access, no skipped records and a recorded manifest digest. But tier 1 is by construction a syntactic rewrite of an identifier that is already in the ID column; it demonstrates plumbing and provenance capture, not entity resolution. The fixture's identifiers are synthetic (\texttt{rs0000001}--\texttt{rs0000086}), so all 86 of those links point at dbSNP records that do not exist, and the linker records its assertion as unverified for exactly that reason.

Tier 2, coordinate-interval lookup against a bundled reference, ran successfully and produced \emph{zero} links from the same 86 records. The run is well-formed --- it records the reference digest, the GRCh38 assembly, 86 unique keys and no skipped records --- but the bundled demonstration gene set does not overlap the fixture's coordinates. Tier 2 is therefore demonstrated to execute, not demonstrated to link.

Tier 3, live service resolution against Ensembl, ran with network access enabled for that cell only. It batched the 86 keys into one request, which returned HTTP 200 after 20.8\,s with an empty result (the recorded response digest is that of \texttt{\{\}}), and it emitted no links. That is the correct answer: Ensembl knows none of the fixture's synthetic identifiers, so where tier 1 linked all 86 of them unchecked, tier 3 correctly linked none. The run records the request hash, response digest, HTTP status and fetch time, so the result can be audited, although, as a live service, it is not reproducible offline. The custom-mapping path was skipped for want of a supplied rules file.

The fair summary is that the linking architecture --- tiered linkers, offline and live operation, per-linker manifest, reference and response digests, link counts and timings in the run record --- is implemented, instrumented and runs end to end, and that its real-world yield is untested because the fixture contains no real identifiers. A credible demonstration needs a real annotated cohort against a real dbSNP or Ensembl release with recall and precision reported against a known overlap, and that experiment has not been run.

\subsection{Policy attachment demonstrator}\label{subsec:policy}
VCF-RDFizer also includes a demonstrator plug-in, \texttt{vcf-rdfizer-policy} (v0.1.0), that attaches ODRL policies \cite{odrl_2018} to RDF graphs and derives per-request release views. It postdates v3.1.0 and is not part of the benchmark campaign. The engine has three generic steps, and each is configured in Turtle rather than code:
\begin{itemize}
\item \emph{select}: a rule targets a resource, or a selection computed by a declared selector type, which is a SPARQL \texttt{SELECT} with named parameters;
\item \emph{partition}: a profile's ownership rule, a property path plus IRI subtrees, states what a withheld resource takes with it;
\item \emph{decide}: ODRL semantics, deny wins, and anything no permission covers is withheld.
\end{itemize}
A VCF Core profile supplies region and variant selectors and the ownership rule for VCF-RDFizer's graphs. Under it, withholding a record also withholds its call, alleles and per-sample calls, and withholding a file withholds everything under it.

The example is a synthetic cohort of five single-sample VCFs: 139 records at real GRCh38 loci, with synthetic genotypes, converted by v3.1.0 in both sample profiles. Each participant's consent is a policy on their file. Two cohort-wide rules target a genomic region (\textit{BRCA1}, readable only for clinical care) and a single variant (the APOE $\varepsilon$4-defining rs429358, readable only for disease-specific research). Purposes are GA4GH Data Use Ontology terms \cite{lawson2021duo}, matched through the DUO hierarchy, so a disease-specific study falls within a general-research consent but not the reverse (Figure~\ref{fig:policy}a). Any RDFS or SKOS purpose vocabulary can replace DUO.

Evaluated for three requesters, one set of policies yields three release views (Figure~\ref{fig:policy}b), with 37, 76 and 56 of the 139 records released. Each view differs in which consents admit which files: P003's health-research consent admits the disease-specific study but not a general-research request. It also differs in which cohort rule is lifted: \textit{BRCA1} for clinical genetics only, and rs429358 for the disease-specific study only. P004 withdrew, and that prohibition overrides every permission. Each view passes four structural checks: the policy digest matches, nothing a binding prohibition owns is present, nothing lacks a permission, and no reference dangles. Each view is also compared with an oracle, which evaluates the same policy on a minimal graph built directly from the VCF text and so never touches the converter. The view must equal it exactly: an extra record is a leak, and a missing one is over-withholding. All three views pass in both sample profiles, and each of six planted faults is detected: a reinstated \textit{BRCA1} record, a restored triple of the withdrawn file, a deleted record, a dangling reference, a swapped view, and a changed policy. The check also caught a real defect during development. Every record decision was correct, but a withdrawn file's header and sample set remained in every view, which the record counts alone could not show. That defect is why the partition is defined by ownership rather than by a list of record subtrees.

Because the policies are RDF in the same graph as the data, one SPARQL query can ask which records a collaborator may not receive, and under which rule. A VCF has no place to state a region- or variant-level policy, and repository consent codes apply to whole datasets. Other partitions need no code either. A selector for records below a QUAL threshold, declared inside a policy file, withholds 38 of the 139 records. Given a different ownership rule, the same engine partitions a non-VCF graph of documents and their sections. The demonstrator's limits are deliberate and stated in its documentation:
\begin{itemize}
\item the cohort is a small synthetic fixture;
\item evaluation happens in memory, after conversion;
\item views keep the original IRIs, since there is no pseudonymization;
\item obligations are recorded but not enforced.
\end{itemize}
It provides governed release, not anonymization: a released genotype remains identifying.

\subsection{Configuration coverage, operating modes and memory feasibility}\label{subsec3.8}
A ten-row covering set exercised every value of all seven configuration axes --- sample representation, INFO representation, storage mode, RDF compression, representations, artifact compression and HDT strategy --- and all ten rows exited 0 and passed validation, including the shapes. Pairwise coverage is complete except for three combinations the wrapper structurally refuses (\texttt{--hdt-strategy single} beside space-optimized storage, beside COTTAS, and beside \texttt{hdt,cottas}), so the remaining gaps are specification, not omission. Each of the tool's operating modes --- \texttt{tsv}, \texttt{compress}, \texttt{decompress}, \texttt{index} for HDT and for COTTAS, a conversion-only phase and a validation-only phase --- ran independently and exited 0, confirming that conversion and validation are separable stages rather than one monolithic command.

A feasibility sweep crossed three memory ceilings (8, 16 and 31\,GB) with three configurations on a one-million-record input. All nine cells completed; peak resident memory was 1.34--1.93\,GB in every case, below every requested ceiling, which is consistent with the flat memory scaling in Section~\ref{subsec3.3}. This experiment carries one caveat that must be reported with it: the ceiling was requested through Docker memory limits but the harness could not confirm that the pinned release forwards them to its container invocations, so these cells establish that the workload is memory-light, not that it survives a genuinely enforced cap.

Finally, the INFO representation axis has a measurable cost: on the structural-variant file, structured INFO produced 96.75M triples against 89.01M for raw INFO ($+8.7\%$) and a 7.4\% larger artifact, and on the 100{,}000-record \texttt{HG005\_GRCh38} input it produced 17.10M against 12.52M ($+36.6\%$). Raw INFO still carries the allele layer here, because the expanded sample profile references it (Section~\ref{subsec3.10}); before that fix the raw arm omitted it and the difference looked larger than it is. Structured header representation costs almost nothing by comparison (17{,}098{,}746 against 17{,}094{,}293 triples, $+0.03\%$).


\subsection{Cross-encoding equivalence and remaining limitations}\label{subsec3.9}
\textbf{Both sample encodings are equivalent across every engine and artifact.} The equivalence experiment converted one 10{,}000-record, multi-sample fixture in both sample representations and both storage modes, built HDT and COTTAS from each, and ran the full twenty-seven-query suite (the fourteen preflight checks and Q1--Q13) under all four engines against all three artifacts. All sixteen validations passed with all four engines in agreement, on graphs of 0.96M triples (expanded) and 0.79M triples (condensed). The complete condensed cell took 70.4\,min end to end. Two further cells asserted that the tool must refuse \texttt{--hdt-strategy single} beside COTTAS and beside space-optimized storage, and it did, with exit status 2. The tested workload therefore supports representation equivalence across both sample encodings, all three artifacts, and all four engines.

\textbf{Scope limits.} The sample ladders hold INFO fields fixed while changing sample columns, so they characterize structural scaling rather than INFO-dependent cohort summaries. Corpus conversion covers eight 250,000-record slices and one whole genome; the 2,504-sample chromosome-20 call set is exercised only through 10,000-record slices. The full paired query workload is run on fixtures and a 100,000-record \texttt{HG005\_GRCh38} slice. Correctness evidence for the corpus-breadth cells is limited to native decoding and source-versus-decoded triple counts. These scopes support comparisons within the measured workloads, without establishing whole-cohort throughput or exhaustive value-level validation for every public input.


\subsection{Issues identified during testing and their resolution}\label{subsec3.10}
Testing identified problems in measurement, conversion, and validation. This subsection brings together the historical benchmark context, the observed failures, and the corresponding corrections. The performance and semantic-equivalence results elsewhere in this paper describe the current campaign and its stated input scopes.

\textbf{Measurement and reporting in the legacy benchmark.}
The earlier six-file, batch-oriented benchmark exposed two measurement problems. Partitioned compression wall times were under-reported; the timing implementation was corrected in commit \texttt{fb48e50}, and the affected historical durations were reconstructed from wrapper logs and execution timestamps. In addition, an input-size column labelled \texttt{.vcf.gz} actually contained the uncompressed VCF stream size. For example, the retained \texttt{NG131FQA1I.vcf} contains 1{,}215{,}509{,}730 bytes, matching the reported 1215.5\,MB. Performance tables now distinguish compressed download sizes from uncompressed processed inputs.

The compression denominator also affected interpretation. The legacy HDT reduction of approximately 92--95\% was measured against uncompressed N-Triples. In the current corpus experiment, HDT is 1.36--1.82 times the size of the stored gzip-framed N-Triples. These observations use different reference artifacts and do not constitute a like-for-like change in compression performance. The legacy conversion and compression tables are therefore excluded from the current performance analysis. The storage evaluation instead pairs the two supported aggregate modes on identical inputs and measures peak workspace separately from final artifact size.

\textbf{Header-only input omitted its declared samples.}
A VCF with a declared sample column but no data records produced a graph without the \texttt{vcfc:SampleSet} and \texttt{vcfc:VCFSample} resources declared by its header. The emitters derived the file IRI from a source name learned from the first data row. The predicate and class censuses (Q9 and Q10) detected the missing resources. Emitting the sample set from the header increased the graph from 181 to 189 triples and allowed validation to complete. The same test exposed an incorrect oracle expectation: \texttt{preflight\_sample\_gt\_inventory} expected one \texttt{vcfc:sampleId}, although that property belongs to a per-record \texttt{vcfc:SampleCall}. The oracle was adjusted to expect no such calls when the file contains no records.

\textbf{COTTAS query execution and timeout enforcement.}
The initial COTTAS query implementation used pycottas' RDFLib store. On the condensed representation it completed the fourteen preflight queries and Q1--Q4, then failed to complete \texttt{q05\_sample\_genotype\_counts}. Two attempts ran for approximately 41\,h and 10\,h at roughly 190\% CPU before being stopped. The second had a 1,800\,s per-query timeout and a 14,400\,s validation budget, but neither interrupted the in-process query. Both runs are archived. Replacing this path with the DuckDB-backed Comunica engine reduced Q5 to 2--5\,s and the thirteen-query workload on the 0.96M-triple comparison graph to 38\,s, against 1,402\,s through RDFLib (Section~\ref{subsec3.6}). Query execution now occurs where the timeout can terminate it. The completed cross-engine measurements use this engine.

\textbf{SHACL report interpretation.}
Integrating the vocabulary's SHACL shapes exposed two reporting errors. The validator treated \texttt{pyshacl}'s \texttt{conforms} flag as a blocking verdict even for recommendations, causing conformant INFO declarations without \texttt{Source} to be rejected. Its violation matcher also expected a report format that \texttt{pyshacl} did not emit. The parser was corrected to classify results by severity, with only \texttt{sh:Violation} blocking a run.

\textbf{Allele references without corresponding resources.}
Applying the shapes to the configuration covering set identified three failing rows, all combining raw INFO with expanded samples. Allele resources were emitted only for structured INFO, but expanded genotypes referenced them through \texttt{vcfc:calledAllele} regardless of the INFO setting. A 1,000-record test produced 1,972 such references without the corresponding allele descriptions. The comparison queries counted those edges without following them, whereas the shapes reported 5,916 violations.

The emitter was changed to produce the allele layer when either representation requires it. The census oracle also needed the same dependency rule: its initial expectation reproduced the emitter's assumption and rejected the added triples. After both were updated, all ten covering-set rows passed. Each affected row gained 10,846 triples, while the other seven outputs remained byte-identical. Regression checks cover all four INFO/sample representation combinations and require every referenced allele to be described.

\textbf{Missing-token preflight false positives.}
The preflight reports contain 608 checks: 599 passed and nine flagged the missing-token rule, all on the 100,000-record \texttt{HG005\_GRCh38} input. The rule looks for bare \texttt{"."} literals that should have been typed as \texttt{vcfc:Null}. It first returned 20 rows there, all on \texttt{vcfc:fieldNumber} or \texttt{vcfc:genotypeString}, where a dot is legitimate: \texttt{Number=.} denotes variable cardinality, and a fully missing genotype is written \texttt{.}. The rule was narrowed to exclude those two predicates. In v3.1.0 it still returns ten rows, and they are the same case one layer over: the header declares ten INFO fields with \texttt{Number=.}, and the header-attribute layer also carries each declaration's Number attribute verbatim as a \texttt{vcfc:attributeValue} of \texttt{"."}. A follow-up change excludes that attribute's value as well while still reporting a bare dot on any other attribute; it postdates v3.1.0, so the ten flags remain in this campaign's reports. None of the flags reflects malformed output.

\textbf{Sites-only fixture limitation.}
The sites-only fixture produced 245 triples and a valid HDT artifact, but its two validations ended with \texttt{EXECUTION\_FAILED}. The fixture declared a FORMAT column without sample columns, which \texttt{bcftools} rejects. This is a fixture/oracle limitation rather than evidence that the generated graph failed semantic comparison. No completed paired result is claimed for this input, and a conformant sites-only fixture remains necessary to establish that coverage.


\section{Discussion}\label{sec4}
The current benchmark demonstrates conversion across heterogeneous public VCF inputs, with eight 250,000-record slices and one whole 2.36\,GB genome processed through RDF, HDT, and COTTAS construction. The whole-file output contains 657.43 million triples and completes in 16.07\,h. On the replicated record ladder, peak resident memory remains between 1.0 and 1.7\,GB over a hundredfold increase in records, while queryable-representation construction dominates end-to-end time. These results support a memory-bounded workflow whose practical resource requirements are governed primarily by build time and disk space.

The paired storage-mode experiment quantifies the temporary disk requirement directly. Plain and space-optimized modes produce identical triples and final artifacts, while space-optimized mode reduces peak host workspace by 7.7--9.2 times at a 3--5\% increase in end-to-end time (Section~\ref{subsec3.3}). This trade-off is useful when temporary storage limits conversion capacity. Final artifact size alone would not capture it.

Sample representation has a larger effect on graph size. Holding 10,000 records fixed, condensed triple production increases by 0.9\% from 1 to 2,504 samples, whereas the expanded graph reaches 432 times the condensed graph at 2,504 samples. Counted in bytes the gap is smaller, 69 times in HDT, because the condensed vectors still carry every sample value; the condensed HDT nonetheless remains smaller than the input VCF. The expanded representation offers individual sample-call resources, but its projected workspace for the whole chromosome-20 cohort exceeds the tested disk budget. The condensed representation is therefore the practical setting for extending the measured workload to cohort scale. Whole-cohort feasibility still requires a dedicated run, because the campaign evaluates that input through 10,000-record slices.

\subsection{Semantic Representation of VCF Challenges}\label{subsec4.1}
%% discuss the impact of the vocabulary here --> how the vocabulary is novel and useful
Because VCF encodes both biological observations and file-structure semantics, representation in RDF requires a vocabulary that explicitly models the structural elements of the format itself.
Existing ontologies capture important aspects of genomic variation, including FALDO for genomic coordinates, the Sequence Ontology (SO) \cite{seq_ont_2005} for variant types, GENO for genotype modeling \cite{gene_ont_2000}, and HERO for clinically oriented genomic semantics \cite{hero-genomics_2025}, but none fully represent the structural semantics of the VCF specification. 

VCF-RDFizer addresses this gap by targeting the VCF Core Vocabulary (\url{https://w3id.org/vcf-core/vocab\#}) \cite{vcfc210}, a version-aware semantic layer aligned with the structural components of the VCF specification while remaining interoperable with existing genomic ontologies. Keeping the vocabulary a separate, versioned artifact means the converter and the model can evolve and be evaluated independently, and the SHACL shapes the vocabulary publishes become the converter's own conformance test. 

The benchmark supports a division of responsibility between query-based comparison and graph conformance. The paired queries test whether VCF-derived summaries, metadata, and digest histograms agree with the RDF results; SHACL checks cardinality, datatypes, and structural relationships. In the controlled mutation experiment, the queries detect 96 of 113 injected corruptions and the combined validation detects all 113 (Section~\ref{subsec3.5}). This evidence is specific to the tested mutations and input sizes. Agreement with the VCF parser assesses preservation of represented content; it does not establish the biological correctness of source calls.


\subsection{The Published VCF-RDFizer Software Tool}\label{subsec4.2}

\textbf{Transformation Architecture and Performance}.
RML provides a declarative framework in which semantic intent is separated from procedural parsing logic, allowing transformation rules to be versioned and reused across datasets. The mapping stage is not the bottleneck: in the current campaign RMLStreamer accounted for 12.2--41.4\,s of a 41\,s to 5{,}476\,s run on the records ladder and 146.8\,s of the 16.07\,h whole-file conversion, with peak resident memory flat at 1.0--1.7\,GB across a hundredfold change in input (Section~\ref{subsec3.3}). End-to-end cost is dominated by building the queryable representations.

The pipeline includes a lightweight preprocessing step that converts VCF files into tabular intermediates compatible with existing RML engines. Because VCF is not yet supported as a native logical source within RML, this step enables stable field extraction and declarative mapping execution. Future extensions to the RML ecosystem could support VCF as a native logical source and eliminate the preprocessing stage.

The paired SPARQL/VCF-parser workload supplies the field-level evidence that syntax checks cannot: 984 of 988 comparisons returned exact equality and the other four were verified not-applicable (Section~\ref{subsec3.5}). The substantial expansion in raw RDF size remains an operational limitation and motivates both archival compression and directly queryable compressed representations.


\textbf{Compression Strategies for Semantic Genomic Data}.
Gzip and Brotli provide packaging options for transfer and archival storage. The current covering-set experiment exercises the supported values of both compression axes and validates their outputs (Section~\ref{subsec3.8}); it does not provide a dedicated compression-ratio or throughput comparison between the two codecs. Packaged artifacts must be unpacked before direct querying.

For compressed RDF that remains queryable, VCF-RDFizer offers both HDT and COTTAS. HDT combines a dictionary and compressed triple structure with indexed triple-pattern access \cite{hdt_2013}. COTTAS stores RDF as a Parquet triple table and uses columnar organization and block-range indexes to evaluate patterns over compressed data \cite{cottas_2025}; VCF-RDFizer builds it with pycottas and queries it with a DuckDB-backed Comunica engine \cite{comunica_cottas_2026}. These formats provide complementary design points, and the COTTAS paper's general RDF benchmarks must not be assumed to predict VCF-RDFizer-specific size or query performance.

Representation construction operates on bounded, record-safe chunks. HDT parts are merged pairwise with \texttt{hdtc} under a fixed memory budget \cite{hdtc_2026,Diefenbach2020HDTCat}, while COTTAS parts are combined in one streaming $k$-way merge. Final representations are indexed and checked through native streamed decoding and source-versus-decoded triple counts. Temporary representation parts, merge workspaces, indexes, and converter scratch data still contribute to peak disk use.

The corpus measurements show a consistent storage/build-time trade-off (Figure~\ref{fig:representations}). COTTAS occupies 0.37--0.55 times the stored gzip-framed N-Triples and 0.27--0.37 times the HDT built from the same graph. HDT occupies 1.36--1.82 times the stored N-Triples, but builds faster: COTTAS requires 1.5--3.0 times its construction time. Artifact choice has little effect on query time for a fixed engine in the tested workload (Section~\ref{subsec3.6}). These results make storage size and construction cost the principal measured trade-offs between HDT and COTTAS.


\textbf{Tool Availability and Community Impact}.
Following best practices for research software publication \cite{jimenez_2017_f1000}, VCF-RDFizer is distributed as open-source software with public version control and synchronized releases across GitHub, PyPI, Conda-Forge, and DockerHub under the MIT License. 
Public issue tracking, release notes, and a documented maintenance plan support transparency and long-term sustainability.


\textbf{Queryable Genomic RDF as a Complementary Access Layer}.
The selected workload illustrates the practical scope of SPARQL even before external annotations are linked. Density windows, allele-shape summaries, Ti/Tv, FILTER distributions, per-sample missingness/genotype classes, and genotype-derived AC/AN are recognizable bioinformatic operations rather than synthetic graph queries. Reproducing them from RDF tests whether genomic coordinates, alleles, filter semantics, sample identities, FORMAT values, and record-to-sample relationships survive semantic lifting.

The longer-term value of SPARQL is not limited to reproducing operations that VCF-native tools already perform well. Once variant records use stable IRIs and ontology-aligned predicates, a query can combine variant/genotype constraints with linked gene, phenotype, pharmacogenomic, provenance, or policy statements without exporting each relation into a new ad hoc table. Multiple VCF-derived graphs can be queried through the same data model, and Comunica's source-oriented architecture can query one or more local HDT files through a common SPARQL interface \cite{Taelman2018Comunica,comunica_hdt_docs_2026}. COTTAS provides another compressed query path through the same Comunica architecture \cite{cottas_2025,comunica_cottas_2026}. These capabilities could support cohort QC across independently produced VCFs, integrated variant prioritization, knowledge-graph enrichment, and governance-aware retrieval using standards such as ODRL \cite{odrl_2018}. Section~\ref{subsec:policy} demonstrates the attachment side of this on a synthetic cohort: consents on files, and rules on a region and a variant, evaluated per request and verified against the source VCFs.

VCF-native tools remain an essential comparator and, for many format-specific operations, are likely to remain the operational baseline. bcftools and cyvcf2 operate directly over VCF/BCF and expose highly optimized parsing, indexing, and genotype access \cite{BCFtools,cyvcf2_2017}. The RDF pathway adds conversion and representation-build costs in exchange for a generic graph query model and semantic joins. It should therefore be positioned as complementary infrastructure rather than an unconditional replacement for VCF/BCF.

A fair comparison must separate one-time conversion/index construction from repeated query execution; apply identical scopes and allele/genotype rules; record cold-cache conditions, result cardinality, wall time and repetitions; and verify result equality before comparing speed. Section~\ref{subsec3.6} follows that protocol, and the answer is conditional rather than directional. On a 17.1M-triple graph, a \emph{single} question costs cyvcf2 11.5\,s because it must scan the VCF whichever question it is, while QLever answers in 0.005--4.62\,s --- between $2.5\times$ and $2300\times$ faster. For the \emph{whole} thirteen-question batch, cyvcf2 answers all of them in one 12.4\,s pass against 17.1\,s of query time plus 22.8\,s of one-time setup for QLever. The RDF path therefore wins on selective, repeated and ad hoc interrogation and loses on a single exhaustive sweep, and neither reading holds without the other. The artifact makes almost no difference --- N-Triples, HDT and COTTAS are within 5\% for the same engine --- whereas the engine does: on the same 0.96M-triple graph the thirteen questions take 1.1\,s under QLever and 23--45\,s under the other three engines. Engine selection, not representation selection, is the performance decision, which is why QLever is the default. None of these figures includes the conversion cost in Section~\ref{subsec3.4}, which the graph must pay once before any of it applies.

\subsection{Impact and Future Work}\label{subsec4.3}
%% this should be short and punchy --> clearly state what needs improvement, what we want to do next, and how it will impact the computational biology community
This work demonstrates that VCF datasets can be systematically transformed into RDF using declarative RML semantic mappings. 
More importantly, we show that traditionally static file-based genomic variant data can be reliably converted to structured knowledge graphs, capable of linking, semantic querying, and governance-aware data sharing.

Three priorities follow from the current measurements. First, validation should scale beyond the fixture and 100,000-record workloads. The two SHACL profiles that check uniqueness and value agreement require substantially more time than the default profile, motivating streaming or indexed implementations of those checks before applying the full suite to large cohorts. Second, conversion and validation should extend from slices to whole multi-sample inputs, including the 2,504-sample chromosome-20 call set in condensed form. Third, linking requires evaluation against a released dbSNP or Ensembl resource with known overlaps and explicit precision and recall. The current experiment shows all three tiers executing, including a live Ensembl query, but on a fixture whose identifiers are synthetic and whose coordinates miss the demonstration reference, so none of them has yet been measured against real overlaps.

Subsequent work will extend semantic coverage of heterogeneous INFO, FORMAT, genotype, header, ordered alternate-allele, and structural-variant constructs; evaluate VCF as a native RML logical source; and develop richer links to clinical and biomedical resources. A separate GIAB truth-concordance experiment could test biological call accuracy, but it must use the appropriate benchmark regions and reference-aware normalization and must remain distinct from representation equivalence.

Ultimately, VCF-RDFizer represents a step toward semantically interoperable genomic data infrastructure in which variant datasets can be compressed, linked, queried, validated, and governed as part of a broader biomedical knowledge-graph ecosystem.
