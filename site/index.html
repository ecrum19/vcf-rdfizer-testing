RQ2 What does the explicit representation in RDF enable in a linked, policy-aware workflow?

Shared identifiers enabled reusable joins and policy-checked release views.

Which participant–variant–gene matches connect an observed allele to a ClinVar classification in the -gene set, and which matches may each requester receive? The RDF workflow links converted VCFs to ClinVar and gene resources, materializes a validated release view for each requester, and queries each view with SPARQL. The conventional workflow harmonizes contigs, annotates with bcftools, and applies the same case definition and simulated release rules in Python. The two workflows must return identical sorted participant, gene, contig, position and allele tuples for every requester. Scenario 1: gene-span slices of single-sample VCFs (). Scenario 2: 1000 Genomes participants. Scenario 3: the complete VCF. Scenario 4: the complete VCF under layered consent, with requesters. Consent and access conditions are simulated; the VCFs are public. Every stage used VCF-RDFizer .

Findings

Across all scenarios, the RDF and conventional workflows returned identical requester-specific participant–variant–gene match sets, and every materialized release view passed the policy and source checks. Released-record counts also agreed in . In , the RDF views additionally released symbolic structural-variant records in restricted cancer-predisposition genes to disease-specific and general research, because VCF-RDFizer links no symbolic allele to a gene; no match changed. The release checks could not detect these records, because they use the same gene links as the policy evaluator.

Shared variant identity changed how one release rule was expressed: restricting a single variant required a policy edit, without changes to the policy engine, and selected the record regardless of contig naming. The other changes were similarly small data edits in both workflows ( changes were data-only in the conventional workflow), so the result demonstrates reusable configuration for an identity-targeted rule rather than a general usability advantage.

Most linked-workflow cost occurred before query execution: conversion, linking, and the materialization, validation and indexing of each release view. After the preprocessing both workflows share, the conventional workflow annotated, selected and released records for every requester in seconds per scenario; conversion and linking alone took minutes in the RDF workflow, more than times as long. Queries over non-empty release views took seconds in every scenario, suggesting that the fixed ClinVar join dominated the measured query rather than establishing scale-independent SPARQL performance.

RQ3 Under which workloads and representation choices are the costs practical?

Semantic coverage and practical cost depend on representation and workload.

Semantic coverage across converters

A shared-input comparison evaluates other executable converters alongside VCF-RDFizer on the same inputs, each with its most complete available options. Content questions are translated to each vocabulary and compared with the same source-derived oracle, normalization, comparator and QLever build used for VCF-RDFizer. A question is reported as not represented when the graph lacks the required information.

Conversion cost

Controlled scaling series vary one dimension at a time: the record-count series processes increasing numbers of HG005 records, and the sample-count series holds 1000 Genomes records fixed while varying the sample count from to under both profiles. Stage timings, resident memory, transient workspace and retained artifact sizes are measured separately.

Retrieval cost

Retrieval experiments compare individual questions, the -question batch and regional questions in QLever against cyvcf2 and bcftools VCF access, checking completed answers for agreement. They also compare the SPARQL engines and RDF artifacts, and QLever on graphs up to the complete HG005 VCF. Regional queries apply the same POS-based selection on every execution path. Setup and query execution are reported separately.

Notes and provenance
  • The core benchmark ran the published image on hosts with identical hardware (below).
  • The large-graph builds and retrieval and the index-storage measurements ran on a third host, vcf-bench-3, with the same CPU model and core count and an older kernel (below). Its harness wrote no environment record, so its details were read from the host after its runs; the running kernel was booted, and Docker installed, before the first of them, and neither has changed since.
  • The linked workflow, regional retrieval, large-graph retrieval at and triples, the consumer WGS validation run and the converter comparison used the published VCF-RDFizer . On the same HG005 records, both releases wrote identical sorted triples.
  • The linked workflow's consents are simulated and do not express any real participant's wishes.
  • Only the runs behind reported results are shown, including reported execution failures. Superseded and pre-release runs are on the repository's legacy branch.
  • The generated RDF is not archived; every cell records the command, commit and image digest that produced it.
