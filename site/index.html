RQ1 Which aspects of VCF information are preserved and verifiable?

Source comparisons and structural validation provide complementary evidence.

Validation compares SPARQL results () with corresponding answers derived independently from the source VCF using cyvcf2 and, for exact FILTER text, bcftools; SHACL shapes check structural constraints that the source-comparison queries do not observe. In the base campaign, paired validation runs covered difficult-input fixtures, a single-sample fixture under both sample profiles and three RDF artifacts, and HG005 slices up to triples. A fault-injection experiment applies deliberate corruptions, and a later consumer WGS validation run tests records from with the default shapes.

Consumer WGS validation run: , first records

Findings

Across the base campaign, all applicable SPARQL results agreed exactly with their source-derived counterparts after normalization; further genotype-query instances were verified as not applicable to files without genotypes. Every engine that answered returned the same normalized answers. This establishes representation equivalence for the fields the queries cover, not the biological correctness of the source calls.

Source comparison and structural validation detect complementary defects. The source-comparison queries did not detect of the injected faults, which fall into mutation classes that change relationships or values the queries do not observe, such as the allele a genotype references or the value of a header attribute. The default SHACL profile, the only profile practical at scale, detected none of them; all shape profiles together detected every one, but the deeper profiles have not been shown practical at whole-VCF scale.

For the consumer WGS validation run, all thirteen query results agreed, and batched default-shape validation reported no violations on triples.

RQ2 What does the explicit representation in RDF enable in a linked, policy-aware workflow?

Shared identifiers enabled reusable joins and verified release views.

Which participant–variant–gene matches connect an observed allele to a ClinVar classification in the -gene set, and which matches may each requester receive? The RDF workflow links converted VCFs to ClinVar and gene resources, materializes a validated release view for each requester, and queries each view with SPARQL. The conventional workflow harmonizes contigs, annotates with bcftools, and applies the same case definition and simulated release rules in Python. The sorted participant, gene, contig, position and allele tuples must agree before timings are compared. Arm 1: gene-span slices of single-sample VCFs (). Arm 2: 1000 Genomes participants. Arm 3: the complete VCF. Arm 4: the complete VCF under layered consent, with requesters. Consent and access conditions are simulated; the VCFs are public. Every stage used VCF-RDFizer .

Released records: release views compared with the conventional workflow

Linksets: records linked to shared identifiers

Findings

Across all arms, the RDF and conventional workflows returned identical requester-specific participant–variant–gene match sets, and every materialized release view passed the policy and source checks. Released-record counts also agreed in . In , the RDF views additionally released symbolic structural-variant records in restricted cancer-predisposition genes to disease-specific and general research, because VCF-RDFizer links no symbolic allele to a gene; no match changed.

Shared variant identity changed how one release rule was expressed: restricting a single variant required a policy edit, without changes to the policy engine, and selected the record regardless of contig naming. The other changes were similarly small data edits in both workflows ( changes were data-only in the conventional workflow), so the result demonstrates reusable configuration for an identity-targeted rule rather than a general usability advantage.

Most linked-workflow cost occurred before query execution: conversion, linking, and the materialization, validation and indexing of each release view. Query times ranged from seconds across the arms, suggesting that the fixed ClinVar join dominated the measured query rather than establishing scale-independent SPARQL performance.

RQ3 Under which workloads and representation choices are the costs practical?

Semantic coverage and practical cost depend on representation and workload.

Semantic coverage across converters

A shared-input comparison evaluates other executable converters alongside VCF-RDFizer on the same inputs, each with its most complete available options. Content questions are translated to each vocabulary and compared with the same source-derived oracle, normalization, comparator and QLever build used for VCF-RDFizer. A question is reported as not represented when the graph lacks the required information.

Conversion cost

Controlled scaling ladders vary one dimension at a time: the record ladder processes increasing numbers of HG005 records, and the sample ladder holds 1000 Genomes records fixed while varying the sample count from to under both profiles. Stage timings, resident memory, transient workspace and retained artifact sizes are measured separately.

Retrieval cost

Retrieval experiments compare individual questions, the -question batch and regional questions in QLever against cyvcf2 and bcftools VCF access, after verifying that every answer agrees. They also compare the SPARQL engines and RDF artifacts, and QLever on graphs up to the complete HG005 VCF. Regional queries apply the same POS-based selection on every execution path. Setup and query execution are reported separately.
