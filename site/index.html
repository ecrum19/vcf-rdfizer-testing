The paper argues that converting VCF to RDF does not pay in speed or in lines of code, but pays where variant identity, external meaning and consent must be explicit, shared across files, and checkable against the source. Fidelity: is the graph faithful to the VCF?

VCF-RDFizer's validation layer asks questions of each graph in SPARQL and answers them again, independently, from the source VCF; SHACL shapes check structure no oracle observes. This section shows what that layer found across the campaign, how sensitive it is to injected faults, and what it found on a consumer WGS VCF.

Consumer WGS validation run: , first records

Interpretation

Wherever the paired comparison ran, the graph and the VCF agreed: of comparisons were exactly equal, the other were genotype questions on a file with no records, and every engine that answered agreed. That establishes representation equivalence for the fields the questions cover, not that the source calls are biologically correct.

The mutation experiment is what makes that agreement meaningful: the queries alone miss of injected faults, in classes they structurally cannot see (which allele a genotype calls, a record's index, a header attribute's value). The default shape profile, the only one cheap enough for large inputs, catches none of them; only the full profile set does, and runs it only on request and only on small inputs. On larger inputs those classes go undetected.

On a consumer WGS VCF converted to triples, all thirteen answers equal the VCF's, and the default shapes, checked in record batches, report no violations. The run used the corrected validator, whose oracle counts phase sets and compares decimal QUAL values canonically.

Interpretation

Both routes returned identical carrier lists for every requester in every arm, so the RDF route is not trading correctness for anything. 's whole-genome answer its arm-1 answer key for key, on a -fold larger input.

It does not pay in lines: realistic changes were data edits of similar size in a table-driven bcftools pipeline. It pays where the conventional route has no place to put a rule. A consent or cohort rule becomes a statement beside the data that a query can ask about and a check can verify against the VCF text, and a rule on one variant's SPDI identity needs no code and holds whatever a file calls its chromosome.

The cost is up front: conversion, linking and an index before the first question ( minutes for the whole genome's index). The query itself took minutes at every scale, because the ClinVar side of the join dominates it.

Conversion cost: scaling, storage and representations

How the cost of conversion grows with records and samples, what the storage mode trades, and what each queryable representation costs to build and store. All from the campaign.

Interpretation

Conversion is memory-bounded: across a -fold change in records the mapping stage's peak memory stays between and  GB, while triples, time and disk grow in proportion. It is disk, not RAM, that scales with the data, and space-optimized storage cuts the peak disk -fold for more time.

Triple counts mislead about size. The condensed sample profile stores per-sample values in vector literals, so its triple count barely moves from to samples while its bytes keep growing; the expanded graph has times the triples but only times the HDT bytes. Choose the profile by what must be addressable: the expanded profile makes every genotype a resource that a query, a shape or a policy can reach.

COTTAS is always the smallest artifact; HDT is larger than the gzip N-Triples it is built from. Under QLever neither is a query index: QLever builds its own, so they serve as transport and archive formats, and building them took of the whole genome's conversion hours.

When does converting pay? A break-even calculator

Interpretation

The answer is conditional, and both conditions must be stated together. Once QLever's index exists, single and selective questions are far faster in SPARQL than a parser's scan, and its cost is flat in the width of a genomic window. But the parser wins any single cold question, one exhaustive pass, and narrow lookups against a tabix index; converting pays only once questions repeat.

The engine, not the artifact, sets query cost: the packagings of one graph differ by under QLever at triples, while engines differ -fold, and the in-place engines fail of the questions at triples. QLever's cost stays linear to triples, seconds per million for the questions.
